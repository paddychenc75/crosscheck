# crosscheck

高信噪比的 AI code review。同一套流程可在 Claude Code、Cursor、Codex 中运行。

核心思路:**宁缺毋滥**。多个专项 reviewer 并行找问题,每条候选再由一个没看过推理过程的 verifier 独立核实、给出依据并打分,低于 80 分的不展示。没有问题时就说没有问题。

除了找 bug 和安全问题,它还能对照需求单和计划检查是否做到了需求,对照团队规则(含组织统一的规则包)检查规范,并把你对每条发现的判断记下来,用来减少重复的误报、逐步沉淀规则。

## 安装

还没有发布到插件市场,目前用拷贝的方式安装:克隆仓库,把 `skills/cr/` 整个目录拷到对应 agent 的 skills 目录下。

```
git clone https://github.com/paddychenc75/crosscheck.git
```

| 宿主 | 拷贝到 | 生效范围 |
|---|---|---|
| Claude Code | `~/.claude/skills/cr/` | 所有项目 |
| Claude Code | `<项目>/.claude/skills/cr/` | 仅该项目 |
| Cursor | `<项目>/.cursor/skills/cr/` | 仅该项目 |
| Codex 及其他支持 SKILL.md 的 agent | `<项目>/.agents/skills/cr/` | 仅该项目 |

以 Claude Code 为例:

```
mkdir -p ~/.claude/skills
cp -R crosscheck/skills/cr ~/.claude/skills/cr
```

拷贝后重启会话,用 `/cr` 调用。

- **更新**:在克隆的目录里 `git pull`,然后重新拷贝一次(先删掉旧的 `cr` 目录)。不想每次拷贝的话,可以改用软链接:`ln -s "$(pwd)/crosscheck/skills/cr" ~/.claude/skills/cr`,之后只需要 `git pull`。
- **拷贝安装不包含 hook。** 审查流程、审查记录、增量和出报告前的状态核对都正常工作,只是审查期间不会主动拦截危险的 git 命令和会显示凭证的操作,也不会在启动子代理时检查任务里有没有带上规则(见「确保规则被读到」)。
- **想带上 hook**:Claude Code 可以用 `claude --plugin-dir ./crosscheck` 把整个仓库作为插件加载,调用方式变为 `/crosscheck:cr`。这个参数只对当次启动的会话生效。

## 怎么用

直接用平时说话的方式提要求,不需要记参数。在 Claude Code 里用 `/cr` 开头(作为插件加载时是 `/crosscheck:cr`),Cursor 同样是 `/cr`,Codex 是 `$cr`;不加前缀直接说"review 一下"也可以。说"cr 帮助"会列出常用说法。

报告的第一行写明这次审查了什么(范围、深度、全量还是增量),看到的范围不对时可以直接说。

### 审查

| 想做什么 | 可以这样说 | 简写 |
|---|---|---|
| 审当前分支的全部改动(含未提交的) | "review 一下""帮我看看这次的改动" | `/cr` |
| 审另一个分支(不用切过去) | "看看 feature/pay 分支" | `/cr feature/pay` |
| 审一个 PR / MR | "review MR 128",或直接贴链接 | `/cr 128`、`/cr <URL>` |
| 审某几个提交 | "看看最近 3 个提交" | `/cr A..B` |
| 只看某个目录 | "只看 src/orders 下面的改动" | `/cr src/orders` |
| 快速过一遍 | "快速看一下"(只查 bug 和安全,最多 5 条) | `--quick` |
| 上线前仔细审 | "仔细看看""上线前深度审一下"(更慢、更贵) | `--deep` |
| 只关心某一方面 | "只看安全问题""只对照一下团队规范" | `--only bug,security,rules,simplify` |
| 告诉它改动的目的 | "这次是为了修复分页丢数据" | `--intent "…"` |
| 告诉它方案在哪 | "方案在 docs/plan.md" | `--plan docs/plan.md` |
| 换一个核实用的模型 | "核实换成某某模型" | `--verifier-model <模型>` |
| 测试也一起看 | "测试也一起看" | `--with-tests` |
| 从头完整审一遍 | "重新审""全量""忽略之前的" | `--full` |
| 审完顺手修掉 | "审完把问题修掉" | `--fix` |

- 不带 `--fix` 时不改任何文件。"review 一下""这个该怎么修"都不算修改请求。
- `--deep`:把改动按不同顺序多查几遍,再从调用方、影响面查一遍,减少遗漏;verifier 会尝试写最小的脚本复现 bug,也可以跑项目已有的类型检查和测试。成本和耗时明显更高。
- 没指定深度时按 standard 跑。如果这次风险高(命中 `risk_paths`、包含数据库迁移、改动超过 800 行、有测试或检查被削弱,或者改动超过 300 行且涉及鉴权、资金相关的文件),会建议改用 deep,但只是建议,不会自己换。
- 审查结果只在本地输出。插件不会往 PR/MR 发评论,也永远不会 approve、request changes 或 merge。

### 审查之后

直接回复就行,用报告里的编号指代发现。

| 想做什么 | 可以这样说 |
|---|---|
| 表态(会被记下来) | "1 对,2 误报:上游已经重试""3 先不改:下个版本" |
| 质疑某条 | "第 2 条不对吧"(会重新读代码核对,成立就解释,站不住就撤回并记录) |
| 修复 | "把第 1、3 条修掉" |
| 看没报的 | "还有别的吗""70 多分的那些是什么" |
| 指出漏报 | "你漏了 cache.ts 的并发问题" |
| 单独深挖 | "cache.ts 用 deep 再看一遍" |
| 定规则 | "以后这种别报了""以后都要检查 X" |
| 改完再看 | "再看一下"(同一目标自动做增量) |

### 维护

这些都在审查之外、由你发起。会往 GitLab 写东西的,一律先给你看要做什么,你确认后才执行。

| 想做什么 | 可以这样说 |
|---|---|
| 从 MR 评论里总结规则 | "从最近一个月的 MR 评论里总结一下规则" |
| 复核规则(负责人定期做) | "检查一下我们的规则""复核规则" |
| 看审查效果和采纳率 | "看看 review 的效果" |
| 同步团队的判断记录 | "同步一下 review 数据" |
| 同步组织规则 | "同步一下组织规则" |
| 跑评测(插件维护者) | "跑一下评测""找几个评测用例" |

### 目标的写法

| target | 含义 |
|---|---|
| 省略 | 当前分支相对主干的改动,加上未提交和未跟踪的文件 |
| 分支名 | 该分支相对主干的改动,不需要先切过去 |
| `A..B` | 指定 commit 范围 |
| 路径 | 只看该路径下的本地改动 |
| 数字或 URL | GitHub PR / GitLab MR |

另外有 `--repo <目录>`(从仓库目录之外运行)、`--base <分支>`(读不到 PR/MR 信息时指定目标分支)、`--platform github|gitlab`(强制指定平台)。

## 让它知道改动的目的

写在哪里都行,汇总成一份"意图"交给所有角色,用来判断某个行为变化是不是作者有意的、有没有做到需求。来源包括:

- MR 描述和标题;本地分支时是这段范围的提交说明。
- MR 关联的需求:GitLab Issue 用 `glab` 读;其他系统(Jira 等)在配置里写 `issue_cmd`,没配或读不到时会提示,可以用 `--intent` 补一句。
- MR 上已有的人工讨论。
- 计划文件:`--plan <文件>`,或仓库里的 `.cr/intent.md`。
- `--intent "…"`。

意图里有明确验收标准时,报告多一节"需求核对":哪一条验收标准没有做到、代码哪里没做到。意图只能解释改动,不能让安全问题不报。

审查时还会做两件事:

- **测试和检查被削弱的地方**(删了测试文件或断言、新增 `skip` / `only` / 抑制注释、降低覆盖率阈值、删除或放宽 CI 检查步骤等)由脚本扫出来,在报告里单列一节,不占缺陷的条数。
- **MR 上已经有人评论过的问题不重复报。**

## 只读与写操作边界

审查过程中不会切换分支:审查的不是当前分支时,代码用 `git show` / `git grep` 从目标分支读取,你的工作区和未提交的改动不受影响。审查过程也不会执行 `checkout`、`reset`、`stash`、`commit`、`push` 等改变仓库状态的 git 操作。`--fix` 只修改工作区里的文件,不会替你暂存或提交。要修的不是当前分支时:工作区有未提交改动就不切换、不修;工作区干净时会先问你是否切过去,同意后才切换。审查 PR/MR 时会执行一次 `git fetch` 把对方的 commit 拉到本地,不影响工作区和本地分支。

**审查过程中从不往 GitLab / GitHub 写任何东西。** 审查结束之后,只有两种写操作,都要你明确确认:

- 创建规则改动的 MR(只创建、不合并,带 `crosscheck-rule` 标签,在临时 worktree 里完成,不碰你的工作区)。
- 把判断记录推到团队数据仓库。

只读有两层保障:

| 保障 | 做什么 | 适用宿主 |
|---|---|---|
| 拦截 | 审查进行期间,直接拒绝 `git checkout` / `reset` / `stash` / `clean` / `add` / `commit` / `push` 等命令、`gh` / `glab` 的写操作,以及对仓库内文件的编辑。主 agent 和子代理都受限 | Claude Code、Codex、Cursor(通过各自的 hook) |
| 核对 | 审查开始时记下分支、HEAD、stash、暂存区和每个改动文件的内容哈希,出报告前对比。有变化就写在报告最前面 | 所有宿主 |

拦截只在审查进行期间生效,其余时间不影响任何命令:

- **开始**:真正执行收集改动的脚本时。只是查看、搜索、编辑这个脚本不算,所以开发或排查这个插件时不会被误当成一次审查。
- **结束**:出报告前核对仓库状态时。之后你让它提交、切分支都不受影响。
- **提前结束**:收集改动的脚本报错、发现没有可审查的内容或改动没有变化时,立刻解除;你中途发新消息时也会解除。
- **范围**:只对发起审查的那个会话有效,同一仓库里的其他会话不受影响。
- **凭证相关的拦截只针对你主目录下的文件**(`~/.zshrc`、`~/.netrc` 等)和 gh/glab 自己的配置。仓库里同名的文件,比如 dotfiles 仓库里的 `.zshrc`、项目里的 `.env.example`,照常可以读。

各宿主启用 hook 的方式:

- **Claude Code**:安装插件后自动生效。
- **Codex**:插件自带的 hook 需要在 `/hooks` 里审阅并信任一次。
- **Cursor**:随插件安装,配置在 `hooks/cursor-hooks.json`。

没有 `jq` 也没有 `python3` 时拦截不生效,只剩核对。

## 配置文件

个人配置放在 `~/.crosscheck/config`,每行一个 `key=value`,`#` 开头是注释。用 `sh <skill_dir>/scripts/config.sh path` 查实际位置;环境变量 `CROSSCHECK_CONFIG` 可以改位置。示例见 `skills/cr/templates/config.example`。

| 设置 | 作用 |
|---|---|
| `gitlab_hosts` | 按 GitLab 处理的域名,多个用逗号分隔,可以带子路径(如 `company.com/gitlab`)。私有化 GitLab 的域名不含 "gitlab" 时必填 |
| `rules_repo`、`rules_ref`、`rules_dir` | 组织规则仓库的地址、跟踪的版本(建议用 tag)、本地克隆的位置(默认 `~/.crosscheck/org-rules`)。地址里不要带账号和 token |
| `data_repo`、`data_dir` | 团队数据仓库(可选),用来共享人的判断记录;本地克隆位置默认 `~/.crosscheck/data` |
| `issue_cmd` | 读取非 GitLab 需求单的命令,`{key}` 替换成编号,如 `jira issue view {key} --plain` |
| `model.finder` | 查找角色用的模型,可以用更便宜的。不写就用宿主当前的模型 |
| `model.verifier` | 核实用的模型。调用时说"核实换成某某模型"会覆盖它 |
| `model.helper` | `rule-miner`、`judge` 这类辅助角色用的模型 |
| `repo.<名字>` | 评测用例里的仓库在本机的位置 |

平台(GitHub 还是 GitLab)按这个顺序判断:`--platform` → 环境变量 `CR_PLATFORM` → 配置的 `gitlab_hosts` → `REVIEW.md` 头部的 `platform` → 域名含 `github.com` 或 `gitlab` → 链接里的 `/pull/`、`/merge_requests/`。判断不了时会告诉你该怎么设。

私有化 GitLab 需要先 `glab auth login --hostname <域名>`。

## 项目规则

### 规则从哪里来

规则分五层,越具体的越先:

| 层 | 来源 | 说明 |
|---|---|---|
| L3 目录级 | 子目录里的 `REVIEW.md` | 只对该目录下的改动生效,最具体 |
| L2 项目级 | 仓库根目录的 `REVIEW.md` | 项目自己维护 |
| 抑制 | `.cr/ignore.md` | 不想再被提醒的模式 |
| L1 组织规则包 | `REVIEW.md` 头部 `extends` 引用 | 来自组织规则仓库,多个项目共用 |
| 外部规则 | `CLAUDE.md`、`AGENTS.md`、Cursor / Copilot 规则等 | 只读,不需要为本插件重写 |

外部规则的来源:

| 来源 | 文件 |
|---|---|
| Claude Code | `CLAUDE.md`(各级目录)、`.claude/CLAUDE.md`、`.claude/rules/*.md`(按 `paths`) |
| Codex / 通用 | `AGENTS.md`、`AGENTS.override.md`(各级目录) |
| Cursor | `.cursor/rules/*.mdc`(`alwaysApply` 或 `globs` 命中改动文件)、`.cursorrules` |
| GitHub Copilot | `.github/copilot-instructions.md`、`.github/instructions/*.instructions.md`(按 `applyTo`) |
| 其他 | `GEMINI.md`、`.windsurfrules`、`CONVENTIONS.md` |

- 只有作用域覆盖本次改动文件的规则才生效;内容完全相同的文件只算一次。
- 外部规则里的操作指令(怎么跑测试、用哪个包管理器)不会被当成 review 规则,只采用能对照代码检查的条目。
- 一条规则都没有也照常工作,只是没有"规范"一节。
- **从哪一版读规则**:审查 PR/MR、其他分支或提交范围时,从 base 那一版读,所以 PR 改不了审查用的规则;审查自己当前的分支时读工作区,改了规则马上生效。

### 规则编号

项目规则 `PRJ-NNN`,抑制 `IGN-NNN`,组织规则用规则包的前缀(如 `ORG-RPC-001`)。编号只增不复用。元数据写在规则下一行的注释里:

```markdown
- 日期格式化统一用 `src/utils/date.ts`,不要直接调用 dayjs。原因:时区统一在那里处理。
  <!-- cr: id=PRJ-001 scope=src/** severity=minor src=manual added=2026-10 reviewed=2026-10 -->
```

`scope` 是路径 glob,`severity` 是 critical / major / minor(默认 minor),`src` 记来源(MR 编号或 `manual`),`added` 是加入的年月,`reviewed` 是上次复核的年月。没有编号的规则也能用,但复核清单里会提示补上。

### REVIEW.md 怎么写

`REVIEW.md` 放在项目仓库里(根目录,或只对某个子目录生效时放在该子目录),由项目自己维护。头部(`---` 之间)是审查设置,**由脚本执行**;正文是规则和写给审查的说明。模板见 `skills/cr/templates/REVIEW.md`。

```markdown
---
extends: [platform/rpc]              # 引用的组织规则包
disable:                             # 关掉某条组织规则,必须写原因
  - ORG-RPC-004: 本项目是网关,超时由上游统一设置
skip: ["src/gen/**"]                 # 不审查的路径
limits: { minor: 3 }                 # 条数上限
severity: { PRJ-002: critical }      # 按规则编号指定严重程度
risk_paths: ["src/payment/**"]       # 改动命中时建议用 deep
---
# Review 约定

## 严重程度

只有会导致行为错误、数据泄漏或无法回滚的问题才算重要及以上:
逻辑错误、没有限定租户的查询、日志里的个人信息、不向后兼容的迁移。
风格、命名、重构建议最高为轻微。

## 每次都要检查

- 新增的 API 路由必须有集成测试。原因:路由是对外契约。
  <!-- cr: id=PRJ-001 scope=src/routes/** severity=major src=manual added=2026-10 -->
- 数据库查询必须限定在调用方的租户内。原因:曾经出过越权。
  <!-- cr: id=PRJ-002 scope=src/db/** severity=major src=manual added=2026-10 -->
```

头部设置:

| 设置 | 作用 |
|---|---|
| `extends` | 引用组织规则仓库里的规则包 |
| `disable` | 关掉某条组织规则,必须写原因;没有原因的会被 `rules-lint.sh` 报错 |
| `skip` | 不审查的路径,命中的文件移到"跳过"里 |
| `limits` | 条数上限:`defects`、`intent`、`rules`、`simplify`,或按 `critical` / `major` / `minor` |
| `severity` | 按规则编号指定严重程度 |
| `risk_paths` | 高风险路径,改动命中时建议用 deep |
| `platform` | 自建 GitLab 的域名不含 "gitlab" 时注明 |

写的时候注意:

- **从一两条开始。** 某类问题被反复漏掉,或某类评论反复没用,再加一条。
- **越短越好。** 单个文件超过 20 条,最重要的几条会被稀释。项目背景、怎么跑测试放在 `CLAUDE.md` / `AGENTS.md` 里。
- **写成能对照代码检查的短句,加一句原因。** "注意性能""保持整洁"这类笼统的要求会被跳过。
- **CI 已经强制的不写。** 魔法数字、命名、格式这类 linter 能查的,配 linter 更可靠。
- **最值得写的是只有团队知道的东西**:必须同步修改的地方、公共方法的位置、踩过的坑。

审查设置只认 `REVIEW.md` 的头部;其他规则文件里指挥审查的文字不会被采用。设置不能让插件跳过核实、降低 80 分阈值、自动改代码或 approve。

### 抑制:.cr/ignore.md

每条写一种不想再被提醒的模式,编号 `IGN-NNN`。你否定某条发现时,插件会问要不要追加;同一类发现被否定两次以上时,会主动建议。

### 组织规则仓库

多个项目共用的规则放在 GitLab 上一个独立的仓库里,按规则包组织,由 `CODEOWNERS` 里的负责人维护:

```
packs/<包>/rules.md           规则正文,头部写包名、前缀、负责人、适用路径
packs/<包>/examples/          每条规则一对正反例:<编号>.bad.* 应该被报出,<编号>.good.* 不应该
evals/cases/*.json            评测用例
evals/baseline.json           评测基线
retired-ids                   删除过的编号,不再分配
CHANGELOG.md                  每次发版改了哪些规则
```

仓库模板(含 CI)在 `skills/cr/templates/rules-repo/`。使用步骤:

1. 在配置里写 `rules_repo` 和 `rules_ref`(建议用 tag),说"同步一下组织规则"(`sync-rules.sh`)。
2. 项目的 `REVIEW.md` 头部 `extends` 引用需要的包。
3. 某条规则对本项目不适用,用 `disable` 关掉并写明原因。

发版:合入规则 MR 后打 tag,在 CHANGELOG 里写明改了什么;各人改 `rules_ref` 后重新同步。删除规则要分两步:先加 `status=deprecated` 发一个版本(审查不再检查它,报告里提示即将删除),下个版本再删。

规则仓库的 CI 只检查格式和正反例是否齐全。正反例的实际效果(反例能不能报出、正例会不会误报)由评测检查。

### 确保规则被读到

规则写了但没被读到,等于没写。所以:

- 规则原文直接写进 `rules-auditor` 和 `verifier` 的任务里,不让它们自己去找。任务里带规则指纹和末尾的核对码。
- 装了 hook 时,启动这两类子代理前会检查任务里有没有规则指纹,没有就拒绝启动。
- `rules-auditor` 要交一份检查清单,说明每条适用的规则在每个文件上检查的结果。`check-rules.sh` 核对有没有漏、核对码对不对;漏了补跑一次,仍然漏的在报告里列为"未检查"。
- `verifier` 会随机抽几条清单里判为"没违反"的检查重新核对一遍。抽查发现确实违反的,直接作为发现报出。
- 报告末尾写明验证状态:任务含规则、核对码、抽查结果。

这只能保证规则被读到,不能保证每条都被正确用上;后者靠核对和抽查降低风险。

### 规则的维护

**每月提炼一次。** 说"从最近一个月的 MR 评论里总结一下规则"。`mine-reviews.sh` 用 `glab` 只读收集 MR 上挂在代码行上的人工评论、你对发现的判断、crosscheck 漏报的问题;`rule-miner` 把反复出现的问题提炼成候选规则:至少 3 条评论、2 个 MR、2 位评论人,能对照代码检查,不是 linter 能查的,不和现有规则重复。你挑选后,`propose-rules.sh` 先预览改动,确认后:

- `--worktree`:直接改到工作区,由你检查后自己提交。审查后顺手定的单条规则用这个。
- `--mr`:在临时 worktree 里基于默认分支改,推送新分支并创建带 `crosscheck-rule` 标签的 MR。只创建,不合并,不碰你的工作区。

写入前都会跑 `rules-lint.sh`,有错误就撤回。也可以单独运行 `sh <skill_dir>/scripts/rules-lint.sh` 检查格式。

**定期复核。** 规则是人批准才生效的,去留也由负责人定期主动复核决定,不靠命中次数这类统计:一条规则长期没被报过,可能是没用了,也可能是大家都遵守了。建议每季度一次;团队小、规则在十几条以内的,半年一次也够。审查报告里提示"规则可能过时"时(这是审查当下的观察),可以提前复核那一条。

说"检查一下我们的规则"或"复核规则",`rules-health.sh [--repo DIR] [--months 6]` 会生成一份规则复核清单:

- 列出每条规则、所在的层、负责人(组织规则包的 `owner`)、上次复核的时间(元数据里的 `reviewed=`,没有就看 `added=`)。超过 6 个月没复核的排在最前。
- 附几项只读仓库就能做的检查提示:作用域匹配不到任何文件;规则里用反引号提到的文件、函数、包在代码库里找不到;和别的规则几乎一样;缺编号或日期;单个文件超过 20 条。
- 这些只是线索,不下结论。比如规则禁止的东西在代码库里找不到,说明大家都遵守了,不用动。

负责人逐条过:

- 还对的:确认保留,记下 `reviewed=<本月>`(`{"op": "confirm", "id": "PRJ-003"}`)。
- 要改的:用 `replace`,不要用 `remove` 再 `add`。
- 不要的:`remove`。命名、格式这类规则,建议改配 lint 规则后再删。

改动同样用 `propose-rules.sh` 预览,确认后 `--mr --yes` 创建 MR。复核不读审查记录,也不需要共享任何数据。

## 报告长什么样

- **第一行**:审查范围、深度、全量还是增量。接着一行写意图取自哪些来源。
- **概览表**:每条缺陷和需求核对一行,列出严重程度、维度、位置和摘要。
- **逐条发现**,每条包含:
  - 位置:`文件:行号`。
  - 问题代码:从被审查的那一版代码里摘出的原文,带行号,出问题的那一行有标记。
  - 问题:具体的输入或状态会导致什么错误结果。
  - 修复建议:能确定时给出 diff 形式的替换代码,否则用文字说明。会改变接口或行为的修复附兼容性说明。
  - **依据**(默认折叠):核实时读过的代码位置、排除了哪些可能、复现结果(deep)、哪些角色查到了。
- **需求核对**:没有做到的验收标准。
- **规范**:违反团队书面规则的问题,逐字引用规则原文和出处。同一条规则在一个文件里违反多处只报一条。
- **可简化**:只列位置和建议,最多 5 条。
- **测试和检查被削弱**:脚本扫出来的,单独列出。
- **已按历史判断忽略**(折叠):因为你以前的判断而没报的发现,可以展开核对。
- **末尾说明**:风险等级和建议深度、规则使用情况、规则读取的验证状态、规则相关提示(可能过时、冲突、未同步)、跳过了多少文件、查了哪些维度、消耗、怎么快速表态、报告文件的链接。

报告是 Markdown,直接显示在对话里,同时存一份到用户目录。审查结束时会用系统默认程序自动打开这份报告,对话里的报告末尾也有一行可点击的 `file://` 链接指向它。

- 不想自动打开:设置 `CROSSCHECK_OPEN=0`。
- 想用指定的程序打开:设置 `CROSSCHECK_OPEN_CMD`,例如 `code` 或 `cursor`;或者直接改系统里 `.md` 文件的默认打开方式(macOS:访达里选中一个 `.md` 文件 → Cmd+I → 打开方式 → 全部更改)。第一次自动打开时,报告末尾会提示一次怎么改。
- 通过 SSH 连接、在 CI 里、或 Linux 上没有图形界面时不会自动打开,只给链接。

### 核实与打分

- verifier 必须给出依据:读过的代码位置、排除了哪些可能,deep 下还有复现结果。
- 脚本会核对依据里的位置在被审查的那一版里真实存在;位置不存在、或根本没给依据的,分数最高 50。
- 规则发现的规则编号和引用原文也会核对,对不上的作废。
- 低于 80 分的不展示,存进这次记录的 `rejected.json`。问"还有别的吗"时可以从里面列出 70 分以上的。

## 记录与增量审查

记录的目录结构:

```
~/.crosscheck/reviews/<项目名>/
├── feedback.jsonl           你对发现的判断(项目级)
├── adoption.jsonl           MR 合并后问题是否真的解决了
└── <目标>/
    ├── 20261009-143000/
    │   ├── report.md        报告全文
    │   ├── findings.json    本次结束时仍然成立的发现
    │   ├── rejected.json    没通过核实的候选(带分数和理由)
    │   ├── hashes.txt       每个文件 diff 的哈希
    │   └── meta.txt         目标、commit、深度、时间、消耗等
    ├── latest               最近一次审查的目录名
    └── baseline             增量审查所依据的那一次
```

`<项目名>` 取自 `origin` 远程地址的最后一段(如 `gitlab.example.com/group/shop-api` 就是 `shop-api`),没有远程时取主工作区的目录名。同一个项目的各个 worktree、不同位置的克隆都落在同一个目录下,分支和 MR 的记录也放在一起。恰好有另一个同名的项目时,后来的那个会在目录名后面加一段哈希来区分。

`<目标>` 是 `branch-<分支名>`、`pr-<编号>`、`mr-<编号>` 或 `range-<范围>`。不管你在不在那个分支上、在哪个 worktree 里,同一个分支用的是同一份记录。用环境变量 `CROSSCHECK_HOME` 可以改存放位置。记录不在仓库里,不会被提交;报告里会引用代码片段,注意这个目录的访问权限。

**同一个目标再次审查时默认做增量**:

- 按文件比较 diff 的哈希。没变的文件不再看,上次在这些文件里的发现原样带过来。
- 变了的和新增的文件重新审。上次在这些文件里的发现会重新核实,分成"遗留"和"已解决"。
- 报告开头会写明这是增量审查、跳过了多少文件,发现分成"新发现""上次遗留""已解决"三段。
- 未提交的改动同样算在内,哈希是按实际内容算的。

**什么时候不做增量**:

- 你说"重新审""全量""忽略之前的",或带 `--full`。
- 这次的深度比上次高(上次 standard,这次 `--deep`)。反过来可以:deep 之后的 standard 会做增量。
- 上次用了 `--only`:只查部分维度的审查会存记录,但不会成为增量的基准。
- 换了目标:另一个分支、另一个 PR,或同一分支上指定了不同的范围。

## 只审有效代码

审查只针对真正会在产品路径上执行、并且改变了行为的代码。

**整个文件不审的**(由脚本过滤,报告末尾会列出各类跳过了多少):

| 类别 | 例子 |
|---|---|
| 测试 | `tests/`、`__tests__/`、`e2e/`、`testdata/` 目录;`*_test.go`、`test_*.py`、`*.test.ts`、`*.spec.tsx`、`*Test.java`、`*_spec.rb` 等 |
| 日志 | `*.log`、`logs/` 目录、`nohup.out` |
| 产物 | 覆盖率报告、`*.bak` / `*.tmp` / `*.pyc`、`.idea/`、`.vscode/` |
| 原本就过滤的 | lock 文件、生成代码、vendored 代码、二进制文件 |
| `REVIEW.md` 的 `skip` | 项目自己指定的路径 |

想连测试一起审,加 `--with-tests` 或直接说"测试也看一下"。测试不审,但审查时仍会读它来了解代码的预期行为;测试被削弱的情况另外扫描并单列。

**文件里不当作问题的**:

- 只改了注释、文档字符串、空行或排版的地方(缩进有语义的语言除外)。
- 原样移动或重命名的代码。
- 被注释掉的代码、遗留的调试代码。
- 没有被用上的代码里的"bug":没有调用方、没被注册或导出、所在条件恒为假。这类代码会作为"新增了但没用上"出现在可简化一节。

规范违规单独列出,带有针对同一规则的抑制注释(`eslint-disable-next-line`、`nolint`、`noqa` 等)的地方不报;现有代码大量反着写的规则会被提示"可能过时"。

## 审查维度

| 维度 | 查什么 |
|---|---|
| `bug` | 逻辑错误、边界、空值、并发、错误处理、资源泄漏、API 误用 |
| `security` | 注入、鉴权/越权、密钥泄漏、不安全反序列化、SSRF、路径穿越等,要求给出攻击路径 |
| `intent` | 需求核对:没有满足意图里明确的验收标准 |
| `rules` | 违反项目自己写下的规范,必须引用规则原文 |
| `simplify` | 可复用已有代码、重复、过度设计。单独列出,最多 5 条 |

## 你的判断会被记住

审查后你对某条发现表态,比如"这条不对""知道了但不改""确实是个问题",agent 会把判断连同原因记下来:

- **对整个项目有效。** 在分支上判过的,换成 MR 或 commit 范围审查同一段代码时同样生效。
- **代码没变就不再报,代码变了会重新评估。** 判断记着那段代码的样子(出问题的那一行加上下各两行);代码改了之后如果问题仍然成立,会重新报告,并注明之前的判断和这次为什么又报。
- **不会悄悄删掉。** 因为历史判断而没报的发现,报告里有一个折叠的"已按历史判断忽略"列表,可以展开核对。
- **否定时要说原因。** agent 会问你为什么;同一类发现被否定两次以上时,会建议你把它写成 `REVIEW.md` 或 `.cr/ignore.md` 里的规则。
- agent 自己撤回的发现也会记录;用 `--fix` 修好的会自动记为成立。

## 审查效果统计

说"看看 review 的效果",会先更新采纳情况,再分几个维度给出结果,互不折算:

| 维度 | 内容 | 用来回答 |
|---|---|---|
| 判断 | 成立、成立但不修、不成立、有争议、未表态 | 报出来的东西对不对 |
| 采纳 | MR 合并后,报过的问题在最终代码里是否真的解决了 | 有没有被采纳 |
| 去向 | 仍在、代码已改、代码没变但不再报、文件已不在改动里 | 代码层面发生了什么 |
| 校准 | 不同置信度区间里有人判断过的发现,实际成立的比例 | 打分有没有区分度 |
| 差一点通过 | 没通过核实的候选的分数分布,尤其是 70–79 分 | 80 分的门槛是不是太严 |
| 规则检查 | rules-auditor 漏检和抽查的情况 | 规则检查本身可不可靠(衡量工具,不是衡量规则) |

- 采纳由 `adoption.sh` 判断:只读拉取已合并 MR 的最终代码,那段代码原样还在算"没采纳";文件已删除的不计入;代码改了的交给 `judge` 确认问题是否真的解决。需要 `glab` 或 `gh`,没有时看 MR 的最后一个提交是否已进入目标分支。
- "代码已改"不等于被采纳,改动可能和这条发现无关;"代码没变但不再报"多半说明这条发现不稳定。
- 成立率和采纳率只按有明确结论的发现计算,并标出样本数;**样本不足 10 条时只给数量,不给比例**。人更倾向于标记错的,所以未表态越多,成立率越不可靠。
- 另外给出各深度的平均用时和 token。
- 统计只给人看,不会自动改变审查行为。要调整就写进 `REVIEW.md`。

## 审查的成本

每次审查结束,报告末尾会有一行"消耗",同时记进这次审查的记录里:

- **用时、启动的查找角色和 verifier 数、候选条数和通过条数。** 三个宿主都有。
- **token 用量。** 由宿主的 hook 从会话记录里读取,所以只有以插件方式安装(带 hook)时才有。拷贝安装时报告里会写"token 未统计";插件不会为了统计去猜或扫描其他会话的记录:

  | 宿主 | 来源 | 范围 |
  |---|---|---|
  | Claude Code | 会话记录里每次模型调用的用量,加上子代理的记录 | 审查开始到保存之间,包含子代理 |
  | Codex | 会话文件里的用量记录 | 审查开始到保存之间;是否包含子代理未知 |
  | Cursor | 一轮结束时 hook 给出的合计 | 整轮对话,不只是审查;命令行版不提供 |

数据都存在本机,不上传:

- 最终结果在 `~/.crosscheck/reviews/<项目名>/<目标>/<时间>/meta.txt` 里,是 `duration_s`、`run_*`、`usage_*` 这些行,和报告、发现放在一起。
- 审查进行中有一个临时的状态文件在系统临时目录的 `cr-guard/` 下,只记会话记录的路径和起始位置,保存时删除。
- 只读取会话记录里的用量数字,不读取、不保存对话内容。

这些字段没有写进各宿主的正式文档,版本变化后可能读不到;读不到时这一项留空,不影响审查。

## 和团队共享(可选)

默认所有记录只在本机。团队想共享判断记录,在配置里写 `data_repo`(GitLab 上的一个独立仓库),然后:

```
sh <skill_dir>/scripts/sync-data.sh status       有多少条本机判断还没推送
sh <skill_dir>/scripts/sync-data.sh pull         拉取团队的记录
sh <skill_dir>/scripts/sync-data.sh push         先拉取,列出要推送的条数
sh <skill_dir>/scripts/sync-data.sh push --yes   确认后推送
```

- 只同步人的判断记录(含代码片段和原因)。人名只存哈希,不存凭证。
- 只在你说"同步一下 review 数据"并确认后才推送,审查过程中从不调用。
- 同步下来的团队判断和本机的一起使用,同一条发现以时间晚的为准。
- 仓库按项目、月份、人分文件,只追加不修改,多人同时同步不会冲突。数据仓库的访问权限要和代码仓库一致。
- 不共享也能正常使用:团队可以靠把常见误报写成 `.cr/ignore.md` 来共享。

## 评测(插件维护者)

改了角色说明、评分标准、换了模型或调了门槛之后,用一批答案已知的用例衡量结果变好还是变坏。普通使用者不需要做。

- 用例是 JSON,放在组织规则仓库的 `evals/cases/`,基线是 `evals/baseline.json`;规则包里每条规则的正反例也会当作用例。
- 说"跑一下评测":`eval.sh prepare` 生成运行计划,逐个用例审查,`eval.sh match` 对答案,`judge` 角色判断两条发现是不是同一个问题,`eval.sh score` 计算召回、误报、精确率、用时并和基线比较。
- 说"找几个评测用例":`eval.sh find-cases` 找候选(修复提交、干净提交),由熟悉代码的人确认后 `add-case`,攒够一批用 `submit-cases` 创建 MR。
- 期望的问题少于 50 个时,评测只能发现明显的倒退。

流程见 `skills/cr/references/eval.md`。

## 依赖

- `git`、POSIX `sh`
- **`python3`(3.8+)**:核心审查流程需要(规则装配、依据校验、汇总、判断记录、统计、设置解析都用它)。没有 python3 时 `REVIEW.md` 头部的设置不生效,判断记录和统计不可用
- GitHub PR:`gh`(已登录)。没有或未登录时改用 git 直接拉取,见下
- GitLab MR:`glab`(已登录),以及 `jq` 或 `python3`。没有或未登录时改用 git 直接拉取,见下
- 读取 GitLab Issue、提炼规则(`mine-reviews.sh`)、MR 评论、采纳判断:`glab`
- 创建规则 MR:`glab`(GitHub 仓库用 `gh`);没有时只推送分支,由你在页面上创建
- 只读拦截:`jq` 或 `python3`

## 前置条件和常见情况

- **必须有本地仓库。** 审查要读代码,只给一个 MR 链接而没有本地克隆是不行的。不在仓库目录里时,告诉它仓库在哪,它会用 `--repo <目录>` 运行。
- **没有 `gh` / `glab`,或没有登录。** 仍然可以审查 PR/MR:脚本会用 git 直接把它的代码拉下来,用的是仓库自己已经配置好的凭证。代价是拿不到标题、描述和关联需求,对比基准按默认分支计算;目标分支不是默认分支时,说明一下目标分支(对应 `--base <分支>`)。
- **连不上代码托管的地址。** 内网的 GitLab 在沙箱里经常解析不了。这是运行环境的限制,脚本会直接说明拉取失败的可能原因;放开网络或换个环境后再试,或者改审已经在本地的分支。
- **无法判断是 GitHub 还是 GitLab。** 在配置里加 `gitlab_hosts=<域名>`,或带 `--platform gitlab`。
- **明明登录了,却提示没登录。** 常见原因是登录用的环境变量(如 `GITLAB_TOKEN`、`GLAB_CONFIG_DIR`)写在 `~/.zshrc` 里,而 agent 的终端是非交互的,不读这个文件。脚本会识别这种情况并告诉你是哪个文件里的哪几个变量:
  - 它只检查变量名有没有出现、当前环境里有没有值,不读取也不输出任何值。
  - 识别到之后,会借你自己的登录 shell 再调用一次 `glab`;那个 shell 的输出全部丢弃,只有 `glab` 返回的 MR 信息被写进临时文件。超过 20 秒就放弃。不想要这个行为设置 `CR_USER_SHELL=0`。
  - 一劳永逸的办法:把这几个变量的设置挪到 `~/.zshenv`(zsh 的所有终端都会读),或配置到宿主的环境变量里。
- **凭证。** 远程地址里嵌着 token 的仓库很常见。脚本显示和保存的远程地址都去掉了账号和凭证;agent 被要求不打印远程地址、不读取任何凭证。审查期间,会显示凭证的操作会被直接拦截:打印环境变量、查看或 `source` shell 配置文件、读取 `.netrc` 和 gh/glab 的配置、`git remote -v`、`gh auth token` 等。
- **报告在哪。** 以报告末尾 `记录:` 一行的链接为准,位置固定在 `~/.crosscheck/reviews/` 下。

## 结构

```
skills/cr/
├── SKILL.md        编排流程
├── roles/          bug-hunter / security-reviewer / rules-auditor / simplifier / verifier,
│                   以及 judge(评测和采纳判断)/ rule-miner(提炼规则)
├── references/     发现结构、评分标准、误报清单、报告格式、报告之后的处理、维护、评测、常用说法
├── templates/      REVIEW.md 模板、配置示例、组织规则仓库模板(含 CI)
└── scripts/        审查流程、规则、记录、统计、维护、评测的脚本,以及共用的 crlib.py
hooks/
├── hooks.json          Claude Code 和 Codex 的 hook 注册
└── cursor-hooks.json   Cursor 的 hook 注册
tests/                  python3 -m unittest discover -s tests
```

`skills/cr/` 自包含,审查流程不依赖任何宿主专属功能。宿主支持子代理时各角色并行运行;不支持时由主 agent 依次执行,流程不变。三个 `.*-plugin/plugin.json` 只是各宿主的安装清单。`hooks/` 是唯一用到宿主专属机制的部分,它只提供额外的拦截和检查,没有它审查照常运行。

为什么这样设计,见 [DESIGN.md](DESIGN.md)。

想调整行为,直接改对应文件:阈值和评分在 `references/scoring-rubric.md`,不该报的东西在 `references/false-positives.md`,各角色的关注点在 `roles/`。

改动较大时会自动按约 1000 行一批拆开审查,每批独立进行;用环境变量 `CR_BATCH_LINES` 调整每批的行数。

测试用 `python3 -m unittest discover -s tests`,其中 `tests/bin/glab` 模拟 GitLab。

## 已知限制

- **规则检查只能保证读到,不能保证用上。** 规则原文在任务里、有核对码和检查清单、有抽查,但 rules-auditor 是否对每条规则都做了正确判断,只能靠核对和抽查降低风险。
- 子代理的规则指纹检查依赖 hook 拦截 `Task` / `Agent` 工具,没带 hook(拷贝安装)时不检查。
- 增量按文件判断:文件 A 没变而它依赖的文件 B 变了时,A 不会被重看。问题如果出在 B 的改动上仍然能发现;担心时用 `--full`。
- 基准分支更新后重新变基,所有文件的 diff 哈希都可能变化,那次会退化成全量。
- PR/MR 的 head commit 无法 fetch 到本地时,只能基于 diff 本身审查,深度会下降,报告中会注明。
- 读不到 PR/MR 信息(没有 `glab` / `gh` 或没登录)时,拿不到关联需求和人工讨论,意图只有提交说明。
- 私有化 GitLab 部署在子路径下时,`glab` 的 `GITLAB_HOST` 设置没有在真实环境里验证过。
- `mine-reviews.sh`、`adoption.sh`、创建规则 MR 等依赖 `glab` 的部分,目前只用模拟的 `glab` 测过,还没有在真实的 GitLab 上跑过。
- 团队数据只在有人手动同步之后才有;没同步时,判断记录只代表你自己。
- 采纳判断里,"代码改了"的情况由 `judge` 判断问题是否真的解决,仍可能判错。
- 评测的用例要靠人确认,数量少时只能发现明显的倒退。
