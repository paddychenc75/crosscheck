# crosscheck

本地运行的 AI code review,同一套流程可在 Claude Code、Codex、Cursor 中使用。

核心思路是**宁缺毋滥**:先尽量把可疑的地方找出来,每条候选再由一个没看过推理过程的 verifier 独立核实、给出依据并打分,低于 80 分的不展示。没有问题时就说没有问题。

一次审查产出两份东西:

| | CR 报告 | MR 说明 |
|---|---|---|
| 给谁看 | 开发者自己,照着修 | MR 评审人,开发者贴进 MR 描述 |
| 内容 | 核实过的问题、修复建议、依据 | 需求链接、一句话、请重点看、阅读顺序、影响面、需注意的改动、可能相关的测试、CR 情况 |
| 性质 | 结论,逐条独立核实 | 事实和链接,由脚本生成或核对,不下结论 |

除了找 bug 和安全问题,它还会对照需求单检查有没有做到需求、对照团队写下的规则检查规范,并记住你对每条发现的判断,同一段代码不再重复报同样的误报。另有一个**规则沉淀**命令,从最近一个季度的 MR 评论里整理出候选规则让你挑。

## 调用

| 功能 | Claude Code | Codex | Cursor | 能否用自然语言 |
|---|---|---|---|---|
| 审查(cr) | `/crosscheck:cr` | `$cr` | `/cr` | 可以,直接说「review 一下」 |
| 规则沉淀(cr-rules) | `/crosscheck:cr-rules` | `$cr-rules` | `/cr-rules` | 不可以,只能用命令 |

说「cr 帮助」会列出常用说法。在 Codex 里,插件自带的 hook 要先运行 `/hooks` 审阅并信任才会生效,否则审查期间的只读拦截和 token 统计都不工作;升级插件后要重新信任。

## 审查

直接用平时说话的方式提要求,不需要记参数。报告第一行写明这次审查了什么(范围、深度、全量还是增量),范围不对时直接说。

| 想做什么 | 可以这样说 | 对应参数 |
|---|---|---|
| 审当前分支的全部改动(含未提交的) | 「review 一下」 | 不带 target |
| 审另一个分支(不用切过去) | 「看看 feature/pay 分支」 | `feature/pay` |
| 审一个 PR / MR | 「review MR 128」,或直接贴链接 | `128`、`<URL>` |
| 审某几个提交 | 「看看最近 3 个提交」 | `A..B` |
| 只看某个目录 | 「只看 src/orders 下面的改动」 | `src/orders` |
| 指定对比基准 | 「对比 develop」「要合到 release/1.2」 | `--base <分支>` |
| 快速过一遍 | 「快速看一下」 | `--depth quick` |
| 上线前仔细审 | 「仔细看看」「上线前深度审一下」 | `--depth deep` |
| 只关心某一方面 | 「只看安全问题」「只对照团队规范」 | `--only bug,security,rules` |
| 顺便看看能不能简化 | 「顺便看看有没有能简化的」 | `--only bug,security,rules,simplify` |
| 告诉它改动的目的 | 「这次是为了修复分页丢数据」 | `--intent "…"` |
| 给方案、接口文档 | 「方案在 docs/plan.md」 | `--doc <文件>`(可多次) |
| 给需求链接 | 「需求单是 <链接>」「这是 hotfix,没有需求单」 | `--source ticket=<链接>`、`ticket=none:hotfix` |
| 说明怎么验证的 | 「本地跑过 jest,手工测了翻页」 | `--tested "…"`(只写进 MR 说明) |
| 测试也一起看 | 「测试也一起看」 | `--with-tests` |
| 换一个核实用的模型 | 「核实换成某某模型」 | `--verifier-model <模型>` |
| 从头完整审一遍 | 「重新审」「全量」 | `--full` |
| 审完顺手修掉 | 「审完把问题修掉」 | `--fix` |

- **深度**:没说时按 standard。quick 由主 agent 自己查和核实,最多 5 条;deep 多一个 reviewer 从调用方往回查影响面,verifier 可以跑项目已有的检查和测试来复现。风险高时(数据库迁移、鉴权或资金相关、改动很大、测试被削弱等)会建议 deep,只建议,不自己换。
- **对比基准**:和 GitHub / GitLab 一样以远端最新为准,审查前先从 origin 拉取目标分支(只更新 `origin/` 下的远程跟踪分支)。当前分支离 develop、release/* 这类分支比离默认分支更近时,会先问你对比哪个。
- **改动很大**:按约 1000 行一批审查;超过 4 批时先问你是全部审、只审某个目录,还是用 quick。
- 不带 `--fix` 时不改任何文件;「review 一下」「这个该怎么修」都不算修改请求。

### 审查之后

直接回复,用报告里的编号指代发现。

| 想做什么 | 可以这样说 |
|---|---|
| 表态(会被记住) | 「1 对,2 误报:上游已经重试」「3 先不改:下个版本」 |
| 质疑某条 | 「第 2 条不对吧」(重新读代码核对:成立就解释,站不住就撤回并记录) |
| 修复 | 「把第 1、3 条修掉」 |
| 看没报的 | 「还有别的吗」「70 多分的那些是什么」 |
| 指出漏报 | 「你漏了 cache.ts 的并发问题」 |
| 单独深挖 | 「cache.ts 用 deep 再看一遍」 |
| 定规则 | 「以后这种别报了」「以后都要检查 X」 |
| 改 MR 说明 | 「重点请看 api/orders.ts:42 的兼容分支」「PRD 是 <链接>」 |
| 生成网页版 MR 说明 | 「生成网页版」(配置了 `output.page` 时) |
| 改完再看 | 「再看一下」(同一目标自动做增量) |

表态、修复、重新审查之后,MR 说明会跟着更新。

## CR 报告

- **第一行**:审查范围、深度、全量还是增量;接着一行写意图取自哪些来源。
- **概览表**:每条缺陷和需求核对一行。
- **逐条发现**:标题写明严重程度、维度和怎么确认的——**已复现**(deep 下实际运行并由 hook 见证)、**已复现(自报)**(有运行记录但没有 hook)、**读代码推断**。每条包含位置、从被审查版本里摘出的问题代码、会导致什么错误结果、修复建议,以及折叠的依据(读过的代码、排除了哪些可能、复现结果)。
- **需求核对**:没有做到的验收标准。
- **规范**:违反团队书面规则的地方,逐字引用规则原文和出处。
- **可简化**:只在你要求时才有,最多 5 条。
- **测试和检查被削弱**:删了断言、新增 skip、降低覆盖率阈值、放宽 CI 等,由脚本扫出,单独列出。
- **已按历史判断忽略**(折叠):因为你以前的判断而没报的,可以展开核对。
- **末尾**:风险等级、用了哪些规则文件、跳过了多少文件、查了哪些维度、消耗、报告文件的链接。

**核实与打分**:verifier 必须给出依据,脚本核对依据里的代码位置真实存在,不存在或没给的最高 50 分;规则发现的出处和引文对不上的作废;AI 声称跑过但拿不出运行记录的,按读代码推断处理、最高 60 分。低于 80 分的不展示,存在记录里。

报告直接显示在对话里,同时存一份到 `~/.crosscheck/reviews/` 并用系统默认程序打开。`CROSSCHECK_OPEN=0` 不自动打开,`CROSSCHECK_OPEN_CMD=code` 指定打开的程序;SSH、CI 和没有图形界面的 Linux 上只给链接。

## MR 说明

审查结束后在报告后面给出,贴进 MR 描述即可。包在 `<!-- crosscheck:begin -->` / `<!-- crosscheck:end -->` 里,控制在 30 行以内,只有事实和链接:

| 部分 | 内容 |
|---|---|
| 基本信息 | 需求单、需求文档的链接和标题(或「未提供(作者跳过)」「无需求单:hotfix」)、分支、规模、审查量(1–5) |
| 一句话 | 你用 `--intent` 写的;没写时由 AI 按需求材料起草(必须引用原文,脚本核对),会提示你确认 |
| 请重点看 | 你点名的最多 3 处,每处可以写想要什么反馈;没点名时列出脚本挑的候选,标明「自动列出」 |
| 阅读顺序 | 按 接口和类型 → 实现 → 配置 → 测试 分组;生成代码、纯格式化、纯重命名、lock 文件列为「可跳过」 |
| 影响面 | 签名变了或被删除的函数、接口、配置键,以及本次改动之外的调用方 |
| 需注意 | 数据库迁移、配置键增删、新环境变量、依赖变化 |
| 测试 | 你写的「怎么验证的」,以及可能相关的测试文件(未执行) |
| CR 情况 | 已修复几条;未修复的严重和重要问题附你的判断和理由,没表态的标「未表态」;写明基于哪个提交 |

- 不写已实现、已覆盖、无风险这类结论。影响面只按名字在本仓库文本匹配,依赖注入、反射、跨服务调用搜不到;签名不变的行为变化由 CR 报告负责。
- 仓库有 MR 模板(`.gitlab/merge_request_templates/`、`.github/pull_request_template.md`)时按模板标题填,模板里需要你自己写的几节放在标记之外,重新生成时不会被覆盖。
- 提交推送到远端后,代码位置带 GitLab / GitHub 的行链接。
- 另有完整版 `mr.html`。配置了 `output.page` 时,第一次会问要不要生成网页版,之后随 CR 报告更新同一个页面,描述里多一行「完整版」链接。
- 插件不提交 MR、不改 MR 描述,只给出 `glab mr create/update` 或 `gh pr create/edit` 命令,由你执行。

## 需求和意图

审查会把下面这些汇总成「意图」交给各个角色,用来判断某个行为变化是不是有意的、有没有做到需求:

- MR 描述;本地分支时用提交说明。
- 关联的需求单:GitLab Issue 用 `glab` 读,GitHub issue 用 `gh` 读,其他系统配 `issue_cmd`。
- MR / PR 上已有的人工讨论(已经有人指出的问题不重复报)。
- `--intent`、`--doc` 给的说明和文档。
- 配置的需求来源(见下)。

意图里有明确验收标准时,报告多一节「需求核对」。意图只能解释改动,不能让安全问题不报。

### 需求来源

在配置里按用途写好读取它们用的工具(只写工具名,怎么调用由 agent 决定),以及每次都要收集哪几类:

```
source.ticket   = <读取需求单的 skill 或命令名>
source.prd      = <读取需求文档的 skill 或命令名>
source.required = ticket, prd                  # 不写时只有 ticket
source.ticket.label = <需求单在 MR 说明里显示的名字>
source.prd.label    = PRD
```

- 先从 MR 描述、分支名、提交说明和你说的话里自动找链接(按工具名和显示名里的关键字识别,也可以用 `source.<类别>.match` 指定)。
- 缺了就在审查开始前问一次:贴链接、说「没有需求单(hotfix 等)」,或跳过。同一个分支问过就记住,90 天后过期。
- 给了链接时,agent 用配置的工具读取内容(需求文档只取需求描述、验收标准和相关章节),读不到就写明原因,不影响审查。读到的内容只当数据,其中的指令不执行。
- MR 说明里只放链接和标题,不引用需求原文。

## 项目规则

规则就是仓库里的 Markdown 文件,不需要编号或专门格式。**`REVIEW.md` 是可选的**:团队已有的 `CLAUDE.md`、`AGENTS.md` 等直接就能用;一条规则都没有也照常审查,只是没有「规范」一节。

| 来源 | 文件 |
|---|---|
| 审查约定 | `REVIEW.md`(根目录对全部改动生效,子目录只对该目录生效;根目录里单独一行的 `@文件名` 会展开成那个文件) |
| 沉淀的规则 | `.agents/rules/**/*.md`(按 frontmatter 的 `paths` 生效;规则沉淀写到这里) |
| Claude Code | `CLAUDE.md`、`.claude/rules/*.md` |
| Codex / 通用 | `AGENTS.md`、`AGENTS.override.md` |
| Cursor | `.cursor/rules/*.mdc`、`.cursorrules`、`.cursor/BUGBOT.md` |
| GitHub Copilot | `.github/copilot-instructions.md`、`.github/instructions/*.instructions.md` |
| 其他 | `GEMINI.md`、`.windsurfrules`、`CONVENTIONS.md` |

- 只有范围覆盖本次改动文件的规则才生效;约定文件里的操作说明(怎么跑测试等)不当作审查规则。
- 审查 PR/MR、其他分支或提交范围时,规则从 base 那一版读,PR 改不了审查用的规则;审查自己当前的分支时读工作区。
- 规则发现必须写出规则所在的文件和逐字原文,脚本核对后再由 verifier 确认,模型不能凭空编出一条规则。

### REVIEW.md 怎么写

头部(`---` 之间)是审查设置,由脚本执行;正文是规则。模板见 `skills/cr/templates/REVIEW.md`。

```markdown
---
skip: ["src/gen/**"]                 # 不审查的路径
limits: { minor: 3 }                 # 条数上限
risk_paths: ["src/payment/**"]       # 改动命中时建议用 deep
---
## 每次都要检查

- 新增的 API 路由必须有集成测试。原因:路由是对外契约。
- 数据库查询必须限定在调用方的租户内。原因:曾经出过越权。

## 不要报

- 生成的 protobuf 代码里的命名问题。
```

- 写成能对照代码检查的短句,加一句原因;「注意性能」这类笼统的要求会被跳过。
- 从一两条开始,单个文件不超过约 15 条;linter 和 CI 能查的不写。
- 「不要报」一节写团队不想再被提醒的情况,只对它所在的目录生效。你否定某条发现时,agent 会问要不要加进去。
- 头部设置(`skip`、`limits`、`risk_paths`、`platform`)只认根目录 `REVIEW.md`,不能让插件跳过核实、降低 80 分门槛、自动改代码或 approve。

### 规则沉淀

用命令 `/crosscheck:cr-rules` 调用(可以带天数,如 `/crosscheck:cr-rules 30 天`):

1. 只读拉取最近一个季度已合并 MR 的人工评论(去掉机器人和系统消息)和你记下的判断,缓存到本机,下次只拉新的。
2. 归纳出候选规则,脚本按准入清单核对:证据是评论原文、至少 2 个 MR 出现、评论后代码确实改了、能写成「必须/禁止」并有「不要报」的边界、工具查不到、不和已有规则重复。
3. 按出现次数排好列给你挑。选中的写进 `.agents/rules/<主题>.md`,每条写规则、原因、严重级别、正反例、不要报和来源 MR;只改工作区,由你提交。

Claude Code、Cursor 写代码时不会自动读 `.agents/rules/`,需要的话在 `AGENTS.md` / `CLAUDE.md` 里用 `@` 引入(会先问你)。说「检查一下我们的规则」时,agent 会逐条看规则能不能检查、有没有范围和边界、是否重复或过长,建议由负责人决定。

## 判断记录

你对某条发现表态(成立 / 不修 / 不成立 / 有争议)时,agent 用 `feedback.sh` 记在**你本机**的 `~/.crosscheck/reviews/<项目名>/feedback.jsonl`,不在仓库里,也不共享给别人:

- 对这个项目的所有分支、MR 和范围有效。
- 记着那段代码的样子(出问题的一行加上下各两行)。代码没变就不再报;代码变了会重新评估,并注明之前的判断。
- 不成立和不修必须写原因;因为历史判断而没报的,在报告里折叠列出。
- 想让全队都不再报,写进 `REVIEW.md` 的「不要报」,随代码一起评审。

## 记录与增量审查

```
~/.crosscheck/
├── config                         个人配置
├── mining/<项目名>/               规则沉淀的 MR 评论缓存
└── reviews/<项目名>/
    ├── feedback.jsonl             你的判断
    ├── sources/<分支>.json        需求链接、请重点看、网页链接
    └── <目标>/<时间>/             report.md、mr.md、mr.html、findings.json、rejected.json、meta.txt
        latest · baseline          最近一次 · 增量基准
```

`<项目名>` 取自 origin 地址的最后一段,同一项目的各个 worktree 和克隆共用记录;`<目标>` 是 `branch-<分支>`、`mr-<编号>`、`pr-<编号>` 或 `range-<范围>`。`CROSSCHECK_HOME` 可以改存放位置。

同一个目标再次审查时默认**只看变了的文件**,上次在没变文件里的发现原样带过来,变了的重新核实,分成「新发现」「上次遗留」「已解决」。以下情况全量重审:你说「重新审」或带 `--full`;规则、审查设置、`--intent` / `--doc`、`--only`、`--with-tests`、模型或插件本身变了;这次深度比上次高。

## 审查范围和维度

| 维度 | 查什么 |
|---|---|
| `bug` | 逻辑错误、边界、空值、并发、错误处理、资源泄漏、API 误用 |
| `security` | 注入、越权、密钥泄漏、不安全反序列化、SSRF、路径穿越等,要求给出攻击路径 |
| `intent` | 没有满足意图里明确的验收标准 |
| `rules` | 违反项目写下的规范,必须引用原文 |
| `simplify` | 可复用已有代码、重复、过度设计;默认不查 |

- 不报风格、命名、可读性、日志措辞和影响很小的性能优化。
- 只审会在产品路径上执行的代码:测试、日志、构建产物、lock 文件、生成代码、vendored 代码和 `REVIEW.md` 的 `skip` 路径整个跳过(测试被削弱另外扫描);只改注释或排版、原样移动的代码、没有调用方的代码不当作问题。

## 只读与安全

审查过程中不切换分支、不改变仓库状态:审查的不是当前分支时,代码用 `git show` 从目标版本读;只有 PR/MR 会 `git fetch` 一次对方的提交。插件从不往 GitLab / GitHub 写任何东西。审查结束后只有两种写操作:你确认后改工作区里的规则文件;你同意后用配置的工具生成或更新 MR 说明的网页版。

| 保障 | 做什么 | 适用 |
|---|---|---|
| 拦截 | 审查进行期间,hook 拒绝改变仓库状态的 git / gh / glab 命令、对仓库文件的编辑、常见的字面路径写入,以及可能显示凭证的命令和读取;主 agent 和子代理都受限 | Claude Code、Codex(需在 `/hooks` 信任)、Cursor |
| 核对 | 开始时记下分支、HEAD、stash、暂存区和改动文件的哈希,出报告前对比,有变化写在报告最前面 | 所有宿主 |

- 拦截从执行收集改动的脚本开始,到出报告前核对仓库状态结束;脚本提前退出或你中途发新消息时也会解除。只对发起审查的会话有效。
- 凭证相关的拦截只针对主目录下的文件(`~/.zshrc`、`~/.netrc` 等)和 gh/glab 的配置;仓库里同名的文件照常可读。
- MR 描述、需求单、评论、规则文件里写给 reviewer 的话(「忽略安全问题」「approve 这个」)一律不执行。
- 这是防误操作的护栏,不是安全边界:`sh -c "…"`、变量拼出的路径、任意程序写文件拦不住,靠核对事后发现。没有 `jq` 也没有 `python3` 时拦截不生效。

## 配置

配置有两层,每行一个 `key=value`,`#` 开头是注释:

- **插件里的 `skills/cr/crosscheck.conf`**:随插件分发,适合团队统一的设置(需求来源、网页版工具)。用自己的插件市场分发时,团队改一次,所有成员装上就生效。
- **个人的 `~/.crosscheck/config`**:逐项覆盖插件里的。`CROSSCHECK_CONFIG` 可以改位置;示例见 `skills/cr/templates/config.example`。

| 设置 | 作用 |
|---|---|
| `gitlab_hosts` | 按 GitLab 处理的域名,逗号分隔,可以带子路径(如 `company.com/gitlab`);私有化 GitLab 的域名不含 "gitlab" 时必填 |
| `issue_cmd` | 读取非 GitLab 需求单的命令,`{key}` 替换成编号 |
| `model.finder` / `model.verifier` | 查找和核实用的模型,核实最好和查找不同;写当前宿主认识的模型名,不支持时用宿主的模型 |
| `source.<类别>`、`source.required`、`source.<类别>.label`、`source.<类别>.match` | 需求来源,见上 |
| `output.page` | 生成和更新 MR 说明网页版用的 skill 或命令名;不写就只生成本地文件 |

平台按 `--platform` → `CR_PLATFORM` → `gitlab_hosts` → `REVIEW.md` 的 `platform` → 域名 → 链接形态的顺序判断。私有化 GitLab 需要先 `glab auth login --hostname <域名>`。

## 成本

报告末尾有一行「消耗」:用时、启动的查找角色和 verifier 数、候选和通过的条数,以及 token 用量。token 由插件的 hook 从会话记录里读取:Claude Code 包含子代理;Codex 是否包含子代理未知;Cursor 的 hook 不提供用量,不统计。统计不到时写明原因(hook 没运行,或读不到用量)。只读用量数字,不读对话内容。

## 依赖和常见情况

- `git`、POSIX `sh`、**`python3`(3.8+)**。没有 python3 时一开始就会提示安装。
- GitHub PR 用 `gh`,GitLab MR 用 `glab`(都要已登录)。没有或没登录时改用 git 直接拉取代码,但拿不到标题、描述和关联需求,目标分支不是默认分支时要说明一下。
- **必须有本地仓库**。只给 MR 链接而没有本地克隆不行;不在仓库目录里时告诉它仓库在哪。
- **连不上内网 GitLab**:常见于沙箱环境,放开网络或换个环境再试,或改审本地分支。
- **明明登录了却提示没登录**:多半是登录用的环境变量写在 `~/.zshrc` 里,而 agent 的终端不读它。脚本会指出是哪个文件的哪几个变量(不读取、不输出值),并借你的登录 shell 再试一次;一劳永逸的办法是挪到 `~/.zshenv`。
- **用自己的历史 bug 检验**:说「拿我们修过的 bug 测一下能不能抓到」,agent 会从 `git log` 挑修 bug 的提交,对引入 bug 的那次改动跑审查,再挑普通改动看误报。

## 结构

```
skills/cr/
├── SKILL.md          编排流程
├── crosscheck.conf   插件级配置(团队统一)
├── roles/            reviewer / rules-auditor / simplifier / verifier / analyst / judge
├── references/       发现结构、评分标准、误报清单、报告格式、报告之后、维护、常用说法
├── templates/        REVIEW.md 模板、个人配置示例
└── scripts/          审查、规则、记录、MR 说明、规则沉淀的脚本,以及共用的 crlib.py
skills/cr-rules/      规则沉淀(只能用命令调用),复用 skills/cr/scripts
hooks/                Claude Code、Codex、Cursor 各一份 hook 注册
tests/                python3 -m unittest discover -s tests
```

`skills/cr/` 自包含,不依赖宿主专属功能:支持子代理时各角色并行,不支持时由主 agent 依次执行。`hooks/` 只提供额外的拦截和 token 统计,没有它审查照常运行。为什么这样设计见 [DESIGN.md](DESIGN.md)。

想调整行为,直接改对应文件:阈值和评分在 `references/scoring-rubric.md`,不该报的在 `references/false-positives.md`,各角色的关注点在 `roles/`。测试里 `tests/bin/glab` 模拟 GitLab,`tests/bin-gh/gh` 模拟 GitHub。

## 已知限制

- **会漏报**:80 分门槛会挡掉一部分真实但没能在代码里完整追踪到的问题;规则检查防得了编造,防不了漏看。
- **增量按文件判断**:没变的文件依赖了这次改动的符号时会一起重看,但只按名字识别;担心时用 `--full`。基准分支更新后重新变基,那次会退化成全量。
- **影响面靠名字匹配**:依赖注入、反射、MyBatis XML、跨服务调用、再导出搜不到,同名方法会混在一起(标「同名歧义」)。
- **MR 说明可以被改**:贴进 MR 后作者能改,评审人应以写明的提交和 MR 最新提交对照。
- **需求来源靠你配置的工具**:能否读到取决于工具和权限;读取发生在审查开始前,只读拦截还没生效。
- **执行见证只防幻觉**:Codex、Cursor 的 hook 没有独立的退出码,见证只能核对输出;不防刻意伪造。
- **真实环境验证不足**:私有化 GitLab 子路径部署、GitHub 的 issue 和评论读取主要用模拟的 `glab` / `gh` 测过;判断记录只在本机。
