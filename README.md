# crosscheck

本地运行的 AI code review,同一套流程可在 Claude Code、Codex、Cursor 中使用。

核心思路是**宁缺毋滥**:先尽量把可疑的地方找出来,每条候选再由一个没看过推理过程的 verifier 独立核实、给出依据并打分,低于 80 分的不展示。没有问题时就说没有问题。

一次审查产出两份东西:

| | CR 报告 | MR 说明 |
|---|---|---|
| 给谁看 | 开发者自己,照着修 | MR 评审人,开发者贴进 MR 描述 |
| 内容 | 核实过的问题、修复建议、依据 | 需求链接、一句话、请重点看、阅读顺序、影响面、需注意的改动、可能相关的测试、CR 情况 |
| 性质 | 结论,逐条独立核实 | 事实和链接,由脚本生成或核对,不下结论 |

除了找 bug 和安全问题,它还会对照需求单检查有没有做到需求、对照团队写下的规则检查规范,并记住你对每条发现的判断,同一段代码不再重复报同样的误报。另有一个**规则维护**命令:从最近一个季度的 MR 评论里沉淀候选规则让你挑、检查现有规则、起草或整理 `REVIEW.md`。

流程演示和设计说明见 [CR-DESIGN.html](CR-DESIGN.html),在本地浏览器打开;标题右上角的太阳/月亮小图标切换深浅色。

## 快速开始

装好插件后,在要审查的仓库里直接说想看什么,可以带上目的:

```
/crosscheck:cr 帮我看下 MR 128,这次是修复分页丢数据
```

Codex 里是 `$crosscheck:cr ...`,Cursor 里是 `/cr ...`。不需要记任何参数,想怎么审就怎么说,下面「审查」一节列出了常用说法。

## 调用

| 功能 | Claude Code | Codex | Cursor | 能否用自然语言 |
|---|---|---|---|---|
| 审查(cr) | `/crosscheck:cr` | `$crosscheck:cr`(拷贝安装时 `$cr`) | `/cr` | 可以,直接说「review 一下」 |
| 规则维护(cr-rules) | `/crosscheck:cr-rules` | `$crosscheck:cr-rules`(拷贝安装时 `$cr-rules`) | `/cr-rules` | 不可以,只能用命令 |

说「cr 帮助」会列出常用说法。在 Codex 里,插件自带的 hook 要先运行 `/hooks` 审阅并信任才会生效,否则 token 用量统计不工作(审查本身不受影响);升级插件后要重新信任。

## 审查

直接用平时说话的方式提要求,不需要记参数。报告第一行写明这次审查了什么(范围、深度、全量还是增量),范围不对时直接说。

| 想做什么 | 可以这样说 |
|---|---|
| 审当前分支的全部改动(含未提交的) | 「review 一下」 |
| 审另一个分支(不用切过去) | 「看看 feature/pay 分支」 |
| 审一个 PR / MR | 「review MR 128」,或直接贴链接 |
| 审某几个提交 | 「看看最近 3 个提交」 |
| 只看某个目录 | 「只看 src/orders 下面的改动」 |
| 指定对比基准 | 「对比 develop」「要合到 release/1.2」,或者直接给提交:「对比基准是 abc1234」(只对这一次生效) |
| 换个对比基准 | 「换个基准」(重新问一次,并更新这个项目的记录) |
| 快速过一遍 | 「快速看一下」 |
| 上线前仔细审 | 「仔细看看」「上线前深度审一下」 |
| 只关心某一方面 | 「只看安全问题」「只对照团队规范」 |
| 告诉它改动的目的 | 「这次是为了修复分页丢数据」 |
| 给方案、接口文档 | 「方案在 docs/plan.md」 |
| 给需求链接 | 「需求单是 <链接>」「这是 hotfix,没有需求单」 |
| 说明怎么验证的 | 「本地跑过 jest,手工测了翻页」 |
| 测试也一起看 | 「测试也一起看」 |
| 换一个核实用的模型 | 「核实换成某某模型」 |
| 从头完整审一遍 | 「重新审」「全量」 |
| 审完顺手修掉 | 「审完把问题修掉」 |

- **深度**:没说时按 standard。查找由一个 reviewer 在同一个上下文里分遍做(正确性 → 安全 → 需求核对),规则由 rules-auditor 单独查。quick 由主 agent 自己查和核实,最多 5 条;deep 时 reviewer 多做一遍影响面(从调用方往回查),verifier 可以跑项目已有的检查和测试来复现。
- **对比基准**:你没说对比什么时,默认以远端最新的目标分支为准(MR 的目标分支,没有 MR 时是默认分支):审查前先从 origin 拉取目标分支(只更新 `origin/` 下的远程跟踪分支),不用本地可能过期的 `main`。拉取失败(离线、没权限)才用本地已有的,并提醒你目标分支可能不是最新。你说了「对比 develop」或「对比基准是 abc1234」时以你说的为准,只对这一次生效。报告第一行写明基准来自哪一版。
- **先问一次基准**:你这次没说对比什么、这个项目也没记过时,审查开始前问一次:远端最新的目标分支(推荐;已合入的 MR 是「合入前的版本」)、其他分支、某个 commit。选前两项会按项目记成**规则**(「远端最新的目标分支」「分支 develop」),之后每次审查都重新取当时的最新值,不再问;选 commit 只用这一次,不记(记下一个提交,下次一定不对)。想改就说「换个基准」。当前分支离 develop、release/* 这类分支比离默认分支更近时,会在同一个问题里提示。没法问的非交互运行用推荐项,报告里写「基准未确认」。
- **已合入的 MR**:照样能审,审的是合入前的那份改动(用 merge commit、squash 还是 rebase 合入都行)。报告开头会写明「这个 MR 已合入」;MR 说明照常生成,但描述已经影响不了合入;要修的话请另开分支,`--fix` 不会改代码。算不出基准时(比如快进合入)它会请你给一个基准提交,不会给出空的结果。
- **改动很大**:按约 1000 行一批审查;超过 4 批时先问你是全部审、只审某个目录,还是用 quick。
- 你没说「修掉」时不改任何文件;「review 一下」「这个该怎么修」都不算修改请求。

### 审查之后

直接回复,用报告里的编号指代发现。

| 想做什么 | 可以这样说 |
|---|---|
| 表态(会被记住) | 「1 对,2 误报:上游已经重试」「3 先不改:下个版本」 |
| 质疑某条 | 「第 2 条不对吧」(重新读代码核对:成立就解释,站不住就撤回并记录) |
| 修复 | 「把第 1、3 条修掉」 |
| 看没报的 | 「还有别的吗」「70 多分的那些是什么」 |
| 指出漏报 | 「你漏了 cache.ts 的并发问题」 |
| 单独深挖 | 「cache.ts 用 deep 再看一遍」 |
| 定规则 | 「以后这种别报了」「以后都要检查 X」 |
| 改 MR 说明 | 「重点请看 api/orders.ts:42 的兼容分支」「需求文档是 <链接>」 |
| MR 说明网页版 | 配置了 `tools.doc_publisher` 时每次自动发布;「更新网页」手动再发一次 |
| 改完再看 | 「再看一下」(同一目标自动做增量) |

表态、修复、重新审查之后,MR 说明会跟着更新。

## CR 报告

- **第一行**:审查范围、深度、全量还是增量;接着一行写意图取自哪些来源。
- **概览表**:每条缺陷和需求核对一行。
- **逐条发现**:标题写明严重程度、维度和怎么确认的——**已复现**(deep 下实际运行过,有运行记录)或**读代码推断**。每条包含位置、从被审查版本里摘出的问题代码、会导致什么错误结果、修复建议,以及折叠的依据(读过的代码、排除了哪些可能、复现结果)。
- **需求核对**:没有做到的验收标准。
- **规范**:违反团队书面规则的地方,逐字引用规则原文和出处。
- **测试和检查被削弱**:删了断言、新增 skip、降低覆盖率阈值、放宽 CI 等,由脚本扫出,单独列出。
- **改动代码里的原有问题**:真实存在,但改动之前的版本里就有同样的问题。单独列在末尾,不计入发现数,也不进 MR 说明;被这次改动变得更容易触发或范围变大的,仍算这次引入。
- **已按历史判断忽略**(折叠):因为你以前的判断而没报的,可以展开核对。
- **末尾**:用了哪些规则文件、跳过了多少文件、查了哪些维度、消耗(含实际用到的模型)、报告文件的链接。配置的查找或核实模型没有出现在会话记录里时,多一行「模型与配置不一致」;流程有缺项(比如 MR 说明没有生成)时,多一行「流程不完整」。

**核实与打分**:verifier 必须给出依据,脚本核对依据里的代码位置真实存在,不存在或没给的最高 50 分;规则发现的出处和引文对不上的作废;AI 声称跑过但拿不出运行记录的,按读代码推断处理、最高 60 分。verifier 每批最多核实 3 条,严重问题单独核实。低于 80 分的不展示,存在记录里。

报告直接显示在对话里,同时存一份到 `~/.crosscheck/reviews/`,报告末尾给出它的链接。上一次审查中途结束、没有保存时,下次审查同一目标会提示一句,然后照常重新审查。

## MR 说明

审查结束后在报告后面给出,贴进 MR 描述即可。包在 `<!-- crosscheck:begin -->` / `<!-- crosscheck:end -->` 里,控制在 30 行以内,只有事实和链接:

| 部分 | 内容 |
|---|---|
| 基本信息 | 需求单、需求文档的链接和标题(或「未提供(作者跳过)」「无需求单:hotfix」)、分支、规模、审查量(1–5) |
| 一句话 | 你说的这次改动的目的;没说时由 AI 按需求材料起草(必须引用原文,脚本核对),会提示你确认 |
| 请重点看 | 你点名的最多 3 处,每处可以写想要什么反馈;没点名时列出脚本挑的候选,标明「自动列出」 |
| 阅读顺序 | 按 接口和类型 → 实现 → 配置 → 测试 分组;生成代码、纯格式化、纯重命名、lock 文件列为「可跳过」 |
| 影响面 | 签名变了或被删除的函数、接口、配置键,以及本次改动之外的调用方 |
| 需注意 | 数据库迁移、配置键增删、新环境变量、依赖变化 |
| 测试 | 你写的「怎么验证的」,以及可能相关的测试文件(未执行) |
| CR 情况 | 已修复几条;未修复的严重和重要问题附你的判断和理由,没表态的标「未表态」;写明基于哪个提交 |

- 不写已实现、已覆盖、无风险这类结论。改了哪些函数和接口按 TS/JS、Go、Python、Java/Kotlin 的写法识别,其他语言退到 git 标出的所在函数或文件级;配置只看改动行里的键。影响面只按名字在本仓库文本匹配,依赖注入、反射、跨服务调用搜不到;签名不变的行为变化由 CR 报告负责。
- 提交推送到远端后,代码位置带 GitLab / GitHub 的行链接。
- 和 CR 报告一样存一份本地版本:`mr.md`(贴进描述的版本)和完整版 `mr.html`,保存记录时直接写进审查记录目录,回复末尾给出链接。
- 配置了 `tools.doc_publisher` 时自动把 `mr.html` 发布成网页,不再询问;之后随 CR 报告更新同一个页面,描述里多一行「完整版」链接。
- 两种用法自己选:把 `mr.md` 的内容复制进 MR 描述,或者直接把网页链接贴进 MR。
- 插件不提交 MR、不改 MR 描述,只给出 `glab mr create/update` 或 `gh pr create/edit` 命令,由你执行。
- 结构和措辞在模板里:`skills/cr/templates/mr.md`(贴进描述的版本)和 `mr.html`(完整版网页)。影响面、阅读顺序、链接、CR 情况这些事实仍由脚本算好再填进去。团队的 MR 有自己的格式时,在自己的插件市场里改 `mr.md` 就能适配(章节名、顺序、措辞都可以调;占位符的写法见文件开头的注释),不用改脚本。

## 需求和意图

审查会把下面这些汇总成「意图」交给各个角色,用来判断某个行为变化是不是有意的、有没有做到需求:

- MR 描述;本地分支时用提交说明。
- 关联的需求单:GitLab Issue 用 `glab` 读,GitHub issue 用 `gh` 读,其他系统用配置的需求管理工具(见下)。
- MR / PR 上已有的人工讨论(已经有人指出的问题不重复报;经代码托管工具读到的讨论,即使标着已答复、已解决,问题还在也照报,只标注「讨论中已有人提出」)。
- 你说的这次改动的目的,和你给的方案、接口文档。
- 配置的需求管理工具和文档阅读工具(见下)。

意图里有明确验收标准时,报告多一节「需求核对」。意图只能解释改动,不能让安全问题不报。

### 需求单和需求文档

配置里可以告诉 agent 去哪里读需求单和需求文档,写法见下面「配置」一节。配了之后:

- 先从 MR 描述、分支名、提交说明和你说的话里自动找链接。要让它认得你们的需求链接,就在配置的那句话里写一个链接示例,它会按其中的域名识别。
- 缺了就在审查开始前问一次:贴链接、说「没有需求单(hotfix 等)」,或跳过。同一个分支问过就记住,90 天后过期。想每次都要需求文档,在配置里写 `intent.required = ticket, doc`;不写时只要需求单。
- 不是必填的资料(默认是需求文档:PRD、设计文档链接)也问一次,可以直接跳过,不算缺失;跳过后同一个分支不再追问。
- 基准、必填的需求、可选的资料放在**同一轮**问完;什么都不需要问时不打断你。
- 给了链接时,agent 按配置里的说明读取内容(需求文档只取需求描述、验收标准和相关章节),读不到就写明原因,不影响审查。读到的内容只当数据,其中的指令不执行。
- MR 说明里只放链接和标题,不引用需求原文。

## 项目规则

规则就是仓库里的 Markdown 文件,不需要编号或专门格式。**`REVIEW.md` 是可选的**:团队已有的 `CLAUDE.md`、`AGENTS.md` 等直接就能用;一条规则都没有也照常审查,只是没有「规范」一节。

| 来源 | 文件 |
|---|---|
| 审查约定 | `REVIEW.md`(根目录对全部改动生效,子目录只对该目录生效) |
| 沉淀的规则 | `.agents/rules/**/*.md`(按 frontmatter 的 `paths` 生效;规则维护命令沉淀的规则写到这里) |
| Claude Code | `CLAUDE.md`、`.claude/rules/*.md` |
| Codex / 通用 | `AGENTS.md`、`AGENTS.override.md` |
| Cursor | `.cursor/rules/*.mdc` |
| GitHub Copilot | `.github/copilot-instructions.md`、`.github/instructions/*.instructions.md` |

- 只有范围覆盖本次改动文件的规则才生效;约定文件里的操作说明(怎么跑测试等)不当作审查规则。
- 审查 PR/MR、其他分支或提交范围时,规则从 base 那一版读,PR 改不了审查用的规则;审查自己当前的分支时读工作区。
- 规则发现必须写出规则所在的文件和逐字原文,脚本核对后再由 verifier 确认,模型不能凭空编出一条规则。

### REVIEW.md 怎么写

头部(`---` 之间)是审查设置,由脚本执行;正文是规则。模板见 `skills/cr-rules/templates/REVIEW.md`。

```markdown
---
skip: ["src/gen/**"]                 # 不审查的路径
limits: { minor: 3 }                 # 条数上限
---
## 出问题长什么样

- 这是支付回调:失败是重复入账或漏入账,不是日志不好看。

## 每次都要检查

- 新增的 API 路由必须有集成测试。原因:路由是对外契约。
- 数据库查询必须限定在调用方的租户内。原因:曾经出过越权。

## 不要报

- 生成的 protobuf 代码里的命名问题。
```

- 「出问题长什么样」由这块代码的负责人写:它失败时会变成什么样(文档写错事实、配置接错路由或开关、迁移不可回滚……)。只写后果的类型,不用来挑风格、命名上的小毛病;不写也能审查。
- 写成能对照代码检查的短句,加一句原因;「注意性能」这类笼统的要求会被跳过。
- 从一两条开始,单个文件不超过约 15 条;linter 和 CI 能查的不写。
- 「不要报」一节写团队不想再被提醒的情况,只对它所在的目录生效。你否定某条发现时,agent 会问要不要加进去。
- 头部设置(`skip`、`limits`)只认根目录 `REVIEW.md`,不能让插件跳过核实、降低 80 分门槛、自动改代码或 approve。

### 规则维护

用命令 `/crosscheck:cr-rules` 调用,后面带的话决定做哪件事:

| 命令 | 做什么 |
|---|---|
| `/crosscheck:cr-rules`(可带天数,如 `30 天`) | 沉淀:从 MR 评论里归纳候选规则 |
| `/crosscheck:cr-rules 检查` | 检查现有规则 |
| `/crosscheck:cr-rules 整理 REVIEW.md` | 起草或整理根目录的 `REVIEW.md` |

所有改动都先给你看,确认后只改工作区,由你提交。

**沉淀**

1. 只读拉取最近一个季度已合并 MR 的人工评论(去掉机器人和系统消息)和你记下的判断,缓存到本机,下次只拉新的。
2. 归纳出候选规则,脚本按准入清单核对:证据是评论原文、至少 2 个 MR 出现、评论后代码确实改了、能写成「必须/禁止」并有「不要报」的边界、工具查不到、不和已有规则重复。
3. 按出现次数排好列给你挑。选中的写进 `.agents/rules/<主题>.md`,每条写规则、原因、严重级别、正反例、不要报和来源 MR;只改工作区,由你提交。

Claude Code、Cursor 写代码时不会自动读 `.agents/rules/`,需要的话在 `AGENTS.md` / `CLAUDE.md` 里用 `@` 引入(会先问你)。

**检查**:逐条看现有规则能不能对照代码检查、有没有原因、范围和「不要报」的边界、提到的文件和函数还在不在、linter 能不能查、有没有重复或矛盾、文件是否太长,以及在你的审查记录里是否长期被判为误报。结论按文件列出,建议由负责人决定。

**整理 REVIEW.md**:还没有时按模板起草,`skip` 用仓库里确实存在的路径,「不要报」从反复被判为不成立的记录里找候选;已经有时检查头部设置能否解析、路径还能不能匹配,把正文整理成「严重程度」「出问题长什么样」「每次都要检查」「不要报」四节(缺「出问题长什么样」时会提醒你补),写给写代码 agent 的说明建议挪到 `CLAUDE.md` / `AGENTS.md`,规则太多时建议拆到 `.agents/rules/`。

## 判断记录

你对某条发现表态(成立 / 不修 / 不成立 / 有争议)时,agent 记在**你本机**的 `~/.crosscheck/reviews/<项目名>/feedback.jsonl`,不在仓库里,也不共享给别人:

- 对这个项目的所有分支、MR 和范围有效。
- 记着那段代码的样子(出问题的一行加上下各两行)。代码没变就不再报;代码变了会重新评估,并注明之前的判断。
- 不成立和不修必须写原因;因为历史判断而没报的,在报告里折叠列出。
- 想让全队都不再报,写进 `REVIEW.md` 的「不要报」,随代码一起评审。

## 记录与增量审查

```
~/.crosscheck/
├── config                         个人配置
├── mining/<项目名>/               规则沉淀的 MR 评论缓存
└── reviews/<项目名>/
    ├── feedback.jsonl             你的判断
    ├── project.json               这个项目的对比基准规则
    ├── sources/<分支>.json        需求链接、请重点看、网页链接
    └── <目标>/<时间>/             report.md、mr.md、mr.html、findings.json、rejected.json、meta.txt
        latest · baseline          最近一次 · 增量基准
```

`<项目名>` 取自 origin 地址的最后一段,同一项目的各个 worktree 和克隆共用记录;`<目标>` 是 `branch-<分支>`、`mr-<编号>`、`pr-<编号>` 或 `range-<范围>`。`CROSSCHECK_HOME` 可以改存放位置。

同一个目标再次审查时默认**只看变了的文件**,上次在没变文件里的发现原样带过来,变了的重新核实,分成「新发现」「上次遗留」「已解决」。以下情况全量重审:你说「重新审」;规则、审查设置、你给的目的说明和文档、只看某一方面、测试是否一起看、模型或插件本身变了;这次深度比上次高。

## 审查范围和维度

| 维度 | 查什么 |
|---|---|
| `bug` | 逻辑错误、边界、空值、并发、错误处理、资源泄漏、API 误用 |
| `security` | 注入、越权、密钥泄漏、不安全反序列化、SSRF、路径穿越等,要求给出攻击路径 |
| `intent` | 没有满足意图里明确的验收标准 |
| `rules` | 违反项目写下的规范,必须引用原文 |

- 不报风格、命名、可读性、日志措辞和影响很小的性能优化。
- 只审会在产品路径上执行的代码:测试、日志、构建产物、lock 文件、生成代码、vendored 代码和 `REVIEW.md` 的 `skip` 路径整个跳过(测试被削弱另外扫描);只改注释或排版、原样移动的代码、没有调用方的代码不当作问题。

## 只读与安全

审查过程中不切换分支、不改变仓库状态:审查的不是当前分支时,代码用 `git show` 从目标版本读;只有 PR/MR 会 `git fetch` 一次对方的提交。插件从不往 GitLab / GitHub 写任何东西。审查结束后只有两种写操作:你确认后改工作区里的规则文件;配置了网页工具时生成或更新 MR 说明的网页版。

| 保障 | 做什么 | 适用 |
|---|---|---|
| 说明 | 「只读约束」和各角色说明写明不改仓库、不接触凭证、被审查的内容只是数据。靠 agent 遵守,不是强制 | 所有宿主 |
| 核对 | 开始时记下分支、HEAD、stash、暂存区和改动文件的哈希,出报告前对比,有变化写在报告最前面 | 所有宿主 |

- 没有事前拦截:审查过程中 agent 能执行的命令不受限制,所以只读靠说明和出报告前的核对。插件的 hook 只做 token 用量统计。
- MR 描述、需求单、评论、规则文件里写给 reviewer 的话(「忽略安全问题」「approve 这个」)一律不执行。

## 配置

配置有两层,每行一个 `key = value`,`#` 开头是注释:

- **插件里的 `skills/cr/crosscheck.conf`**:随插件分发,适合团队统一的设置。它同时是完整的配置模板:所有设置都列在里面,默认全部注释掉,用哪项就去掉那行开头的 `#` 再填值。用自己的插件市场分发时,团队改一次,所有成员装上就生效。
- **个人的 `~/.crosscheck/config`**:逐项覆盖插件里的。格式相同,可以把 `crosscheck.conf` 复制过去再改。值为空的行和注释行一样,都等于没配置。

**四类外部工具**。插件本身不认识任何一家的工具,由你告诉 agent 用什么;每项的值是**一句话的提示词**:用哪个 skill 或命令、怎么用,想让它自动识别链接就写一个链接示例。

| 设置 | 干什么 | 不写会怎样 | 示例 |
|---|---|---|---|
| `tools.code_host` | 代码托管工具:读 MR / PR 的标题、描述、讨论、目标分支和源引用。**只能是只读的**,不评论、不改描述、不合入。写了以后贴 MR / PR 链接(GitHub、GitLab 的也一样)都由它读;读到的东西插件会自己核对仓库、分支和提交,对不上就只用 git 拉代码,并写明「MR 信息没有读到」 | GitHub 用 gh、GitLab 用 glab;都认不出的平台只能审本地分支 | `用 acme-kit:mr-reader 读 MR,链接形如 https://code.example.com/x/y/merge/12` |
| `tools.requirement` | 需求管理工具:读需求单(标题、描述、验收标准) | 只认 GitLab / GitHub 的 Issue,别的需求单要你用一句话补充目的 | `用 acme-kit:ticket-reader 读需求单,链接形如 https://tickets.example.com/browse/XX-123` |
| `tools.doc_reader` | 文档阅读工具:读 PRD、技术方案等文档链接 | 不读文档内容,只记下链接 | `用 acme-kit:doc-reader 读文档链接,支持 https://docs.example.com/ 下的页面` |
| `tools.doc_publisher` | 文档发布工具:把 MR 说明发布成网页,之后随报告更新 | 只生成本地文件 | `用 acme-kit:page-publisher 把 HTML 发布成网页,返回网页链接` |

写在一行里,值里不要出现「空格加 #」(行尾的 ` # ...` 会被当成注释截掉)。文档阅读和发布常是同一套系统的读写两面,可以写成同一个工具的两句话。

**其他设置**

| 设置 | 作用 |
|---|---|
| `gitlab_hosts` | 按 GitLab 处理的域名,逗号分隔,可以带子路径(如 `company.com/gitlab`);私有化 GitLab 的域名不含 "gitlab" 时必填 |
| `model.finder` / `model.verifier` | 查找和核实用的模型,核实最好和查找不同;写当前宿主认识的模型名,不支持时用宿主的模型。Claude Code 推荐 `model.finder = opus`、`model.verifier = opus`:查找用强模型能找到更多高危问题,但成本比便宜的组合高;想省钱把 `model.finder` 换成 `sonnet`。Codex 用 sol 一类的强模型,Cursor 写它自己的模型名 |
| `intent.required` | 每次都要收集(可跳过)的需求类别,`ticket`(需求单)、`doc`(需求文档),逗号分隔;不写时只有 `ticket` |

平台依次按你指定的、环境变量 `CR_PLATFORM`、`gitlab_hosts`、域名和链接形态判断。私有化 GitLab 需要先 `glab auth login --hostname <域名>`。配置了 `tools.code_host` 时,贴完整链接的 MR / PR 不走这一套,只给编号时照旧。

## 成本

报告末尾有一行「消耗」:用时、启动的查找角色和 verifier 数、候选和通过的条数,以及 token 用量和会话记录里实际出现的模型名。token 在 Claude Code 和 Codex 里统计:由插件的 hook 从会话记录里读取,包含子代理;Cursor 不统计。统计不到时写明原因(hook 没运行、读不到用量,或这个宿主不统计)。只读用量数字和模型名,不读对话内容。

## 依赖和常见情况

- `git`、POSIX `sh`、**`python3`(3.8+)**。没有 python3 时一开始就会提示安装。
- GitHub PR 用 `gh`,GitLab MR 用 `glab`(都要已登录)。没有或没登录时改用 git 直接拉取代码,但拿不到标题、描述和关联需求,目标分支不是默认分支时要说明一下。
- **必须有本地仓库**。只给 MR 链接而没有本地克隆不行;不在仓库目录里时告诉它仓库在哪。
- **连不上内网 GitLab**:常见于沙箱环境,放开网络或换个环境再试,或改审本地分支。
- **明明登录了却提示没登录**:多半是登录用的环境变量写在 `~/.zshrc` 里,而 agent 的终端不读它。脚本会指出是哪个文件的哪几个变量(不读取、不输出值),办法是把它们挪到 `~/.zshenv` 或宿主的环境变量配置里;在那之前会改用 git 直接拉取代码。
- **用自己的历史 bug 检验**:说「拿我们修过的 bug 测一下能不能抓到」,agent 会从 `git log` 挑修 bug 的提交,对引入 bug 的那次改动跑审查,再挑普通改动看误报。

## 结构

```
skills/cr/
├── SKILL.md          编排流程
├── crosscheck.conf   插件级配置(团队统一)
├── roles/            reviewer / rules-auditor / verifier / analyst
├── references/       发现结构、评分标准、误报清单、报告的填写规则、报告之后、维护、常用说法
├── templates/        report.md(CR 报告的骨架)、mr.md 和 mr.html(MR 说明)
└── scripts/          审查、规则、记录、MR 说明、规则沉淀的脚本,以及共用的 crlib.py
skills/cr-rules/      规则维护:沉淀、检查、整理 REVIEW.md(只能用命令调用),复用 skills/cr/scripts;自带 templates/(REVIEW.md、rule.md)
hooks/                Claude Code、Codex、Cursor 各一份 hook 注册(只做 token 统计)
tests/                python3 -m unittest discover -s tests
```

脚本的入口都是 `.sh`,实现放在同名的 `.py` 模块里;每个模块只做一件事(例如收集上下文由 `intent.py`、`discussions.py`、`weakening.py`、`platform_api.py` 组成,公共函数在 `crlib.py`)。`skills/cr/` 自包含,不依赖宿主专属功能:支持子代理时各角色并行,不支持时由主 agent 依次执行。`hooks/` 只提供 token 统计,没有它审查照常运行。为什么这样设计见 [DESIGN.md](DESIGN.md)。

想调整行为,直接改对应文件:阈值和评分在 `references/scoring-rubric.md`,不该报的在 `references/false-positives.md`,各角色的关注点在 `roles/`,报告的章节顺序在 `templates/report.md`(填写规则在 `references/report-format.md`)。每个 skill 的模板放在它自己的 `templates/` 下:cr 的在 `skills/cr/templates/`,cr-rules 的在 `skills/cr-rules/templates/`。测试里 `tests/bin/glab` 模拟 GitLab,`tests/bin-gh/gh` 模拟 GitHub。

## 已知限制

- **会漏报**:80 分门槛会挡掉一部分真实但没能在代码里完整追踪到的问题;规则检查防得了编造,防不了漏看。
- **增量按文件判断**:没变的文件依赖了这次改动的符号时会一起重看,但只按名字识别;担心时说「重新审」。基准分支更新后重新变基,那次会退化成全量。
- **影响面靠名字匹配**:依赖注入、反射、MyBatis XML、跨服务调用、再导出搜不到,同名方法会混在一起(标「同名歧义」)。
- **MR 说明可以被改**:贴进 MR 后作者能改,评审人应以写明的提交和 MR 最新提交对照。
- **需求来源靠你配置的工具**:能否读到取决于工具和权限;读取发生在审查开始前。
- **运行记录只防幻觉**:声称跑过的命令要有 `run-check.sh` 留下的记录,但记录本身不防刻意伪造。
- **真实环境验证不足**:私有化 GitLab 子路径部署、GitHub 的 issue 和评论读取主要用模拟的 `glab` / `gh` 测过;判断记录只在本机。`tools.code_host` 只用本地仓库模拟过,没在真实的代码托管平台上验证。
- **代码托管工具靠约定只读**:`tools.code_host` 由 agent 执行,插件看不出远端的 MR 有没有被改过,只能靠配置和说明里「只读」的约束;读到的标题、描述和讨论也只是 agent 转述的,插件只核对得了仓库、分支和提交。
