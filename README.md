# crosscheck

在本地仓库中运行的 AI 代码审查插件,支持 Claude Code、Codex、Cursor,可审本地分支、提交范围、GitHub PR 和 GitLab MR。

**先查找候选,再独立核实,只展示证据评分达到 80 分的发现。** 每条附代码位置、失败场景和修复建议;没有确认发现也会如实说明。quick 由主线程顺序查找和核实,standard / deep 在宿主支持时使用独立子代理。评分衡量证据充分程度,不是正确概率。

| 什么时候用 | 命令 | 得到什么 |
|---|---|---|
| 检查改动里的 bug、安全问题、需求遗漏和规则违反 | `review` | CR 报告,供开发者核对和修复;可记录你对发现的判断 |
| 准备向评审人说明这次改动 | `describe` | 可复制的 PR/MR 描述 `describe.md` 和含出处的完整版 `describe.html`;不依赖审查结果 |
| 把反复出现的评审意见变成规则,或检查、整理现有规则 | `improve` | 候选计划或修改建议;确认后才改工作区规则 |

**托管平台始终只读。** 插件不创建或修改 PR/MR、评论和状态;描述由你复制粘贴。审查默认不改代码,明确要求修复后才改本地工作区。这里的“本地”指运行方式,仍可通过 Git、gh/glab 或配置的工具读取远端资料;不提供平台机器人或 CI 服务部署。

[快速开始](#快速开始) · [审查](#审查) · [PR/MR 描述](#prmr-描述describe) · [规则维护](#规则维护improve) · [配置](#配置) · [已知限制](#已知限制)。原理和流程演示见 [DESIGN.html](DESIGN.html),在本地浏览器打开。

## 快速开始

1. 从 **person-marketplace** 安装完整插件,命令见市场仓库 README 的安装指南。插件仓库本身不带市场清单。已有源码时,Claude Code 可直接用 `claude --plugin-dir "<crosscheck插件根目录>"` 加载;手动拷贝见[安装与目录布局](#安装与目录布局)。
2. 进入要审查的本地 Git 仓库。需要 `git`、POSIX `sh`、`python3`(3.8+);读取 GitHub PR / GitLab MR 的信息还需要已登录的 `gh` / `glab`,或配置只读的 `tools.code_host`。只给远端链接而没有本地克隆不能运行。
3. 在宿主中输入命令,带上目标和改动目的即可:

```text
/crosscheck:review 帮我看下 MR 128,这次是修复分页丢数据
```

不带目标时审当前分支的全部改动(含未提交内容)。Codex 使用 `$crosscheck:review ...`,Cursor 使用 `/review ...`。报告会写明实际范围与基准;无法确定基准时才提问。

需要描述时用 `/crosscheck:describe 帮我写一下这个分支的 PR 描述`;需要维护规则时用 `/crosscheck:improve` 选择任务。三个命令的宿主写法见下表。

## 调用

| 功能 | Claude Code | Codex | Cursor | 能否用自然语言 |
|---|---|---|---|---|
| 审查(review) | `/crosscheck:review`(拷贝安装时 `/review`) | `$crosscheck:review`(拷贝安装时 `$review`) | `/review` | 可以,直接说「review 一下」 |
| PR/MR 描述(describe) | `/crosscheck:describe`(拷贝安装时 `/describe`) | `$crosscheck:describe`(拷贝安装时 `$describe`) | `/describe` | 可以,直接说「写一下 PR 描述」 |
| 规则维护(improve) | `/crosscheck:improve`(拷贝安装时 `/improve`) | `$crosscheck:improve`(拷贝安装时 `$improve`) | `/improve` | 不可以,只能用命令 |

说「review 帮助」会列出常用说法。在 Codex 里,插件自带的 hook 要先运行 `/hooks` 审阅并信任才会生效,否则 token 用量统计不工作(审查本身不受影响);升级插件后要重新信任。

## PR/MR 描述(describe)

给评审人看的改动说明,在要提 PR / MR 的分支上直接说:

```
/crosscheck:describe 帮我写一下这个分支的 PR 描述
```

也可以带分支、提交范围、PR / MR 编号或链接。开始前问哪些资料由配置 `describe.ask` 定(不写是需求单 `requirement`),而且要配了对应的读取工具(`tools.requirement` / `tools.doc_reader`),没配的类别不问。要问的每次生成都问一次(审查记录里问过也照问):贴链接、说没有需求单(hotfix、重构),或跳过。非交互运行(`claude -p`、`codex exec`、CI)不提问,没有资料链接时表格对应值留空。给了链接后按配置的 `tools.requirement` 读取,读不到就如实写读不到;没配工具时不读取需求单,表格仍保留这一行。

### 产物与内容

文件保存在 `~/.crosscheck/describe/<项目名>/<目标>/`:

| 文件 | 用途与内容 |
|---|---|
| `describe.md` | 复制进 PR/MR 描述。依次是资料表、人工填写的 CR 负责人、改了什么、主要影响、请重点看(作者点名才有)、怎么验证 |
| `describe.html` | 完整版,补充规模、分支、需求对照、代码块编号 H1… 与出处、技术明细和自动识别范围 |

短描述的各部分这样生成:

- **资料与负责人**:需求单、需求文档、设计稿各一行,始终保留,没有链接就留空;本地文件不写入资料表。作者没给需求文档或设计稿时,可从需求材料中找链接,链接必须原样出现在材料里。表格后、改了什么前固定为人工填写的单行 `### CR负责人: @reviewer.username`,不查询或设置远端 reviewer。
- **改了什么**:先一句话,再按功能分组,文字和代码名按可读性组织,不设字数、反引号数量或固定句式门槛;文件链接和代码块编号只进完整版。多语言文案按文件数和语言汇总;没归组的代码块由脚本补一条「其他」,文件多时按目录汇总。
- **主要影响**:写 diff 直接支持、能补充改动说明的业务影响,以及接口、删除/签名变化、迁移、配置与依赖等必要技术变化。**有效业务影响和必要技术事实不按数量或篇幅裁剪**,无内容时省略。普通内部新增函数、资源数量明细和技术自动识别限制只进完整版。引用校验只确认出处,不证明业务语义。
- **怎么验证**:由 analyst 根据改动和目标版本的必要上下文起草可操作建议,不限条数,不强制箭头句式。建议须关联对应改动组,引文核对到本次 diff 或目标版本文件的具体位置;来源真实不代表业务判断正确。没有分析、缺批或无法确定入口时明确披露缺项,脚本不会补造步骤、预期效果或验证结果;自动识别的入口只在完整版标为「入口线索,未核对调用链」。步骤不表示已经执行。不会问你「怎么验证的」;你主动给了执行情况,才有「执行记录」。

想让评审人重点看某处,可以主动点名,最多 3 条。「执行记录」和「请重点看」会在之后重新生成时沿用。模板在 `skills/describe/templates/`,团队可以调整格式。

### 与审查的关系

描述只列事实和链接,不判断对错、风险或修复建议。它复用 review 的采集脚本(origin 绑定、只读、基准问答一致),不依赖审查结果,没审查过也能用。描述目录与 `reviews/` 分开,不会被增量审查当成上一次审查;采集后恢复原有的「进行中」标记和需求来源记录。与同一目标的审查并发运行仍有互相覆盖记录的风险,见「已知限制」。

生成后自己核对 `describe.md`,再复制粘贴;插件不提供发布配置。

## 审查

直接用平时说话的方式提要求。报告开头写明这次审查了什么(范围、深度、全量还是增量),范围不对时直接说。

| 想做什么 | 可以这样说 |
|---|---|
| 审当前分支的全部改动(含未提交的) | 「review 一下」 |
| 审另一个分支(不用切过去) | 「看看 feature/pay 分支」 |
| 审一个 PR / MR | 「review MR 128」,或直接贴链接 |
| 审某几个提交 | 「看看最近 3 个提交」 |
| 只看某个目录 | 「只看 src/orders 下面的改动」 |
| 指定对比基准 | 「对比 develop」「要合到 release/1.2」,或者直接给提交:「对比基准是 abc1234」(只对这一次生效) |
| 换个对比基准 | 「换个基准」(重新选择,默认仅本次,不改项目记录) |
| 记住基准规则 | 「以后跟随每个 MR 的目标分支,记住」「以后固定对比 develop,记住」 |
| 快速过一遍 | 「快速看一下」 |
| 上线前仔细审 | 「仔细看看」「上线前深度审一下」 |
| 只关心某一方面 | 「只看安全问题」「只对照团队规范」 |
| 告诉它改动的目的 | 「这次是为了修复分页丢数据」 |
| 给方案、接口文档 | 「方案在 docs/plan.md」 |
| 给需求链接 | 「需求单是 <链接>」「这是 hotfix,没有需求单」 |
| 说明怎么验证的 | 「本地跑过 jest,手工测了翻页」 |
| 测试也一起看 | 「测试也一起看」 |
| 换一个核实用的模型 | 「核实换成某某模型」 |
| 从头完整审一遍 | 「重新审」「全量」 |
| 审完顺手修掉 | 「审完把问题修掉」 |

- **深度**:没说时按 standard;quick 最快,最多报 5 条,全程由主线程自己查找和核实、不启动子代理(要独立查找和核实用 standard);deep 会多查一遍影响面(从调用方往回查),并在工作区就是被审查的版本时按需运行项目已有的检查和测试来复现问题(工作区不是被审版本时只读代码,报告会写明)。
- **对比基准自动选,确定不了才问**:你当次明确指定的优先,其次是你明确保存的项目规则;PR/MR 用目标分支;本地分支会从分支创建记录识别切出来源(例如 feature/pay 从 develop 切出,就对比最新的 origin/develop)。记录缺失或有歧义时才问你,不会猜。报告开头写明实际基准和来源。
- **默认不记住**:你指定或回答的基准都只对这一次生效,问题里会提示「是否记住为这个项目的默认规则」,明确说记住才保存(可以保存「跟随每个 MR 的目标分支」或「固定对比 develop」,每次仍取最新版本)。
- **基准不可用时**:没有共同祖先、基准分支缺失等情况会停下来说明原因,让你指定分支或提交,不会当成「没有问题」。非交互运行无法确认来源时用推荐基准并标「基准未确认」。
- **已合入的 MR**:照样能审,审的是合入前的那份改动。报告开头会写明「这个 MR 已合入」;要修的话请另开分支,`--fix` 不会改代码。
- **改动很大**:按约 1000 行一批审查;超过 4 批时先问你是全部审、只审某个目录,还是用 quick。
- 你没说「修掉」时不改任何文件;「review 一下」「这个该怎么修」都不算修改请求。

### 审查之后

直接回复,用报告里的编号指代发现。

| 想做什么 | 可以这样说 |
|---|---|
| 表态(会被记住) | 「1 对,2 误报:上游已经重试」「3 先不改:下个版本」 |
| 质疑某条 | 「第 2 条不对吧」(重新读代码核对:成立就解释,站不住就撤回并记录) |
| 修复 | 「把第 1、3 条修掉」 |
| 看没报的 | 「还有别的吗」「70 多分的那些是什么」 |
| 指出漏报 | 「你漏了 cache.ts 的并发问题」 |
| 单独深挖 | 「cache.ts 用 deep 再看一遍」 |
| 当场定一条规则 | 「以后都要检查 X」(写进 `.agents/rules/`)、「以后这种别报了」(规则的例外写进那条规则的「不要报」字段,其余写进对应目录 `REVIEW.md` 的「不要报」);先给你看,确认后只改工作区 |
| 补充需求资料 | 「需求文档是 <链接>」「这个没有需求单」 |
| 改完再看 | 「再看一下」(同一目标自动做增量) |

## CR 报告

报告直接显示在对话里,同时存一份到 `~/.crosscheck/reviews/`,末尾给出链接。上一次审查中途结束、没有保存时,下次审查同一目标会提示一句,然后照常重新审查。

- **开头**:标题和首句概括本次发现及覆盖限制;未完成时明确写「审查未完成」「已检查部分确认 N 条发现」。再写范围、深度、全量还是增量,以及意图来源。
- **概览表**:每条缺陷和需求核对一行。
- **逐条发现**:标题写明严重程度、维度和怎么确认的(**已复现**、**读代码推断**等);每条有位置、问题代码、失败后果、修复建议和折叠的依据,运行过的保留真实命令和日志。
- **需求核对**:没有做到的验收标准。
- **规范**:违反团队书面规则的地方,逐字引用规则原文和出处。
- **测试与检查变更**:删断言、新增 skip、降低覆盖率阈值、放宽 CI 等检测信号单独列出,附位置和短原文,不代表已确认缺陷,不计入发现数。
- **改动代码里的原有问题**:真实存在,但改动之前就有。单独列在末尾,不计入发现数;被这次改动变得更容易触发的,仍算这次引入。
- **已按历史判断忽略**(折叠):你之前判为不修、不成立的条目。「不修」不等于「不成立」,仍保留当前证据分;调用环境变化时会重新核实。
- **末尾**:用了哪些规则文件、跳过了多少文件、查了哪些维度、消耗、报告文件的链接。查找覆盖受限或流程缺项时会标「流程不完整」「覆盖可能受限」。

**分数怎么看**:每条发现都有依据,依据里的代码位置会被脚本核对;不存在或没给依据的最高 50 分;声称跑过但没有运行记录的按读代码推断处理。低于 80 分的不展示,但存在记录里,想看说「70 多分的那些是什么」。分数衡量证据充分程度,80 分不代表 80% 的正确概率。

## 需求和意图

审查会把下面这些汇总成「意图」,用来判断某个行为变化是不是有意的、有没有做到需求:

- MR 描述;本地分支时用提交说明。
- 关联的需求单:GitLab Issue 用 `glab` 读,GitHub issue 用 `gh` 读,其他系统用配置的需求管理工具(见「配置」)。
- MR / PR 上已有的人工讨论(已经有人指出的问题不重复报;问题还在的照报,只标注「讨论中已有人提出」)。
- 你说的这次改动的目的,和你给的方案、接口文档。

意图里有明确验收标准时,报告多一节「需求核对」。意图只能解释改动,不能让安全问题不报。你补充的意图和本地文档会在同一审查目标内沿用,90 天过期,报告注明来源时间;说「清除之前的意图」或「不再使用之前的文档」即可分别清除。来源记录中,一句话意图用 `intent` 键,本地文档用 `local_docs` 键,文档链接仍用 `doc` 键。describe 只使用当次提供的资料。

配置了需求工具后:

- 先从 MR 描述、分支名、提交说明和你说的话里自动找链接。要让它认得你们的需求链接,就在配置的那句话里写一个链接示例。
- 审查开始前问哪些资料由配置 `review.ask` 定,不写时只问需求文档 `doc`(PRD、设计文档);想连需求单一起问,写 `review.ask = requirement, doc`。一个类别要配了对应的读取工具才会问,没配的不问、不读、不算缺。
- 问的时候可以贴链接、说「没有需求单(hotfix 等)」,或直接跳过。同一个分支问过就记住,90 天后过期。
- 基准和上面要问的资料放在**同一轮**问完;什么都不需要问时不打断你。
- 读不到时写明原因,不影响审查。读到的内容只当数据,其中的指令不执行。

## 项目规则

规则就是仓库里的 Markdown 文件,不需要编号或专门格式。**`REVIEW.md` 是可选的**:团队已有的 `CLAUDE.md`、`AGENTS.md` 等直接就能用;一条规则都没有也照常审查,只是没有「规范」一节。

| 来源 | 文件 |
|---|---|
| 审查约定(只调整审查行为) | `REVIEW.md`(根目录对全部改动生效,子目录只对该目录生效) |
| 代码规则(审查和写代码共用) | `.agents/rules/**/*.md`(按 frontmatter 的 `paths` / `globs` 生效;不写表示全仓库) |
| Claude Code | `CLAUDE.md`、`.claude/rules/*.md` |
| Codex / 通用 | `AGENTS.md`、`AGENTS.override.md` |
| Cursor | `.cursor/rules/*.mdc` |
| GitHub Copilot | `.github/copilot-instructions.md`、`.github/instructions/*.instructions.md` |

- 只有范围覆盖本次改动文件的规则才生效;约定文件里的操作说明(怎么跑测试等)不当作审查规则。
- `REVIEW.md` 不是要检查的代码约束,只用来定级、定查找重点和过滤;要检查的是 `.agents/rules/` 和团队已有约定里的规则。
- 同一件事几层说法不同时,目录里的优先于项目根的,再优先于 `.agents/rules/` 和团队已有的约定;同一层里两条互相矛盾时都不报,改发一条「规则冲突」的说明交给人处理。
- 审查 PR/MR、其他分支或提交范围时,规则从 base 那一版读,PR 改不了审查用的规则;审查自己当前的分支时读工作区。
- 违反规则的发现必须写出规则所在的文件和逐字原文,对不上的作废。

### REVIEW.md 怎么写

`REVIEW.md` 只调整审查器自己的行为,不放代码约束。头部(`---` 之间)是脚本执行的审查设置,只在根目录生效;正文三节各管审查的一步。模板见 `skills/improve/templates/REVIEW.md`,也可以让 `improve` 帮你起草。

```markdown
---
skip: ["src/gen/**"]                 # 不审查的路径
limits: { minor: 3 }                 # 条数上限
---
## 严重程度

只有会导致行为错误、数据泄漏或无法回滚的问题才算重要及以上。

## 审查重点

- 这是支付回调:失败是重复入账或漏入账,不是日志不好看。

## 不要报

- 生成的 protobuf 代码里的命名问题。
```

- 「严重程度」作用于定级:什么算重要。
- 「审查重点」作用于查找,由这块代码的负责人写:它失败时会变成什么样(文档写错事实、配置接错路由或开关、迁移不可回滚……)。只写后果的类型,不用来挑风格、命名上的小毛病;不写也能审查。
- 「不要报」作用于过滤,只压住审查器的通用直觉(「应该加重试」「应该补测试」「可以重构」这类不来自任何项目规则的建议),写清在什么条件下不报,要写窄。某条规则自己的例外不写这里,写进那条规则的「不要报」字段。你否定某条发现时,agent 会问要不要记下来。
- 子目录的 `REVIEW.md` 只有这三节,只对所在目录生效;头部设置(`skip`、`limits`)只认根目录 `REVIEW.md`,头部没写完整(缺结尾的 `---`)时会提示设置没有生效。任何规则都不能让插件跳过核实、降低 80 分门槛、自动改代码或 approve。
- 一条好规则、规则文件的完整样例,见 [DESIGN.html](DESIGN.html) 的「CR 规则」一节。

**一句话放哪,依次问三个问题**

1. 脚本能执行吗(跳过哪些路径、报几条)?能 → 根目录 `REVIEW.md` 的头部。
2. 写代码的 agent 也要遵守吗(必须 / 禁止怎样写代码,比如「数据库查询必须限定在调用方的租户内」)?要 → `.agents/rules/<主题>.md`,审查和写代码共用,用 `paths` / `globs` 限定范围;规则自己的例外写在规则块的「不要报」字段。
3. 都不是 → `REVIEW.md` 正文的三节。

不该写的:linter 和 CI 能查的;泛泛的规范(「写干净代码」);大段背景或设计介绍;写给写代码 agent 的操作说明(放 `CLAUDE.md` / `AGENTS.md`)。从一两条开始,同样的评论反复出现再加;单个文件约 15 条以内,越短越容易被遵守。

### 规则维护(improve)

只能用命令调用(不会被自然语言自动触发):

| 命令 | 做什么 |
|---|---|
| `/crosscheck:improve` | 不带参数先列出三件事,问你选哪件 |
| `/crosscheck:improve 沉淀`(可带时间,如 `30 天`、`最近半年`) | 从已合并 MR 的评论里归纳候选规则,生成一份计划让你修改,预演无误后写入 |
| `/crosscheck:improve 检查` | 检查现有规则 |
| `/crosscheck:improve 整理 REVIEW.md` | 起草或整理根目录的 `REVIEW.md` |

所有改动都先给你看,确认后只改工作区,不会 `git add` 或提交,由你检查后提交。审当前分支时读工作区规则;PR/MR、其他分支和提交范围从 base 读取规则。

**规则写到哪**:要查的(「以后都要查 X」、沉淀出的规则类)写进 `.agents/rules/<主题>.md`。不要报的(「以后这种别报了」、沉淀出的不要报类)是某条已有规则的例外时,并进 `.agents/rules/<主题>.md` 里那条规则的「不要报」字段(计划里的去向写 `.agents/rules/<主题>.md#<规则标题>`);是审查器的通用直觉时写进 `REVIEW.md` 的「不要报」,范围正好是一个目录的用该目录的 `REVIEW.md`,否则用根目录的并把范围写进句子。

**沉淀**

1. 只读拉取范围内所有目标分支的已合并 MR(GitHub 从已关闭 PR 中筛选已合并项)及完整讨论,并冻结本机判断记录。默认最近 90 天,没有隐含 MR 数量上限;可按时间调整,或显式用 `--limit` 限定最近合并数量并披露范围。GitLab 去掉系统事件,两边只按平台明确标识过滤机器人,保留作者回复并区分作者与其他评论。分页失败或缓存版本不明时记录未完成资源和错误类型,停止生成计划。
2. **分批观察**:本次 `snapshot.json` 固定评论与判断记录,`batch-<n>.json` 按完整线程分批控制上下文。每批允许保留单 MR 观察,附反证、未知和主题级排除理由;先核对所有批次、线程覆盖声明及引文,生成 `observations.json`,缺批或未读完不能用空数组补齐。
3. **全局归并**:汇合全部观察与判断记录,回查完整讨论,再应用至少两个独立 MR/判断记录的门槛。模型附具体依据判断 accepted/rejected/unknown,平台 `resolved` 和 `changed_after` 独立保留,不等于采纳;明确未采纳的 MR 不凑支持案例,wontfix 不自动成为永久不报。核对已有规范和实际运行的检查配置,不靠词句相似度或自检布尔值认定覆盖。读取明确规则路径中的文件/目录链接及规则正文的显式本地文件引用,在 `rules-sources.json` 和 `existing-rules.txt` 冻结逻辑路径、真实来源、范围和全文;不自动读取远程链接。无法读取的来源记问题,覆盖未核对完整时标未知/待确认。项目外来源只读,写入边界不变。
4. **生成计划**:全局结果写入 `synthesis.json`,脚本重新核对结构、引文与来源,不替模型判断共同约束。每个观察和判断记录须进入候选或附理由的排除项,零候选也说明主题级原因。工作目录生成 `plan.md`,候选与计划内容指纹绑定。动作默认「待定」;证据从 candidates.json 取。已有计划可用相同候选重跑,候选变化则保留原配对并拒绝;重新采集到新目录可生成另一份计划。
5. **对话修改**:改措辞、范围、严重级别、去向及「写入 / 跳过」后运行 `rules-write.py <work_dir> --check`,展示实际 diff。反例、正例是字段后的围栏代码块,可多行,写进规则文件时保持同一写法。标了「写入」但仍有待确认项(评审人只有 1 位、已采纳不足 2 个、已有约束未核对完整、缺示例)时预演输出 WARN,写不写由负责人定;原因字段里写了 MR 号报 ERROR,来源只由脚本写在注释里。任何校验错误都不落盘。规则类不能写进 `REVIEW.md`;例外指向的规则找不到或标题重复时报 ERROR;子目录 `REVIEW.md` 只能覆盖所在目录。
6. **确定写入**:确认预演后 `--apply`,逐文件原子替换,成功才输出 WRITE,最后更新计划状态。目标物理路径不得越出工作区或进入 Git 元数据。失败报告已完成、未完成及计划状态;修复后重跑,完整规则、范围、边界一致才跳过并补记状态。手写规则文件仍受保护,只改工作区。

Claude Code、Cursor 写代码时不会自动读 `.agents/rules/`。写入后脚本按仓库里有什么打印接入建议:有 `.claude/` 时给建 `.claude/rules/<主题>.md` 软链接的命令,有 `.cursor/` 时给建 `.cursor/rules/<主题>.mdc` 软链接的命令(Cursor 官方未写明软链接和多余字段的处理,请自行确认),有 `AGENTS.md` 时给一行写明适用路径的普通 Markdown 链接;已经接上的不再提示。建议只打印,agent 不会替你执行。新建的规则文件头部 `paths` 和 `globs` 写同一串逗号分隔的 glob(Claude 只读 paths,Cursor 只读 globs);两者都写但范围不同时,审查会提示规则来源有问题。经软链接出现多次的同一份规则只读一次,优先按 `.agents/rules/` 的路径读。

**检查**:逐条看现有规则能不能对照代码检查、有没有原因、范围和「不要报」的边界、提到的文件和函数还在不在、linter 能不能查、有没有重复或矛盾、文件是否太长,以及在你的审查记录里是否长期被判为误报。结论按文件列出,由负责人决定改不改。

**整理 REVIEW.md**:还没有时按模板起草,`skip` 只用仓库里确实存在的路径,「不要报」从反复被判为不成立的记录里找候选;已经有时检查头部设置能否解析、路径还能不能匹配,把正文整理成「严重程度」「审查重点」「不要报」三节,里面的代码约束(包括旧版「每次都要检查」一节)标为放错位置、建议挪到 `.agents/rules/`(只提示,不自动迁移),写给写代码 agent 的说明建议挪到 `CLAUDE.md` / `AGENTS.md`。只整理 `REVIEW.md` 本身,不顺带改 `.agents/rules`。

**什么时候维护**:同一类问题被人工指出两次以上就沉淀;审查里反复出现你认为不该报的,写进对应规则或 `REVIEW.md` 的「不要报」;规则文件太长或长期没命中,就用「检查」整理。每次只加少量,下一轮审查看有没有被遵循,再决定要不要继续加。

## 判断记录

你对某条发现表态(成立 / 不修 / 不成立 / 有争议)时,agent 记在**你本机**的 `~/.crosscheck/reviews/<项目名>/feedback.jsonl`,不在仓库里,也不共享给别人:

- 对这个项目的所有分支、MR 和范围有效。
- 记着那段代码的样子(出问题的一行加上下各两行)。代码没变就不再报;代码变了会重新评估,并注明之前的判断。
- 不成立和不修必须写原因;因为历史判断而没报的,在报告里折叠列出。
- 想让全队都不再报:是某条规则的例外,写进那条规则的「不要报」字段;否则写进 `REVIEW.md` 的「不要报」。都随代码一起评审。

## 记录与增量审查

```
~/.crosscheck/
├── config                         个人配置
├── mining/<项目名>/               规则沉淀的 MR 评论缓存
└── reviews/<项目名>/
    ├── feedback.jsonl             你的判断
    ├── project.json               这个项目的对比基准规则
    ├── sources/<分支>.json        需求链接、你补充的意图和文档(90 天)
    └── <对象>/<时间>/             report.md、findings.json、rejected.json、meta.txt
        latest                     最近一次
```

`<项目名>` 取自 origin 地址的最后一段,同一项目的各个 worktree 和克隆共用记录;`<对象>` 是 `branch-<分支>`、`mr-<编号>`、`pr-<编号>` 或 `range-<范围>`。同时审查多个目标互不影响。

同一个目标再次审查时默认**只看变了的文件**;未变文件的发现若涉及历史反馈、引用证据变化或缺少旧证据快照,也会重审主文件并重新核实,其余原样带过来,分成「新发现」「上次遗留」「已解决」。以下情况全量重审:你说「重新审」;规则、审查设置、你给的目的说明和文档、实际读取的远端需求正文或读取状态、只看某一方面、测试是否一起看、模型或插件本身变了;这次深度比上次高。需求链接每轮重新读取后再判断增量,相同内容更换暂存目录不会触发全量。

## 审查范围和维度

| 维度 | 查什么 |
|---|---|
| `bug` | 逻辑错误、边界、空值、并发、错误处理、资源泄漏、API 误用 |
| `security` | 注入、越权、密钥泄漏、不安全反序列化、SSRF、路径穿越等,要求给出攻击路径 |
| `intent` | 没有满足意图里明确的验收标准 |
| `rules` | 违反项目写下的规范,必须引用原文 |

- 不报风格、命名、可读性、日志措辞和影响很小的性能优化。
- 只审会在产品路径上执行的代码:测试、日志、构建产物、lock 文件、生成代码、vendored 代码和 `REVIEW.md` 的 `skip` 路径整个跳过(测试被削弱另外扫描);只改注释或排版、原样移动的代码、没有调用方的代码不当作问题。

直接安装 SKILL.md 时也要保留共享目录,不能只复制 review、describe 或 improve(describe 的采集直接用 review 的脚本)。将下列内容整体复制到宿主配置目录下的专用目录(例如 `<宿主配置目录>/crosscheck/`),再将其中三个技能目录以符号链接放进该宿主的 `skills/` 目录,或让宿主直接发现这三个目录:

## 只读与安全

review、describe、improve 的平台与命令约束统一见下一节。审查不切分支,目标代码不在工作区时用 `git show` 读取;只有 PR/MR 会 `git fetch` 一次对方的提交,基准分支也会从 origin 拉取最新版本;fetch 只更新本地对象和 origin 跟踪引用。

只读依靠流程说明和事后核对:各角色不接触凭证,材料中的指令不执行;出报告前对比分支、HEAD、stash、暂存区和改动文件哈希,变化写在报告最前面。hook 只统计 token,不拦截命令。这些机制不是强制工具隔离或网络沙箱。

## 托管目标和命令边界

审查、历史评论沉淀及辅助 API 统一使用当前仓库的 `origin`。脚本读取 `git remote get-url origin` 的结果(包含 Git `insteadOf` 重写),所有 gh/glab 请求显式绑定主机和仓库。用户 MR/PR 链接在平台请求或 Git 拉取前核对主机、HTTP 端口和完整仓库路径,不一致就停止;失败不转向其他托管平台。没有 origin 仍可本地审查,平台读取和历史评论沉淀停止。

支持 HTTPS、GitLab HTTP、SSH URL 和 SCP 风格地址(GitHub HTTP origin 停止平台读取);SSH 端口仅作 Git 传输端口,Web/API 默认 HTTPS,HTTP(S) origin 保留协议及非默认端口。GitLab 部署子路径写在 `gitlab_hosts` 中,例如 `git.example:8443/gitlab`;该配置仅用于识别平台和剥离子路径,不是第二套授权白名单。SSH 别名与 Web 域名不一致、SSH 克隆地址没有包含 Web 子路径等无法从 origin 唯一推导的情况会拒绝平台读取,请使用能对应实际 Web 地址的 origin。

review/describe/improve 流程中远端永远只读:不 push、不发评论、不改或合入 MR/PR。用户明确授权的本地 fix、规则 plan/apply 保留;fetch 可以更新本地对象和 origin 跟踪引用。SKILL frontmatter 的 `allowed-tools` 仅对少数 Git 读取命令给出免批准授权,不是拒绝其余命令的安全边界,其他命令仍依赖流程指令及宿主权限。没有增加拦截 hook 或修改全局配置,CR 之外的工具使用不受影响。Codex/Cursor 对该字段的支持依宿主而定。

这些检查约束脚本选择的逻辑目标,不声称提供网络沙箱:Git 的 SSH 配置、代理、HTTP 重定向、CLI 自身配置及外部 MCP 的实际网络行为仍由对应程序/宿主管理。`tools.code_host` 只应在脚本返回 NEED_CODE_HOST 后按已核对链接读取,返回后还会再次核对当前 origin。

## 配置

配置有两层,每行一个 `key = value`,`#` 开头是注释:

- **插件里的 `config/defaults.conf`**:随插件分发,适合团队统一的设置。它同时是完整的配置模板:所有设置都列在里面,默认全部注释掉,用哪项就去掉那行开头的 `#` 再填值。用自己的插件市场分发时,团队改一次,所有成员装上就生效。
- **个人的 `~/.crosscheck/config`**:逐项覆盖插件里的。格式相同,可以把 `config/defaults.conf` 复制过去再改。值为空的行和注释行一样,都等于没配置。

所有技能共用插件级 `scripts/config.py`(shell 入口 `scripts/config.sh`),例如 `python3 "<插件目录>/scripts/config.py" get model.finder`。`path` 返回个人配置路径,`plugin-path` 返回团队配置路径。`CROSSCHECK_PLUGIN_CONFIG` 覆盖团队文件位置;个人文件固定是 `~/.crosscheck/config`。个人非空值逐项覆盖团队值,空环境变量按未设置处理。迁移不移动或改写个人配置。

**三类外部工具**。插件本身不认识任何一家的工具,由你告诉 agent 用什么;每项的值是**一句话的提示词**:用哪个 skill 或命令、怎么用,想让它自动识别链接就写一个链接示例。

| 设置 | 干什么 | 不写会怎样 | 示例 |
|---|---|---|---|
| `tools.code_host` | 代码托管工具:读 MR / PR 的标题、描述、讨论、目标分支和源引用。**只能是只读的**,不评论、不改描述、不合入。写了以后贴 MR / PR 链接(GitHub、GitLab 的也一样)都由它读;读到的东西插件会自己核对仓库、分支和提交,主机或仓库对不上就停止;工具读取失败才从同一 origin 拉代码,并写明「MR 信息没有读到」 | GitHub 用 gh、GitLab 用 glab;都认不出的平台只能审本地分支 | `用 acme-kit:mr-reader 读 MR,链接形如 https://code.example.com/x/y/merge/12` |
| `tools.requirement` | 需求管理工具:读需求单(标题、描述、验收标准) | 不处理需求单:不问、不读,你主动给的链接只记下 | `用 acme-kit:ticket-reader 读需求单,链接形如 https://tickets.example.com/browse/XX-123` |
| `tools.doc_reader` | 文档阅读工具:读 PRD、技术方案等文档链接 | 不处理文档:不问、不读,你主动给的链接只记下 | `用 acme-kit:doc-reader 读文档链接,支持 https://docs.example.com/ 下的页面` |

写在一行里,值里不要出现「空格加 #」(行尾的 ` # ...` 会被当成注释截掉)。

**其他设置**

| 设置 | 作用 |
|---|---|
| `gitlab_hosts` | 按 GitLab 处理的域名,逗号分隔,可以带子路径(如 `company.com/gitlab`);私有化 GitLab 的域名不含 "gitlab" 时必填 |
| `model.finder` / `model.verifier` | 查找和核实用的模型,写当前宿主认识的模型名,不写或不支持时用宿主的模型。可分别选择查找与核实模型;跨厂商核实是一种可选策略,没有证据保证一定更好 |
| `review.ask` / `describe.ask` | 各技能开始前要问的资料类别,`requirement`(需求单)、`doc`(需求文档),逗号分隔;类别要配了对应读取工具才会问。不写时 review 问 `doc`,describe 问 `requirement` |

平台只从当前 origin 推导;`--platform` / `CR_PLATFORM` 可补充未识别的平台类型,不能覆盖已识别的 origin 平台。`gitlab_hosts` 辅助识别域名和部署子路径,链接只在主机与完整仓库核对后参与类型识别。私有化 GitLab 需要事先登录对应主机。`tools.code_host` 同样在读取前核对 origin,身份不匹配直接停止。

## 成本

报告末尾有一行「消耗」:用时、启动的查找角色和 verifier 数、候选和通过的条数,以及 token 用量和会话记录里实际出现的模型名。token 在 Claude Code 和 Codex 里统计(由插件的 hook 从会话记录里读取,包含子代理),Cursor 不统计;统计不到时写明原因。只读用量数字和模型名,不读对话内容。

## 依赖和常见情况

- `git`、POSIX `sh`、**`python3`(3.8+)**。没有 python3 时一开始就会提示安装。
- GitHub PR 用 `gh`,GitLab MR 用 `glab`(都要已登录)。没有或没登录时改用 git 直接拉取代码,但拿不到标题、描述和关联需求,目标分支不是默认分支时要说明一下。
- **必须有本地仓库**。只给 MR 链接而没有本地克隆不行;不在仓库目录里时告诉它仓库在哪。
- **连不上内网 GitLab**:常见于沙箱环境,放开网络或换个环境再试,或改审本地分支。
- **明明登录了却提示没登录**:多半是登录靠 `GITLAB_TOKEN`、`GH_TOKEN` 这类环境变量,而宿主没把它传给命令。比如 Codex 的 `shell_environment_policy` 设为 `inherit = "core"` 时会过滤掉 token,从 Dock 启动的宿主也读不到只写在 `~/.zshrc` 里的变量。agent 会先说明原因,再让你选:让 `gh` / `glab` 自己保存登录(推荐)、在宿主里只放行这一个变量,或者这次先不读平台。它不会打印 token,也不会自己改宿主的全局配置。做法见 [code-host-auth.md](skills/review/references/code-host-auth.md);在那之前 review 会改用 git 直接拉取代码。
- **用自己的历史 bug 检验**:说「拿我们修过的 bug 测一下能不能抓到」,agent 会从 `git log` 挑修 bug 的提交,对引入 bug 的那次改动跑审查,再挑普通改动看误报。

## 自定义

想调整行为,直接改对应文件:阈值和评分在 `skills/review/references/scoring-rubric.md`,不该报的在 `references/false-positives.md`,各角色的关注点在 `roles/`,报告的章节顺序在 `templates/report.md`(填写规则在 `references/report-format.md`)。improve 的模板在 `skills/improve/templates/`。跑测试:`python3 -m unittest discover -s tests`。设计依据见 [DESIGN.html](DESIGN.html)。

## 已知限制

- **会漏报**:80 分门槛会挡掉一部分真实但没能在代码里完整追踪到的问题;规则检查防得了编造,防不了漏看。
- **增量按文件判断**:没变的文件依赖了这次改动的符号时会一起重看,但只按名字识别,配置、反射等间接影响可能漏掉;担心时说「重新审」。基准分支更新后重新变基,那次会退化成全量。已经按历史判断抑制的条目不会自动带入以后每轮增量。
- **影响面靠名字匹配**:依赖注入、反射、MyBatis XML、跨服务调用、再导出搜不到,同名方法会混在一起(标「同名歧义」)。
- **需求来源靠你配置的工具**:能否读到取决于工具和权限;读取发生在审查开始前。
- **运行记录只防幻觉**:声称跑过的命令要有记录,但记录本身不防刻意伪造。
- **规则冲突只靠提示**:两条规则互相矛盾时由审查角色判断并提示,脚本不检测。
- **规则沉淀仍需人工复核**:分批观察和全局归并不保证召回完整,引文与覆盖声明校验也不能证明语义正确。平台的 `resolved`、`changed_after` 独立保留,不能据此判断采纳;无法确认采纳或已有约束覆盖时标为未知/待确认。分页或缓存不完整时停止生成计划;规则共享来源无法读取时披露问题,不能宣称已核对完整。
- **同时审查同一个目标**:两次审查共用「进行中」标记,可能误报「上一次没有保存」,审查结果不受影响。describe 采集期间(几秒)会临时写入并恢复这个标记和来源记录,与同一目标正在进行的审查同时运行时,可能互相覆盖。
- **真实环境验证不足**:私有化 GitLab 子路径部署、GitHub 的 issue 和评论读取主要用模拟的 `glab` / `gh` 测过;判断记录只在本机。`tools.code_host` 只用本地仓库模拟过。
- **代码托管工具靠约定只读**:`tools.code_host` 由 agent 执行,插件看不出远端的 MR 有没有被改过,只能靠配置和说明里「只读」的约束;读到的标题、描述和讨论也只是 agent 转述的,插件只核对得了仓库、分支和提交。
