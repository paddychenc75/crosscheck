# crosscheck

高信噪比的 AI code review。同一套流程可在 Claude Code、Cursor、Codex 中运行。

核心思路:**宁缺毋滥**。先尽量把可疑的地方找出来,每条候选再由一个没看过推理过程的 verifier 独立核实、给出依据并打分,低于 80 分的不展示。没有问题时就说没有问题。

机制刻意保持简单,只留业界验证过有效的几条:先找后核实、只报高置信度的、依据由脚本校验、规则就是仓库里的 Markdown、用合并时问题有没有真的解决(采纳率)衡量效果。

除了找 bug 和安全问题,它还能对照需求单和计划检查是否做到了需求,对照团队写下的规则检查规范,并把你对每条发现的判断记下来,同一段代码不再重复报同样的误报。

一次审查产出两份东西:

| | CR 报告 | MR 说明 |
|---|---|---|
| 给谁看 | 开发者自己,照着修 | MR 评审人,开发者贴进 MR 描述 |
| 内容 | 核实过的问题、修复建议、依据 | 需求单和需求文档链接、一句话、请重点看、阅读顺序、影响面、需注意的改动、可能相关的测试、CR 情况 |
| 性质 | 结论,逐条独立核实 | 事实和链接,由脚本生成或核对,不下结论 |

另外有一个 `cr-rules` skill:从最近一个季度已合并 MR 的人工评论里沉淀规则,列出候选让你挑。只有 cr 能用自然语言触发;`cr-rules` 必须用命令调用(Claude Code 里 `/crosscheck:cr-rules`,Codex 里 `$cr-rules`,Cursor 里 `/cr-rules`),不会被一句话误触发。


## 安装

建议以**插件**方式安装:插件带 hook,审查期间会拦截改动仓库的命令,并统计 token。拷贝安装只有 skill,没有这层保护。

crosscheck 通过插件市场分发,本仓库只提供插件本体和三家的插件清单(`.claude-plugin/plugin.json`、`.codex-plugin/plugin.json`、`.cursor-plugin/plugin.json`),都按各家官方文档编写。把它加进你们的插件市场后,按各宿主的方式安装:

| 宿主 | 安装 | 调用 | 注意 |
|---|---|---|---|
| Claude Code | `claude plugin install crosscheck@<市场名>` | `/crosscheck:cr` | 装好后新开会话 |
| Codex | `codex plugin add crosscheck@<市场名>`,或在插件目录里安装 | `$cr`(可能显示为 `crosscheck:cr`) | **装好后运行 `/hooks`,审阅并信任 crosscheck 的 hook**。Codex 不会自动信任插件自带的 hook,没信任时只读拦截和 token 统计都不生效;升级插件后 hook 文件变了,要重新信任 |
| Cursor | 在插件设置里添加市场后安装 | `/cr` | Cursor 的 hook 不提供用量,不统计 token |

都可以不加前缀,直接说「review 一下」。

### 拷贝安装(没有 hook)

克隆仓库,把 `skills/cr/` 整个目录拷到对应 agent 的 skills 目录下;要用规则沉淀,把 `skills/cr-rules/` 也拷到同一个目录下(它复用 cr 的脚本):

```
git clone https://github.com/paddychenc75/crosscheck.git
```

| 宿主 | 拷贝到 | 生效范围 |
|---|---|---|
| Claude Code | `~/.claude/skills/cr/` | 所有项目 |
| Claude Code | `<项目>/.claude/skills/cr/` | 仅该项目 |
| Cursor | `~/.cursor/skills/cr/` | 所有项目 |
| Cursor | `<项目>/.cursor/skills/cr/` | 仅该项目 |
| Codex 及其他支持 SKILL.md 的 agent | `~/.agents/skills/cr/` | 所有项目 |
| Codex 及其他支持 SKILL.md 的 agent | `<项目>/.agents/skills/cr/` | 仅该项目 |

以 Claude Code 为例:

```
mkdir -p ~/.claude/skills
cp -R crosscheck/skills/cr ~/.claude/skills/cr
```

拷贝后重启会话,用 `/cr` 调用。

- **更新**:在克隆的目录里 `git pull`,然后重新拷贝一次(先删掉旧的 `cr` 目录)。也可以改用软链接:`ln -s "$(pwd)/crosscheck/skills/cr" ~/.claude/skills/cr`,之后只需要 `git pull`。
- **没有 hook。** 审查流程、记录、增量和出报告前的状态核对都正常,只是审查期间不会主动拦截危险的 git 命令和会显示凭证的操作。报告末尾会写「只读拦截:没有检测到」。
- **不要同时装两份。** Cursor 也会读 `~/.claude/skills`,在那里拷贝过又装了插件,会出现两个 cr。

## 怎么用

直接用平时说话的方式提要求,不需要记参数。在 Claude Code 里用 `/crosscheck:cr`(拷贝安装时是 `/cr`),Cursor 是 `/cr`,Codex 是 `$cr`;不加前缀直接说"review 一下"也可以。说"cr 帮助"会列出常用说法。

报告的第一行写明这次审查了什么(范围、深度、全量还是增量),看到的范围不对时可以直接说。

### 审查

| 想做什么 | 可以这样说 | 简写 |
|---|---|---|
| 审当前分支的全部改动(含未提交的) | "review 一下""帮我看看这次的改动" | `/cr` |
| 审另一个分支(不用切过去) | "看看 feature/pay 分支" | `/cr feature/pay` |
| 审一个 PR / MR | "review MR 128",或直接贴链接 | `/cr 128`、`/cr <URL>` |
| 审某几个提交 | "看看最近 3 个提交" | `/cr A..B` |
| 只看某个目录 | "只看 src/orders 下面的改动" | `/cr src/orders` |
| 快速过一遍 | "快速看一下"(只查 bug、安全和需求,最多 5 条,不启动子代理) | `--depth quick` |
| 上线前仔细审 | "仔细看看""上线前深度审一下"(更慢、更贵) | `--depth deep` |
| 只关心某一方面 | "只看安全问题""只对照一下团队规范" | `--only bug,security,rules` |
| 顺便看看能不能简化 | "顺便看看有没有能简化的"(默认不查) | `--only bug,security,rules,simplify` |
| 告诉它改动的目的 | "这次是为了修复分页丢数据" | `--intent "…"` |
| 告诉它方案在哪 | "方案在 docs/plan.md" | `--plan docs/plan.md` |
| 换一个核实用的模型 | "核实换成某某模型" | `--verifier-model <模型>` |
| 测试也一起看 | "测试也一起看" | `--with-tests` |
| 从头完整审一遍 | "重新审""全量""忽略之前的" | `--full` |
| 审完顺手修掉 | "审完把问题修掉" | `--fix` |

- 不带 `--fix` 时不改任何文件。"review 一下""这个该怎么修"都不算修改请求。
- `--depth deep`:多一个 reviewer 从调用方、影响面往回查一遍,减少遗漏;verifier 会尝试写最小的脚本复现 bug,也可以跑项目已有的类型检查和测试。成本和耗时更高。
- 没指定深度时按 standard 跑。如果这次风险高(命中 `risk_paths`、包含数据库迁移、改动超过 800 行、有测试或检查被削弱,或者改动超过 300 行且涉及鉴权、资金相关的文件),会建议改用 deep,但只是建议,不会自己换。
- 审查结果只在本地输出。插件不会往 PR/MR 发评论,也永远不会 approve、request changes 或 merge。

### 审查之后

直接回复就行,用报告里的编号指代发现。

| 想做什么 | 可以这样说 |
|---|---|
| 表态(会被记下来) | "1 对,2 误报:上游已经重试""3 先不改:下个版本" |
| 质疑某条 | "第 2 条不对吧"(会重新读代码核对,成立就解释,站不住就撤回并记录) |
| 修复 | "把第 1、3 条修掉" |
| 看没报的 | "还有别的吗""70 多分的那些是什么" |
| 指出漏报 | "你漏了 cache.ts 的并发问题" |
| 单独深挖 | "cache.ts 用 deep 再看一遍" |
| 定规则 | "以后这种别报了""以后都要检查 X" |
| 改完再看 | "再看一下"(同一目标自动做增量) |

### 维护

这些都在审查之外、由你发起。不会往 GitLab / GitHub 写任何东西;要改规则文件时先给你看,确认后只改工作区。

| 想做什么 | 可以这样说 |
|---|---|
| 看审查效果和采纳率 | "看看 review 的效果" |
| 从 MR 里沉淀规则 | 命令 `/crosscheck:cr-rules`(Codex 里 `$cr-rules`,Cursor 里 `/cr-rules`),可以带上天数,如 `/crosscheck:cr-rules 30 天`。不能用自然语言触发 |
| 检查规则还好不好用 | "检查一下我们的规则" |
| 用修过的 bug 检验效果 | "拿我们修过的 bug 测一下能不能抓到" |

### 目标的写法

| target | 含义 |
|---|---|
| 省略 | 当前分支相对对比基准的改动,加上未提交和未跟踪的文件 |
| 分支名 | 该分支相对对比基准的改动,不需要先切过去 |
| `A..B` | 指定 commit 范围 |
| 路径 | 只看该路径下的本地改动 |
| 数字或 URL | GitHub PR / GitLab MR |

另外有 `--repo <目录>`(从仓库目录之外运行)、`--base <分支>`(对比基准:本地分支默认对比默认分支,从 develop、release 拉出的分支用它指定;PR/MR 只在读不到目标分支时用)、`--platform github|gitlab`(强制指定平台)。

对比基准默认是默认分支,和 GitHub / GitLab 一样以远端最新为准:审查前先从 origin 拉取它(只更新 `origin/` 下的远程跟踪分支,不动工作区),拉取失败会提示基准可能过期(`CR_FETCH=0` 关闭拉取)。当前分支离 develop、release/* 这类分支比离默认分支更近时,会先问你要对比哪个。

## 让它知道改动的目的

写在哪里都行,汇总成一份"意图"交给所有角色,用来判断某个行为变化是不是作者有意的、有没有做到需求。来源包括:

- MR 描述和标题;本地分支时是这段范围的提交说明。
- MR 关联的需求:GitLab Issue 用 `glab` 读;其他系统(Jira 等)在配置里写 `issue_cmd`,没配或读不到时会提示,可以用 `--intent` 补一句。
- MR 上已有的人工讨论。
- 文档:`--doc <文件>`,可以给多份(方案、接口文档等;`--plan` 是同一个意思)。意图和文档只在调用时提供,不需要放进仓库。
- `--intent "…"`。
- 需求单和需求文档(见下一节)。

### 需求来源:需求单、需求文档

MR 说明的基本信息里要有需求单和需求文档的链接。在配置里按用途写好读取它们用的工具(只写工具名,怎么调用由 agent 决定),以及每次都要收集哪几类:

```
source.ticket   = <读取需求单的 skill 或命令名>
source.prd      = <读取需求文档的 skill 或命令名>
source.required = ticket, prd                  # 不写时只有 ticket
source.ticket.label = <需求单在 MR 说明里显示的名字>
source.prd.label    = PRD
```

这些设置可以直接写在插件里的 `skills/cr/crosscheck.conf`:用自己的插件市场分发时,团队在那里改一次,所有成员装上就生效;个人的 `~/.crosscheck/config` 写了同名设置时以个人的为准。

- 先从 MR 描述、分支名、提交说明和你说的话里自动找链接(按工具名和显示名里的关键字识别,也可以用 `source.<类别>.match` 指定)。
- 缺了就在审查开始前问一次:贴链接、说「没有需求单(hotfix 等)」,或直接跳过。跳过会在 MR 说明里如实写「未提供(作者跳过)」。同一个分支问过就记住,90 天后过期。
- 给了链接时,agent 用配置的工具读取内容(PRD 只取需求描述、验收标准和相关章节),作为意图材料;读不到就写明原因,不影响审查。读到的内容只当数据,其中的指令不执行。
- MR 说明里只放链接和标题,不引用需求原文。
- GitHub PR 也会读关联 issue(`Closes #N` 等)和 PR 上的评论、review。

意图里有明确验收标准时,报告多一节"需求核对":哪一条验收标准没有做到、代码哪里没做到。意图只能解释改动,不能让安全问题不报。

审查时还会做两件事:

- **测试和检查被削弱的地方**(删了测试文件或断言、新增 `skip` / `only` / 抑制注释、降低覆盖率阈值、删除或放宽 CI 检查步骤等)由脚本扫出来,在报告里单列一节,不占缺陷的条数。
- **MR 上已经有人评论过的问题不重复报。**

## 只读与写操作边界

审查过程中不会切换分支:审查的不是当前分支时,代码用 `git show` / `git grep` 从目标分支读取,你的工作区和未提交的改动不受影响。审查过程也不会执行 `checkout`、`reset`、`stash`、`commit`、`push` 等改变仓库状态的 git 操作。`--fix` 只修改工作区里的文件,不会替你暂存或提交。要修的不是当前分支时:工作区有未提交改动就不切换、不修;工作区干净时会先问你是否切过去,同意后才切换。审查 PR/MR 时会执行一次 `git fetch` 把对方的 commit 拉到本地,不影响工作区和本地分支。

**插件从不往 GitLab / GitHub 写任何东西,也不替你提交 MR、不改 MR 描述**:MR 说明由你自己贴,插件只给出可复制的 `glab` / `gh` 命令。审查结束后只有两种写操作:你确认后把规则改到工作区里的规则文件(不提交、不推送);你同意后用配置的 `output.page` 工具生成或更新 MR 说明的网页版。

只读有两层保障:

| 保障 | 做什么 | 适用宿主 |
|---|---|---|
| 拦截 | 审查进行期间,直接拒绝 `git checkout` / `reset` / `stash` / `clean` / `add` / `commit` / `push` 等命令、`gh` / `glab` 的写操作,以及对仓库内文件的编辑。主 agent 和子代理都受限 | Claude Code、Codex、Cursor(通过各自的 hook) |
| 核对 | 审查开始时记下分支、HEAD、stash、暂存区和每个改动文件的内容哈希,出报告前对比。有变化就写在报告最前面 | 所有宿主 |

拦截只在审查进行期间生效,其余时间不影响任何命令:

- **开始**:真正执行收集改动的脚本时。只是查看、搜索、编辑这个脚本不算,所以开发或排查这个插件时不会被误当成一次审查。
- **结束**:出报告前核对仓库状态时。之后你让它提交、切分支都不受影响。
- **提前结束**:收集改动的脚本报错、发现没有可审查的内容或改动没有变化时,立刻解除;你中途发新消息时也会解除。
- **范围**:只对发起审查的那个会话有效,同一仓库里的其他会话不受影响。
- **凭证相关的拦截只针对你主目录下的文件**(`~/.zshrc`、`~/.netrc` 等)和 gh/glab 自己的配置。仓库里同名的文件,比如 dotfiles 仓库里的 `.zshrc`、项目里的 `.env.example`,照常可以读。

各宿主启用 hook 的方式:

- **Claude Code**:安装插件后自动生效。
- **Codex**:插件自带的 hook 需要在 `/hooks` 里审阅并信任,装上插件不等于信任;hook 文件变化(如升级插件)后要重新信任。没信任时 hook 不运行,只读拦截和 token 统计都不生效。
- **Cursor**:随插件安装,配置在 `hooks/cursor-hooks.json`。

没有 `jq` 也没有 `python3` 时拦截不生效,只剩核对。

## 配置文件

配置有两层:插件里的 `skills/cr/crosscheck.conf`(随插件分发,适合团队统一的设置,如需求来源和网页版工具)和个人的 `~/.crosscheck/config`(逐项覆盖插件里的)。每行一个 `key=value`,`#` 开头是注释。用 `sh <skill_dir>/scripts/config.sh path` 查实际位置;环境变量 `CROSSCHECK_CONFIG` 可以改位置。示例见 `skills/cr/templates/config.example`。

| 设置 | 作用 |
|---|---|
| `gitlab_hosts` | 按 GitLab 处理的域名,多个用逗号分隔,可以带子路径(如 `company.com/gitlab`)。私有化 GitLab 的域名不含 "gitlab" 时必填 |
| `issue_cmd` | 读取非 GitLab 需求单的命令,`{key}` 替换成编号,如 `jira issue view {key} --plain` |
| `model.finder` | 查找角色用的模型,可以用更便宜的。不写就用宿主当前的模型 |
| `model.verifier` | 核实用的模型,最好和查找用的不同(两者的盲区不同)。调用时说"核实换成某某模型"会覆盖它 |
| `source.<类别>`、`source.required`、`source.<类别>.label`、`source.<类别>.match` | 需求来源,见「需求来源」一节 |
| `output.page` | 生成和更新 MR 说明网页版用的 skill 或命令名。不写就只生成本地文件 |

模型名要写当前宿主认识的名字(`sonnet`、`opus` 是 Claude Code 的写法;Codex、Cursor 写各自的模型名)。宿主不支持给子代理指定模型时,照常用宿主的模型运行,报告的「已检查」一行会写明配置了什么、实际由宿主决定。

平台(GitHub 还是 GitLab)按这个顺序判断:`--platform` → 环境变量 `CR_PLATFORM` → 配置的 `gitlab_hosts` → `REVIEW.md` 头部的 `platform` → 域名含 `github.com` 或 `gitlab` → 链接里的 `/pull/`、`/merge_requests/`。判断不了时会告诉你该怎么设。

私有化 GitLab 需要先 `glab auth login --hostname <域名>`。

## 项目规则

规则就是仓库里的 Markdown 文件,不需要编号、元数据或专门的格式。**`REVIEW.md` 是可选的**:团队已有的 `CLAUDE.md`、`AGENTS.md` 等直接就能用,只有想专门调整审查时才需要写;一条规则都没有也照常工作,只是没有"规范"一节。

### 规则从哪里来

越具体的越先:

| 来源 | 说明 |
|---|---|
| 子目录里的 `REVIEW.md` | 只对该目录下的改动生效 |
| 仓库根目录的 `REVIEW.md` | 项目的审查约定 |
| 给 coding agent 的约定文件 | 不需要为本插件重写,见下表 |

| 来源 | 文件 |
|---|---|
| Claude Code | `CLAUDE.md`(各级目录)、`.claude/CLAUDE.md`、`.claude/rules/*.md`(按 `paths`) |
| Codex / 通用 | `AGENTS.md`、`AGENTS.override.md`(各级目录) |
| Cursor | `.cursor/rules/*.mdc`(`alwaysApply` 或 `globs` 命中改动文件)、`.cursorrules` |
| GitHub Copilot | `.github/copilot-instructions.md`、`.github/instructions/*.instructions.md`(按 `applyTo`,`excludeAgent: code-review` 的不用) |
| 其他 | `GEMINI.md`、`.windsurfrules`、`CONVENTIONS.md` |
| 沉淀的规则 | `.agents/rules/**/*.md`(按 frontmatter 的 `paths` 或 `globs`;`cr-rules` 写到这里) |

- 只有范围覆盖本次改动文件的规则才生效。
- 约定文件里的操作说明(怎么跑测试、用哪个包管理器)不会被当成 review 规则,只采用能对照代码检查的条目。
- **从哪一版读规则**:审查 PR/MR、其他分支或提交范围时,从 base 那一版读,所以 PR 改不了审查用的规则;审查自己当前的分支时读工作区,改了规则马上生效。

### 规则发现怎么保证可信

`rules-auditor` 自己读 `rules.txt`。每条规则发现必须写出规则所在的文件和逐字引用的原文,脚本核对原文确实出现在那份规则里、那份规则覆盖这个文件,对不上的直接作废;之后再由 verifier 独立确认改动的行确实违反了它。模型不能凭空编出一条规则来报。

### REVIEW.md 怎么写

`REVIEW.md` 放在项目仓库里(根目录,或只对某个子目录生效时放在该子目录),由项目自己维护。头部(`---` 之间)是审查设置,**由脚本执行**;正文是规则和写给审查的说明。模板见 `skills/cr/templates/REVIEW.md`。

```markdown
---
skip: ["src/gen/**"]                 # 不审查的路径
limits: { minor: 3 }                 # 条数上限
risk_paths: ["src/payment/**"]       # 改动命中时建议用 deep
---
# Review 约定

## 严重程度

只有会导致行为错误、数据泄漏或无法回滚的问题才算重要及以上:
逻辑错误、没有限定租户的查询、日志里的个人信息、不向后兼容的迁移。
风格、命名、重构建议最高为轻微。

## 每次都要检查

- 新增的 API 路由必须有集成测试。原因:路由是对外契约。
- 数据库查询必须限定在调用方的租户内。原因:曾经出过越权。

## 不要报

- 生成的 protobuf 代码里的命名问题。
```

头部设置:

| 设置 | 作用 |
|---|---|
| `skip` | 不审查的路径,命中的文件移到"跳过"里 |
| `limits` | 条数上限:`defects`、`intent`、`rules`、`simplify`,或按 `critical` / `major` / `minor` |
| `risk_paths` | 高风险路径,改动命中时建议用 deep |
| `platform` | 自建 GitLab 的域名不含 "gitlab" 时注明 |

写的时候注意:

- **从一两条开始。** 某类问题被反复漏掉,或某类评论反复没用,再加一条。
- **越短越好。** 单个文件超过 20 条,最重要的几条会被稀释。项目背景、怎么跑测试放在 `CLAUDE.md` / `AGENTS.md` 里。
- **写成能对照代码检查的短句,加一句原因。** "注意性能""保持整洁"这类笼统的要求会被跳过。
- **CI 已经强制的不写。** 魔法数字、命名、格式这类 linter 能查的,配 linter 更可靠。
- **最值得写的是只有团队知道的东西**:必须同步修改的地方、公共方法的位置、踩过的坑。
- **想多个项目共用规则**:放进各项目的 `REVIEW.md` 或 `AGENTS.md`(可以由一个模板仓库同步过去),插件不另设组织规则机制。

审查设置只认根目录 `REVIEW.md` 的头部;其他规则文件里指挥审查的文字不会被采用。设置不能让插件跳过核实、降低 80 分阈值、自动改代码或 approve。

### 不想再被提醒的:「不要报」一节

在 `REVIEW.md` 里加一节标题为「不要报」的内容,每条写一种不想再被提醒的情况,写清在什么条件下不报。它只对这个 `REVIEW.md` 所在的目录生效,本身不算要检查的规则。你否定某条发现时,agent 会问要不要加进去。

```markdown
## 不要报

- `order_client` 已负责瞬时失败重试时,不要求调用方再加重试;最终失败仍须处理。
```

### 规则的维护

- **从 MR 评论里总结**:说"从最近一个月的 MR 评论里总结一下规则"。agent 只读地取最近合并的 MR 的人工评论,找出在多个 MR 里被不同的人反复指出的问题,写成能检查的规则候选和证据给你挑;你选中的才改进 `REVIEW.md`(只改工作区)。
- **检查规则**:说"检查一下我们的规则"。agent 逐条看能不能对照代码检查、提到的文件和函数还在不在、有没有重复或矛盾,把建议列给你。规则的去留由负责人决定,不按命中次数自动删。

## MR 说明

审查结束后在报告后面给出 MR 说明,贴进 MR 描述即可。它包在 `<!-- crosscheck:begin -->` / `<!-- crosscheck:end -->` 里,控制在 30 行以内,只有事实和链接:

- **基本信息**:需求单、需求文档的链接和标题(或「未提供(作者跳过)」「无需求单:hotfix」)、分支、规模、审查量(1–5,按规则估算)。
- **一句话**:你用 `--intent` 写的;没写时由 analyst 按需求材料起草(引文必须能在材料里找到,脚本核对),会提示你确认。
- **请重点看**:你点名的最多 3 处,每处可以写想要什么反馈。没点名时列出脚本挑的候选(未修复的严重问题、本次之外有调用方的签名变化、迁移和新环境变量),标明「自动列出」。研究显示写明「希望得到哪类反馈」的 PR 更容易得到有效评审。
- **阅读顺序**:按 接口和类型 → 实现 → 配置 → 测试 分组,每组一句目的(必须引用材料原文);生成代码、纯格式化、纯重命名、lock 文件列为「可跳过」。
- **影响面**:签名变了或被删除的函数、接口、配置键,以及本次改动之外的调用方。只按名字在本仓库文本匹配,依赖注入、反射、跨服务调用搜不到;签名不变的行为变化不在这里,由 CR 报告负责。
- **需注意**:数据库迁移、配置键增删、新环境变量、依赖变化。
- **测试**:你写的「怎么验证的」(`--tested`),以及可能相关的测试文件(未执行)。
- **CR 情况(作者本地运行)**:已修复几条;未修复的严重和重要问题逐条列出,附你的判断和理由,没表态的标「未表态」;轻微的只给数量。写明基于哪个提交,之后又有提交时会标出来。
- 最后一行请评审人回复「有 / 无 / 有误」,用来衡量这份说明有没有用。

不写已实现、已覆盖、无风险这类结论,不画图。仓库有 MR 模板(`.gitlab/merge_request_templates/`、`.github/pull_request_template.md`)时按模板的标题填,模板里需要你自己写的几节放在标记之外,重新生成时不会被覆盖。提交推送到远端之后,代码位置会带上 GitLab / GitHub 的行链接。

另有一份完整版 `mr.html`(全部调用方、代码块、验收标准对应的改动、全部未修复问题)。配置了 `output.page` 时,第一次会问要不要生成网页版,同意后用那个工具发布,描述里多一行「完整版」链接;之后 CR 报告一更新(重新审查、表态、`--fix`),MR 说明和网页都会跟着更新,链接不变。

## 报告长什么样

- **第一行**:审查范围、深度、全量还是增量。接着一行写意图取自哪些来源。
- **概览表**:每条缺陷和需求核对一行,列出严重程度、维度、位置和摘要。
- **逐条发现**,标题标明怎么确认的:**已复现**(deep 下实际运行并由 hook 见证)、**已复现(自报)**(有运行记录但没有加载 hook)、**读代码推断**。AI 声称跑过但没有运行记录的,按读代码推断处理并降分。每条包含:
  - 位置:`文件:行号`。
  - 问题代码:从被审查的那一版代码里摘出的原文,带行号,出问题的那一行有标记。
  - 问题:具体的输入或状态会导致什么错误结果。
  - 修复建议:能确定时给出 diff 形式的替换代码,否则用文字说明。会改变接口或行为的修复附兼容性说明。
  - **依据**(默认折叠):核实时读过的代码位置、排除了哪些可能、复现结果(deep)、哪些角色查到了。
- **需求核对**:没有做到的验收标准。
- **规范**:违反团队书面规则的问题,逐字引用规则原文和出处。同一条规则在一个文件里违反多处只报一条。
- **可简化**:只在你要求时才有,只列位置和建议,最多 5 条。
- **测试和检查被削弱**:脚本扫出来的,单独列出。
- **已按历史判断忽略**(折叠):因为你以前的判断而没报的发现,可以展开核对。
- **末尾说明**:风险等级和建议深度、用了哪些规则文件、规则相关提示(可能过时、冲突、格式有误)、跳过了多少文件、查了哪些维度、消耗、怎么快速表态、报告文件的链接。

报告是 Markdown,直接显示在对话里,同时存一份到用户目录。审查结束时会用系统默认程序自动打开这份报告,对话里的报告末尾也有一行可点击的 `file://` 链接指向它。

- 不想自动打开:设置 `CROSSCHECK_OPEN=0`。
- 想用指定的程序打开:设置 `CROSSCHECK_OPEN_CMD`,例如 `code` 或 `cursor`;或者直接改系统里 `.md` 文件的默认打开方式(macOS:访达里选中一个 `.md` 文件 → Cmd+I → 打开方式 → 全部更改)。第一次自动打开时,报告末尾会提示一次怎么改。
- 通过 SSH 连接、在 CI 里、或 Linux 上没有图形界面时不会自动打开,只给链接。

### 核实与打分

- verifier 必须给出依据:读过的代码位置、排除了哪些可能,deep 下还有复现结果。
- 脚本会核对依据里的位置在被审查的那一版里真实存在;位置不存在、或根本没给依据的,分数最高 50。
- 规则发现的出处和引用原文也会核对,对不上的作废。
- 低于 80 分的不展示,存进这次记录的 `rejected.json`。问"还有别的吗"时可以从里面列出 70 分以上的。

## 记录与增量审查

记录的目录结构:

```
~/.crosscheck/reviews/<项目名>/
├── feedback.jsonl           你对发现的判断(项目级)
├── adoption.jsonl           MR 合并后问题是否真的解决了
└── <目标>/
    ├── 20261009-143000/
    │   ├── report.md        报告全文
    │   ├── findings.json    本次结束时仍然成立的发现
    │   ├── rejected.json    没通过核实的候选(带分数和理由)
    │   ├── hashes.txt       每个文件 diff 的哈希
    │   └── meta.txt         目标、commit、深度、时间、消耗等
    ├── latest               最近一次审查的目录名
    └── baseline             增量审查所依据的那一次
```

`<项目名>` 取自 `origin` 远程地址的最后一段(如 `gitlab.example.com/group/shop-api` 就是 `shop-api`),没有远程时取主工作区的目录名。同一个项目的各个 worktree、不同位置的克隆都落在同一个目录下,分支和 MR 的记录也放在一起。恰好有另一个同名的项目时,后来的那个会在目录名后面加一段哈希来区分。

`<目标>` 是 `branch-<分支名>`、`pr-<编号>`、`mr-<编号>` 或 `range-<范围>`。不管你在不在那个分支上、在哪个 worktree 里,同一个分支用的是同一份记录。用环境变量 `CROSSCHECK_HOME` 可以改存放位置。记录不在仓库里,不会被提交;报告里会引用代码片段,注意这个目录的访问权限。

**同一个目标再次审查时默认做增量**:

- 按文件比较 diff 的哈希。没变的文件不再看,上次在这些文件里的发现原样带过来。
- 变了的和新增的文件重新审。上次在这些文件里的发现会重新核实,分成"遗留"和"已解决"。
- 报告开头会写明这是增量审查、跳过了多少文件,发现分成"新发现""上次遗留""已解决"三段。
- 未提交的改动同样算在内,哈希是按实际内容算的。

**什么时候不做增量**:

- 你说"重新审""全量""忽略之前的",或带 `--full`。
- 这次的深度比上次高(上次 standard,这次 `--depth deep`)。反过来可以:deep 之后的 standard 会做增量。
- 上次用了 `--only`:只查部分维度的审查会存记录,但不会成为增量的基准。
- 换了目标:另一个分支、另一个 PR,或同一分支上指定了不同的范围。

## 只审有效代码

审查只针对真正会在产品路径上执行、并且改变了行为的代码。

**整个文件不审的**(由脚本过滤,报告末尾会列出各类跳过了多少):

| 类别 | 例子 |
|---|---|
| 测试 | `tests/`、`__tests__/`、`e2e/`、`testdata/` 目录;`*_test.go`、`test_*.py`、`*.test.ts`、`*.spec.tsx`、`*Test.java`、`*_spec.rb` 等 |
| 日志 | `*.log`、`logs/` 目录、`nohup.out` |
| 产物 | 覆盖率报告、`*.bak` / `*.tmp` / `*.pyc`、`.idea/`、`.vscode/` |
| 原本就过滤的 | lock 文件、生成代码、vendored 代码、二进制文件 |
| `REVIEW.md` 的 `skip` | 项目自己指定的路径 |

想连测试一起审,加 `--with-tests` 或直接说"测试也看一下"。测试不审,但审查时仍会读它来了解代码的预期行为;测试被削弱的情况另外扫描并单列。

**文件里不当作问题的**:

- 只改了注释、文档字符串、空行或排版的地方(缩进有语义的语言除外)。
- 原样移动或重命名的代码。
- 被注释掉的代码、遗留的调试代码。
- 没有被用上的代码里的"bug":没有调用方、没被注册或导出、所在条件恒为假。要求简化建议时,这类代码会作为"新增了但没用上"出现在可简化一节。

规范违规单独列出,带有针对同一规则的抑制注释(`eslint-disable-next-line`、`nolint`、`noqa` 等)的地方不报;现有代码大量反着写的规则会被提示"可能过时"。

## 审查维度

| 维度 | 查什么 |
|---|---|
| `bug` | 逻辑错误、边界、空值、并发、错误处理、资源泄漏、API 误用 |
| `security` | 注入、鉴权/越权、密钥泄漏、不安全反序列化、SSRF、路径穿越等,要求给出攻击路径 |
| `intent` | 需求核对:没有满足意图里明确的验收标准 |
| `rules` | 违反项目自己写下的规范,必须引用规则原文 |
| `simplify` | 可复用已有代码、重复、过度设计。默认不查,要求时单独列出,最多 5 条 |

不报风格、命名、可读性、日志措辞和影响很小的性能优化:这类建议很少有人去改,却会冲淡真正的问题。

## 你的判断会被记住

审查后你对某条发现表态,比如"这条不对""知道了但不改""确实是个问题",agent 会把判断连同原因记下来:

- **对整个项目有效。** 在分支上判过的,换成 MR 或 commit 范围审查同一段代码时同样生效。
- **代码没变就不再报,代码变了会重新评估。** 判断记着那段代码的样子(出问题的那一行加上下各两行);代码改了之后如果问题仍然成立,会重新报告,并注明之前的判断和这次为什么又报。
- **不会悄悄删掉。** 因为历史判断而没报的发现,报告里有一个折叠的"已按历史判断忽略"列表,可以展开核对。
- **否定时要说原因。** agent 会问你为什么;有充分证据的长期误报模式可以提出有范围、有条件的忽略候选，不按出现次数自动生效。
- agent 自己撤回的发现也会记录;用 `--fix` 修好的会自动记为成立。

## 审查效果统计

说"看看 review 的效果",会先更新采纳情况,再分几个维度给出结果,互不折算。最重要的是**采纳率**:报过的问题,在 MR 合并时是不是真的被解决了。

| 维度 | 内容 | 用来回答 |
|---|---|---|
| 判断 | 成立、成立但不修、不成立、有争议、未表态 | 报出来的东西对不对 |
| 采纳 | MR 合并后,报过的问题在最终代码里是否真的解决了 | 有没有被采纳 |
| 去向 | 仍在、代码已改、代码没变但不再报、文件已不在改动里 | 代码层面发生了什么 |
| 校准 | 不同置信度区间里有人判断过的发现,实际成立的比例 | 打分有没有区分度 |
| 差一点通过 | 没通过核实的候选的分数分布,尤其是 70–79 分 | 80 分的门槛是不是太严 |

- 采纳由 `adoption.sh` 判断:只读拉取已合并 MR 的最终代码,那段代码原样还在算"没采纳";文件已删除的不计入;代码改了的交给 `judge` 确认问题是否真的解决。需要 `glab` 或 `gh`,没有时看 MR 的最后一个提交是否已进入目标分支。
- "代码已改"不等于被采纳,改动可能和这条发现无关;"代码没变但不再报"多半说明这条发现不稳定。
- 成立率和采纳率只按有明确结论的发现计算,并标出样本数;**样本不足 10 条时只给数量,不给比例**。人更倾向于标记错的,所以未表态越多,成立率越不可靠。
- 另外给出各深度的平均用时和 token。
- 统计只给人看,不会自动改变审查行为。要调整就写进 `REVIEW.md`。

## 审查的成本

每次审查结束,报告末尾会有一行"消耗",同时记进这次审查的记录里:

- **用时、启动的查找角色和 verifier 数、候选条数和通过条数。** 三个宿主都有。
- **token 用量。** 由宿主的 hook 从会话记录里读取,所以只有以插件方式安装(带 hook)、并且 hook 真的在运行时才有。插件不会为了统计去猜或扫描其他会话的记录。统计不到时,报告里会写明原因:
  - 「hook 没有运行」:拷贝安装(没有 hook),或者在 Codex 里还没有信任插件的 hook。Codex 装上插件并不等于信任它的 hook,没信任的会被跳过,这时只读拦截也不生效;在 Codex 里运行 `/hooks`,审阅并信任 crosscheck 的 hook 即可,hook 文件变化(如升级插件)后要重新信任;
  - 「hook 在运行,但……」:宿主没有给出会话记录,或者记录的格式变了,读不到用量。

  各宿主的来源:

  | 宿主 | 来源 | 范围 |
  |---|---|---|
  | Claude Code | 会话记录里每次模型调用的用量,加上子代理的记录 | 审查开始到保存之间,包含子代理 |
  | Codex | 会话文件里的用量记录 | 审查开始到保存之间;是否包含子代理未知 |
  | Cursor | 不统计:会话记录里没有用量,hook 的官方输入里也没有 | — |

数据都存在本机,不上传:

- 最终结果在 `~/.crosscheck/reviews/<项目名>/<目标>/<时间>/meta.txt` 里,是 `duration_s`、`run_*`、`usage_*` 这些行,和报告、发现放在一起。
- 审查进行中有一个临时的状态文件在系统临时目录的 `cr-guard/` 下,只记会话记录的路径和起始位置,保存时删除。
- 只读取会话记录里的用量数字,不读取、不保存对话内容。

这些字段没有写进各宿主的正式文档,版本变化后可能读不到;读不到时这一项留空,不影响审查。

## 用自己的历史 bug 检验

各家公开的评测数字互相矛盾,最可靠的是拿自己仓库里真实修过的 bug 来测。说"拿我们修过的 bug 测一下能不能抓到",agent 会从 `git log` 里挑几个修 bug 的提交,找到引入 bug 的那次改动,对它跑一次审查,看有没有抓到;再挑几个普通改动做对照,看有没有误报。样本少时只给数量。

## 依赖

- `git`、POSIX `sh`
- **`python3`(3.8+)**:必需。规则装配、依据校验、汇总、判断记录、统计、设置解析都用它;没有时 `collect-diff.sh` 一开始就会提示安装
- GitHub PR:`gh`(已登录)。没有或未登录时改用 git 直接拉取,见下
- GitLab MR:`glab`(已登录),以及 `jq` 或 `python3`。没有或未登录时改用 git 直接拉取,见下
- 读取 GitLab Issue、MR 评论、采纳判断、从 MR 评论总结规则:`glab`(GitHub 用 `gh`)
- 只读拦截:`jq` 或 `python3`

## 前置条件和常见情况

- **必须有本地仓库。** 审查要读代码,只给一个 MR 链接而没有本地克隆是不行的。不在仓库目录里时,告诉它仓库在哪,它会用 `--repo <目录>` 运行。
- **没有 `gh` / `glab`,或没有登录。** 仍然可以审查 PR/MR:脚本会用 git 直接把它的代码拉下来,用的是仓库自己已经配置好的凭证。代价是拿不到标题、描述和关联需求,对比基准按默认分支计算;目标分支不是默认分支时,说明一下目标分支(对应 `--base <分支>`)。
- **连不上代码托管的地址。** 内网的 GitLab 在沙箱里经常解析不了。这是运行环境的限制,脚本会直接说明拉取失败的可能原因;放开网络或换个环境后再试,或者改审已经在本地的分支。
- **无法判断是 GitHub 还是 GitLab。** 在配置里加 `gitlab_hosts=<域名>`,或带 `--platform gitlab`。
- **明明登录了,却提示没登录。** 常见原因是登录用的环境变量(如 `GITLAB_TOKEN`、`GLAB_CONFIG_DIR`)写在 `~/.zshrc` 里,而 agent 的终端是非交互的,不读这个文件。脚本会识别这种情况并告诉你是哪个文件里的哪几个变量:
  - 它只检查变量名有没有出现、当前环境里有没有值,不读取也不输出任何值。
  - 识别到之后,会借你自己的登录 shell 再调用一次 `glab`;那个 shell 的输出全部丢弃,只有 `glab` 返回的 MR 信息被写进临时文件。超过 20 秒就放弃。不想要这个行为设置 `CR_USER_SHELL=0`。
  - 一劳永逸的办法:把这几个变量的设置挪到 `~/.zshenv`(zsh 的所有终端都会读),或配置到宿主的环境变量里。
- **凭证。** 远程地址里嵌着 token 的仓库很常见。脚本显示和保存的远程地址都去掉了账号和凭证;agent 被要求不打印远程地址、不读取任何凭证。审查期间,会显示凭证的操作会被直接拦截:打印环境变量、查看或 `source` shell 配置文件、读取 `.netrc` 和 gh/glab 的配置、`git remote -v`、`gh auth token` 等。
- **报告在哪。** 以报告末尾 `记录:` 一行的链接为准,位置固定在 `~/.crosscheck/reviews/` 下。

## 结构

```
skills/cr/
├── SKILL.md        编排流程
├── roles/          reviewer / rules-auditor / simplifier / verifier / analyst(MR 说明),以及 judge(采纳判断)
├── references/     发现结构、评分标准、误报清单、报告格式、报告之后的处理、维护、常用说法
├── templates/      REVIEW.md 模板、配置示例
└── scripts/        审查流程、规则、记录、统计、MR 说明、规则沉淀的脚本,以及共用的 crlib.py
skills/cr-rules/    从 MR 评论里沉淀规则(SKILL.md、roles/miner.md、agents/openai.yaml),复用 skills/cr/scripts;只能用命令调用
hooks/
├── hooks.json          Claude Code 的 hook 注册
├── codex-hooks.json    Codex 的 hook 注册(在 .codex-plugin/plugin.json 里指定)
└── cursor-hooks.json   Cursor 的 hook 注册
tests/                  python3 -m unittest discover -s tests
```

`skills/cr/` 自包含,审查流程不依赖任何宿主专属功能。宿主支持子代理时各角色并行运行;不支持时由主 agent 依次执行,流程不变。三个 `.*-plugin/plugin.json` 只是各宿主的安装清单。`hooks/` 是唯一用到宿主专属机制的部分,它只提供额外的拦截,没有它审查照常运行。

为什么这样设计,见 [DESIGN.md](DESIGN.md)。

想调整行为,直接改对应文件:阈值和评分在 `references/scoring-rubric.md`,不该报的东西在 `references/false-positives.md`,各角色的关注点在 `roles/`。

改动较大时会自动按约 1000 行一批拆开审查,每批独立进行;用环境变量 `CR_BATCH_LINES` 调整每批的行数。

测试用 `python3 -m unittest discover -s tests`,其中 `tests/bin/glab` 模拟 GitLab,`tests/bin-gh/gh` 模拟 GitHub。

## 已知限制

- **规则检查防得了编造,防不了漏看。** 报出来的规则违反都核对过原文和出处,但 rules-auditor 没报的规则,不保证每条都认真看过。
- 增量按文件判断:文件 A 没变而它依赖的文件 B 变了时,A 不会被重看。问题如果出在 B 的改动上仍然能发现;担心时用 `--full`。
- 基准分支更新后重新变基,所有文件的 diff 哈希都可能变化,那次会退化成全量。
- PR/MR 的 head commit 无法 fetch 到本地时,只能基于 diff 本身审查,深度会下降,报告中会注明。
- 读不到 PR/MR 信息(没有 `glab` / `gh` 或没登录)时,拿不到关联需求和人工讨论,意图只有提交说明。
- 私有化 GitLab 部署在子路径下时,`glab` 的 `GITLAB_HOST` 设置没有在真实环境里验证过。
- 判断记录只在本机,代表你自己的判断;团队共享常见误报靠把它写进 `REVIEW.md` 的「不要报」。
- 采纳判断里,"代码改了"的情况由 `judge` 判断问题是否真的解决,仍可能判错。
- MR 说明的影响面靠名字做文本匹配:依赖注入、反射、MyBatis XML、跨服务调用、再导出搜不到,同名方法会混在一起(标「同名歧义」);签名不变的行为变化不在影响面里。
- MR 说明里的「CR 情况」是作者本地运行的结果,贴进 MR 后作者可以改,评审人应以它写明的提交和 MR 最新提交对照。
- 读取需求单、需求文档靠 agent 调用你配置的工具,能否读到取决于工具和权限;读取发生在审查开始前,只读拦截还没生效。

### 核实完整性与重复展示

核实回复缺失、重复、分数格式错误或遗漏需要重新核实的旧发现时，汇总会停止，不能把缺回复当作已解决。补齐结果后重新汇总。

通过核实的同一问题，可由主 agent 在 `display-groups.json` 指定主编号、关联编号与理由；`report-lines.sh` 校验后生成 `report.json`，供报告合并展示。原始独立发现和编号仍保存在 `final.json` / `findings.json`，关联规则的原文及出处保留。不同根因不能因为位置相同而合并，简化建议不与缺陷混合。
