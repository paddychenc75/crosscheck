      一、设计原则

      1. 精确率优先。两条真实发现好过十条里错三条。作者看到几条错误评论后就不再认真看其余的，报告为空是正当结果。
      2. 查找负责不漏，核实负责不错。查找阶段放开去查，查到一半的也交；verifier 看不到查找时的推理，先尝试推翻、再打分，必须给出依据。
      3. 确定性的工作交给脚本。diff、行范围、规则装配、依据和规则引文校验、过滤排序、增量都由脚本完成，agent 只做判断。
      4. 规则就是文件。项目的 REVIEW.md 和已有的 CLAUDE.md、AGENTS.md、Cursor / Copilot 规则直接用，不需要编号、元数据或专门格式。
      5. 记住人的判断。表态时写下原因，同一段代码不再重复报同样的误报；团队共享的写进 REVIEW.md。
      6. 机制保持简单。只留业界验证过有效的；在有真实使用数据之前，不为“可能有用”加机制。
      7. 给评审人的只写事实。MR 说明不经核实，所以只放脚本算出或能对上原文的内容，不写“已实现”“无风险”这类结论。

      不做什么

      • 不替代编译器、类型检查器、linter 和 CI，它们能拦住的问题不报。
      • 不审查改动之外的存量代码；不报风格、命名、可读性、日志措辞和影响很小的性能优化（除非项目写成了规则）。
      • 不往 PR/MR 发评论，不 approve、request changes、merge；不提交 MR、不改 MR 描述，MR 说明由开发者自己贴。
      • 默认不改文件，只有用户明确要求时才修复，且只改工作区、不提交。
      • 不往 GitLab / GitHub 写任何东西。审查后的写操作只有两种：你确认后把规则改到工作区里的规则文件；配置了网页工具时生成或更新 MR 说明的网页版。
      • 不做组织级的规则分发、团队数据同步和评测平台。
      设计依据：这些原则从哪来
      • 精确率优先：Uber 发现开发者对低质量建议很快失去信任，整类砍掉评分最差的评论；OpenAI 接受召回略降，换取信号质量。Uber：uReview；OpenAI：A Practical Approach to Verifying Code at Scale
      • 先找后核实：Claude Code Review 由多个 agent 并行查找，再由单独的验证步骤逐条对照代码过滤误报；官方 code-review 命令要求规则违反引用原文。Anthropic：Claude Code Review；Claude Code 官方 code-review 命令
      • 确定性的交给脚本：简单的语法规则 linter 最好，LLM 补语义判断；CodeRabbit 用工具结果过滤模型的误报。Addy Osmani：Agentic Code Review；CodeRabbit：架构（沙箱、工具结果过滤误报）
      • 规则就是文件：REVIEW.md、BUGBOT.md、Copilot 指令文件都是普通 Markdown。Claude Code Review：REVIEW.md 自定义；Cursor Bugbot 文档（BUGBOT.md）；GitHub Copilot：定制代码评审（只读前 4000 字符）
      • 记住人的判断：Bugbot 从开发者的反应和回复里学习规则，CodeRabbit 把开发者的回复记成 learnings，避免同样的误报反复出现。Cursor：Bugbot 从反馈中学习规则；CodeRabbit：Learnings
      • 给评审人的只写事实：Google 要求 CL 描述写清做了什么、为什么；写明“希望得到哪类反馈”的 PR 合并几率高约 65–72%。Google：写好 CL 描述；MSR 2026：PR 描述与评审结果（8 万个 PR）

      二、总体设计

      入口在本地调用；只有审查能用平时说话的方式触发

      设计依据：总体结构

      • 生成 → 打分 → 过滤 → 去重：Uber uReview 的多阶段流水线。Uber：uReview
      • 先克隆仓库、跑工具再给模型：CodeRabbit 在沙箱里跑几十种 linter / SAST，结果既当上下文也用来过滤误报。CodeRabbit：架构（沙箱、工具结果过滤误报）
      • 两份产出：评审工具的 PR 摘要和评审指南（CodeRabbit walkthrough、Qodo /describe 与 /review）与问题清单分开展示。CodeRabbit：Walkthrough 与评审工作量；Qodo PR-Agent：/describe

      三、审查流程

      步骤谁做产出
      0. 需求来源（缺了才有）主 agent 问一次；用配置的工具读取需求单、需求文档的链接和内容；同一分支记住
      1. 收集改动collect-diff.sh（内部调用 collect-context.sh、settings.sh、feedback.sh history）diff.patch、ranges.txt、intent.md、sources.json、analysis-facts.json、weakening.txt、history.json；增量时 prev-findings.json
      2. 装配规则collect-rules.shrules.txt、rules-index.json
      3. 查找候选reviewer、rules-auditor，同时 analyst 起草 MR 说明（并行）candidates.json；analysis.json（经 analysis_check.py 校验）
      4. 核实prepare-verify.sh 分批 → verifier × Nverify/result-*.json
      5. 汇总aggregate.shfinal.json、findings.json、rejected.json
      6. 报告check-state.sh、report-lines.sh、主 agent、save-review.sh报告和审查记录；保存时同时写入 mr.md、mr.html
      6b. MR 说明mr-note.sh补充链接和网页版；表态、修复、重新审查后重新生成
      7. 修复（仅要求时）主 agent工作区改动，修好的记为成立

      对比基准

      和 GitHub / GitLab 一样，diff 从源分支与目标分支远端最新的 merge-base 算起：

      • PR / MR 用平台给的目标分支；本地分支默认对比默认分支，用户说「对比 develop」时传 --base。
      • 算之前先从 origin 拉取基准分支（只更新 origin/ 下的远程跟踪分支，不动工作区）。本机缓存过期时，别人合进 main 的提交不会被当成这次的改动。拉取失败照常审查，但提示基准可能过期。
      • 不每次都问：develop、release/* 这类长期分支比默认分支更近时，脚本输出 BASE_CHOICE，agent 才问用户要对比哪个。

      深度

      档位查找核实上限
      quick主 agent 自己按 reviewer 说明做第 1–3 遍主 agent 自己核实5 条
      standard（默认）reviewer（同一上下文分遍：正确性、安全、需求核对）、rules-auditor 并行verifier 子代理，只读代码，每批最多 3 条缺陷 10 条；需求核对、规范各 5 条
      deep同 standard，reviewer 多做一遍影响面（从使用方往回查）verifier 可以跑项目已有的类型检查和测试来复现同 standard

      改动较大时按约 1000 行一批，reviewer 和 rules-auditor 每批各跑一次。

      流程是否走完

      • 进行中标记：真正开始审查时在记录目录写 pending，保存成功后删除；下次审查同一目标时标记还在，就提示上一次没有保存、很可能提前结束，然后照常重新审查。
      • 非交互运行：没有人在场时（claude -p、codex exec、CI）必须前台启动子代理，等每个子代理的最终 JSON 都回来再进入下一步，全部返回之前不写报告、不保存记录。
      • MR 说明随保存生成：mr.md、mr.html 缺任何一个，报告里写“流程不完整”。
      • 实际用的模型：消耗行列出会话记录里实际出现的模型名；配置的查找或核实模型没有出现在记录里时，报告多一行“模型与配置不一致”。
      设计依据：查找怎么分工
      • 成本看子代理数量：宿主的提示缓存按“前缀完全相同”命中。跨子代理的读取一般吃不到缓存，所以子代理数量推高成本；同一个 agent 内多轮读取走缓存，代价小。按类别拆焦点、但放在同一个上下文里，第 2 遍以后读到的代码已经在上下文里。
      • 单 agent 自主调查：Cursor 的 Bugbot 把多路并行换成能自己决定往哪查的 agent，是他们效果提升最大的一次；OpenAI 给单个 reviewer 仓库访问和执行能力后，严重问题抓得更多、误报更少。
      • 按类别专项：Anthropic 官方 code-review 命令有专门查规则和查安全逻辑的 agent，Uber uReview 的缺陷、最佳实践、应用安全是三个助手。分遍是两者的折中。
      • 安全一遍默认开：照搬 Anthropic security-review 的排除清单，默认不报只导致服务不可用的问题、缺少限流、开放重定向、只在测试代码里出现的。
      • 规则单独查：“只认写下来的规则、必须引原文”和 reviewer 的判断标准差别最大，Anthropic、Amp、Uber、Qodo 也都单独拆出来。
      • 不报可读性和小重构：Uber 的数据显示这类建议的评分一直最差，宿主也自带 /simplify。
      • 流程不能省：用公开 PR 评测时，便宜的宿主模型常觉得改动简单就不启动子代理、自己读一遍出结论。所以 standard、deep 只要能启动子代理就必须启动，改动再小也一样；按流程走完时，干净对照基本没有误报。
      • 留标记、下次发现：会话提前结束时进程已经不在了，没有谁能事后补写“失败”；开始时写下标记、保存后删除，下次就能发现上一次没走完。非交互运行没有人在场，后台启动的子代理会在会话结束时丢掉，所以必须前台启动。
      • 实际模型从会话记录里读：宿主不支持为子代理指定模型时会照常用宿主的模型，用户读报告时只看到自己配置了什么，所以由脚本读出实际模型，对不上就提示；只读模型名，不读对话内容。
      • 查找不自己过滤：评测里漏掉的问题大多是查找阶段根本没提出来，而不是被核实否决。所以 reviewer 不读误报清单，拿不准的都交给 verifier；这和 Qodo 的多 agent 方案“先尽量找全、再统一核实”一致。

      待验证：分遍和多个子代理相比，抓到的问题和 token 变化，要在同一批改动上对比。

      四、审查角色

      1reviewer

      查正确性、安全和需求核对。先看 weakening.txt 里被削弱的测试和检查，再对照 intent.md；对每处改动读完整个函数，顺着调用方和数据流深挖。安全问题要说清可控输入从哪进、经过哪几步、得到什么。最多 15 条，查到一半的也交，写明 needs_check。

      在同一个上下文里分遍：① 正确性 ② 安全（默认不报 DoS、限流、开放重定向、仅测试代码）③ 需求核对；deep 加 ④ 影响面，从使用方往回查漏改的地方和被破坏的隐式契约。每条带 pass。改动违反了接口写明的约定、或去掉了原有的锁、事务、过滤条件、校验时，即使现在没人这样调用也要提交。只负责找、不负责判：不读误报清单，拿不准的照常提交并写 needs_check；每块改动对照 base 过一遍最常漏的几类检查点。

      2rules-auditor

      自己读 rules.txt，按 目录级 → 项目级 → 约定文件 的顺序，只用能对照代码检查的条目，只看改动的行。有针对同一规则的抑制注释不报；现有代码大量反着写时提示“规则可能过时”。

      每条违反写出 rule_file 和逐字的 rule_quote，脚本会核对。

      3verifier

      只拿到候选结论。先查历史判断（同一问题、代码没变 → 0 分），再按封顶检查尝试推翻：不在改动行、不可达、CI 会拦、命中误报清单。缺陷真实、但 base 里已以同样结果存在的，不打 0 分，标 pre_existing，过了 80 分门槛后单列在报告“改动代码里的原有问题”一节，不计入发现数、不进 MR 说明；被本次改动变得更容易触发或范围变大的，仍算本次引入。没推翻才走完场景打分。例外：本次改动破坏了接口写明的约定或原有保护时，不按“现在没人这样调用”否决，最高评为重要。

      必须给 evidence（读过的代码位置）和 ruled_out；位置不存在或没给依据的最高 50 分。每批最多 3 条，严重问题单独核实。严重程度按后果类型定（数据错误、崩溃或未处理的异常——包括正常输入稳定返回 500、现有调用方因违反约定出错、安全边界被破坏算严重），不因影响范围窄、尚未出现、措辞轻重而降级，只在后果类型判断错时调整级别；定级标准附有几条虚构的对照例子。同一根因、同一改法的多处合并为一条，其余位置列在 also_at，逐处核对；汇总时脚本再合并位置有交集（或同文件相距 5 行内）且摘要相似度不低于 0.85 的重复发现，宁可漏合并也不误合并。deep 下运行命令必须经 run-check.sh 留记录，报告标「已复现 / 读代码推断」，展示的输出取自运行日志；声称跑过但没有记录的最高 60 分。

      4analyst（MR 说明）

      和查找角色同时启动。代码分析由脚本 analysis_facts.py 先做好：改了哪些函数和接口、签名变化、本仓库里的调用方（影响面）、迁移和配置变化，按代码块编号。analyst 读这份分析、需要时看对应的 diff，再对照需求材料，起草一句话、改动分组、验收标准对应的代码块。不判断对错。

      每句必须带材料原文的引文，分组只能用脚本给的编号；analysis_check.py 核对引文、编号和禁用词，对不上的删掉。
      设计依据：角色分工
      • 并行查找 + 独立核实：Claude Code Review 多个 agent 各查一类问题，验证步骤逐条对照代码确认（如是否已有空值保护）。Anthropic：Claude Code Review
      • verifier 的执行证据：Meta TestGen-LLM 只保留能编译、稳定通过、确实提高覆盖率的测试；有 agent 跑了 0 个测试、退出码 0 就报告“全部通过”，所以执行声明要核对原始记录。Meta：TestGen-LLM（可执行的过滤器）；综述：agent 自报“测试通过”的核实
      • 原有问题单独标出：Anthropic 内部的代码审查给发现加 Pre-existing 标签：问题真实，但不是这次改动引入的，不当作作者要修的缺陷，也不丢掉。我们同样把它们和本次引入的问题分开展示。Anthropic：Solving code review at Anthropic
      • analyst 只写可核对的描述：Qodo /describe、CodeRabbit walkthrough 生成改动说明；我们要求引用原文并由脚本核对。Qodo PR-Agent：/describe；CodeRabbit：Walkthrough 与评审工作量

      五、MR 说明与需求来源

      团队问卷（约 27 人）：52% 卡在“改动太大、难以判断影响”，15% 缺需求背景，15% 缺验证手段，“意见不准”只有 4%。这不是多找几个问题能解决的，所以审查之外再给 MR 评审人一份 MR 说明，由开发者贴进 MR 描述。

      CR 报告MR 说明
      给谁看开发者自己，照着修MR 评审人
      内容核实过的问题、修复建议、依据需求链接、一句话、请重点看、阅读顺序、可跳过、影响面、需注意、可能相关的测试、CR 情况
      性质结论，逐条独立核实事实和链接，脚本生成或核对，不下结论
      去处留在本地保存记录时直接写进记录目录的 mr.md、mr.html，缺了算流程不完整；开发者复制进 MR 描述（30 行以内），或直接贴网页链接；配置了网页工具时自动发布，随 CR 报告更新
      • 事实交给脚本：analysis_facts.py 提取改了哪些函数、接口、配置键和签名变化，用 git grep 找本仓库里的调用方，标出迁移、配置、环境变量、依赖变化和可跳过的文件。表头写明能力边界：依赖注入、反射、跨服务调用搜不到；签名不变的行为变化由 CR 报告负责。
      • 请重点看由作者点名：最多 3 处，每处写想要什么反馈；没点名时列出脚本挑的候选并标“自动列出”。
      • CR 情况如实列出：严重和重要的未修复问题附作者的判断，没表态的标“未表态”；写明基于哪个提交，之后又有提交时标出。
      • 需求来源：配置三类外部工具：需求管理工具 tools.requirement、文档阅读工具 tools.doc_reader、文档发布工具 tools.doc_publisher，值是写给 agent 的一句话（用什么、怎么用、链接长什么样）；全部设置列在随插件分发的 crosscheck.conf 里、默认注释掉，个人配置逐项覆盖，缺了在审查开始前问一次（贴链接 / 没有需求单 / 跳过），同一分支记住；agent 用配置的工具读取内容作为意图材料。MR 说明里只放链接和标题。
      • 人提交 MR：插件不提交 MR、不改 MR 描述，只给出 glab / gh 命令。网页版用文档发布工具 tools.doc_publisher，写进配置就自动发布，不再逐次询问。
      • 衡量：先不做自动收集；用一段时间后直接问评审人有没有帮他找到重点，重发问卷看“难以判断影响”的比例是否下降。
      设计依据：为什么这样写 MR 说明？
      • 业界实践：CodeRabbit walkthrough 和工作量评分、Qodo /describe 与 /review（重点问题、优先看的文件）、Baz 按功能分组、Google CL 描述要求一句话写清做了什么和为什么。
      • 研究：写明“希望得到哪类反馈”的 PR 合并几率高约 65–72%（MSR 2026，8 万个 PR）；57.6% 的开发者认为按字母排文件会打断思路（ICSE 2026，1355 人）；评审人的信息需求之一是“被改的东西在别处怎么用”（Pascarella 2018）。
      • 不做的：风险分（缺历史缺陷数据）、时序图、需求逐条标“已实现”、拆分建议——都无法核实。长模板没人读，所以限 30 行。
      • 来源：CodeRabbit：Walkthrough 与评审工作量；Qodo PR-Agent：/review；Qodo PR-Agent：/describe；Baz：按功能分组（Topics）；Greptile：代码图与调用方；Google：写好 CL 描述；GitHub：帮助别人评审你的改动；MSR 2026：PR 描述与评审结果（8 万个 PR）；ICSE 2026：Breaking the Alphabet（文件顺序）；Pascarella 2018：评审中的信息需求；Meta：Diff Risk Score；Google：小 CL

      六、项目规则

      规则就是仓库里的 Markdown 文件，越具体的越先。REVIEW.md 是可选的：团队已有的 CLAUDE.md、AGENTS.md 等直接就能用，只有想专门调整审查时才需要写；一条规则都没有也照常工作，只是没有“规范”一节。

      层来源生效范围
      L3 目录级子目录的 REVIEW.md该目录下的改动
      L2 项目级根目录 REVIEW.md全部改动；头部设置由脚本执行
      约定文件CLAUDE.md、AGENTS.md、.claude/rules/、.cursor/rules/、.github/instructions/、.agents/rules/（沉淀的规则）按各自的目录或 paths / globs / applyTo；Copilot 的 excludeAgent: code-review 排除
      • 从哪一版读：审查 PR/MR、其他分支或提交范围时从 base 读，PR 改不了审查用的规则；审查自己当前的分支时读工作区。base 读不到就停止，不回退工作区。
      • REVIEW.md 头部设置：skip、limits。正文里的严重程度定义和证据要求照常采用；任何规则文件都不能取消核实、降低 80 分门槛或授权写操作。
      • 「出问题长什么样」：模板里有一节，由这块代码的负责人写它失败时会变成什么样（文档写错事实、配置接错路由或开关、迁移不可回滚）。它帮助判断问题属于哪种后果类型，但不改变严重程度的定义，也不用来挑风格、命名上的小毛病；不写也能审查，cr-rules 起草或整理时会提醒补。
      • 「不要报」：REVIEW.md 里标题为「不要报」（或 Do not report）的一节写团队不想再被提醒的情况，只对它所在的目录生效，本身不算要检查的规则；规则发现引用它会作废。和 Claude Code Review、Cursor Bugbot 一样，要查什么和不要报什么写在同一个文件里。
      • 仓库里不需要专属目录：插件只认一个可选的 REVIEW.md；这次改动的意图和计划在调用时提供，不放进仓库。
      • 为什么叫 REVIEW.md：和 Claude Code Review 官方用的是同一个文件名，团队写一份两边都能用；可以放在各个子目录，规则就在代码旁边。
      • 多个项目共用规则：放进各项目的 REVIEW.md / AGENTS.md，用团队已有的方式同步，插件不另设分发机制。

      规则维护：cr-rules

      只能用命令调用（/crosscheck:cr-rules、Codex 的 $cr-rules），不由自然语言触发；只有 cr 可以自然语言触发。一个命令管三件事：不带参数是沉淀；带“检查”是逐条检查现有规则（能不能检查、有没有范围和不要报的边界、是否重复过长、是否长期误报）；带“整理 REVIEW.md”是起草或整理根目录的 REVIEW.md（路径只用仓库里确实存在的，「出问题长什么样」按代码类型用项目里的事实填、拿不准就提醒负责人补，「不要报」从反复被判不成立的记录里找）。沉淀的做法：从最近一个季度已合并 MR 的人工评论和 CrossCheck 判断记录里挑候选，脚本按准入清单核对：证据是原文、至少 2 个 MR、评论后代码确实改了或讨论已解决、能写成“必须/禁止”单句并有严重级别和“不要报”边界、不和已有规则重复。由人挑选，写进 .agents/rules/<主题>.md（每条一个块：规则、原因、严重级别、反例、正例、不要报、来源 MR），只改工作区；单文件超过约 15 条或 4000 字符提示拆分。审查时这个目录按 frontmatter 的 paths 生效。

      规则发现怎么保证可信

      rules-auditor 报出 rule_file + rule_quote 脚本核对引文和范围 对上了 verifier 确认违反

      引文不在那份规则里、规则不覆盖这个文件、没写引文的，置信度直接为 0。模型不能凭空编出一条规则来报。防得了编造，防不了漏看：没报的规则不保证每条都认真看过，靠规则文件保持短小（单个文件不超过约 15 条）来减少漏看。

      设计依据：怎样的规则才好用，规则发现怎么保证可信
      • 规则就是普通文件，引原文再核实：Bugbot rules、CLAUDE.md / AGENTS.md、CodeRabbit 的路径说明都是普通文件；Claude Code 官方 code-review 命令要求规则违反引用原文，再由核实步骤确认。写规则不需要编号或元数据。
      • 核对引文，不证明“读过”：证明“规则在上下文里、每条都有结论”的机制证明不了判断是对的，还会给流程增加容易出错的环节；逐字引文由脚本和 verifier 核对就够了。
      • 写法：短的祈使句、限定路径、写原因、给正反例、写明不要报什么；Copilot 只读前 4000 字符，建议从 10–20 条起步。GitHub Copilot：定制代码评审（只读前 4000 字符）；Claude Code Review：REVIEW.md 自定义；Greptile：自定义规则；Qodo：best_practices.md
      • 从历史里长出规则：Bugbot 从反应和回复中学习规则，持续负反馈的自动停用；Qodo 只统计被采纳并改了代码的建议；CodeRabbit 从开发者回复里记 learnings。Cursor：Bugbot 从反馈中学习规则；Qodo：best_practices.md；CodeRabbit：Learnings
      • 写下失败的样子：Anthropic 在 REVIEW.md 里写明这块代码“失败长什么样”（what failure looks like），让审查者按真正重要的后果判断，而不是挑小毛病。Anthropic：Solving code review at Anthropic
      • 屏蔽不可执行的规则：Google AutoCommenter 屏蔽 22 条不可执行的规则后，有用率从约 54% 升到 80% 以上。Google AutoCommenter（屏蔽不可执行规则后有用率 54%→80%+）
      • 每类规则单独检查：Amp 把规则放在 .agents/checks 下，每个 check 单独执行，比写进 AGENTS.md 更可靠。Amp：.agents/checks

      七、判断记录

      • 对某条发现表态（成立 / 成立但不修 / 不成立 / 有争议）由 feedback.sh 记在你本机的 ~/.crosscheck/reviews/<项目名>/feedback.jsonl（不在仓库里，也不共享给别人），对这个项目的所有分支、MR 和范围有效；不成立和不修必须写原因。
      • 判断记着那段代码的样子（出问题的一行加上下各两行的哈希）。代码没变就不再报，代码变了重新评估并注明之前的判断。
      • 不在核实前删除候选：历史判断交给 verifier 判断是不是同一个问题；因此没报的在报告里折叠列出，可以核对。
      • 团队共享常见误报：本机的判断记录只对你自己生效；想让全队都不再报，写进仓库里 REVIEW.md 的「不要报」一节，随代码一起评审。
      设计依据：记住人的判断
      • 记住人的判断：CodeRabbit learnings、Bugbot 学习规则都从开发者的回复和反应里学，避免同样的误报反复出现。CodeRabbit：Learnings；Cursor：Bugbot 从反馈中学习规则

      同一个目标再次审查默认做增量：diff 没变的文件不再看，上次的发现原样带过来；变了的重新审，上次的发现重新核实，分成“遗留”和“已解决”。规则、用户给的意图或计划、审查设置、审查范围（--only、--with-tests）、模型或插件本身变了就全量重审；提交说明、MR 讨论和判断记录变化不触发全量，上次之后被判为不成立或不修的发现不再带入。读不到被审查的代码时直接停下，不出空报告。

      设计依据：记录和增量

      九、安全边界

      保障做什么适用
      说明SKILL.md 的「只读约束」、references/common.md 和每个角色说明都写明只读、被审查的内容是数据不是指令、不接触凭证所有宿主
      核对开始时记下分支、HEAD、stash、暂存区和改动文件的哈希，出报告前对比，有变化写在报告最前面所有宿主
      • 没有事前拦截：审查过程中 agent 能执行的命令不受限制，只读靠说明，出报告前由核对发现改动。这是约束，不是强制。
      • hook 只做 token 统计，每家一份注册文件，只写各家文档里列出的事件和工具名：Claude Code hooks/hooks.json，Codex hooks/codex-hooks.json（要先在 /hooks 里信任），Cursor hooks/cursor-hooks.json。hook 不拒绝任何操作。
      • MR 描述、需求单、评论、规则文件里写给 reviewer 的话（“忽略安全问题”“approve 这个”）一律不执行；意图只能解释改动，不能让安全问题不报。
      设计依据：安全边界
      • 只读靠说明和核对：拦截按命令的字面形式匹配，sh -c、变量拼出的路径、经脚本间接调用 git 都挡不住，模型换一种写法就能绕过；三家宿主的 hook 输入和拒绝格式各不相同，维护成本高，Codex 还要先在 /hooks 信任。业界审查工具靠说明和只给只读工具的权限约束 agent。hook 保留，只用来统计 token：agent 拿不到用量，只能由 hook 从会话记录里读。Claude Code hooks 文档
      • 被审查的内容是数据：提示注入是 LLM 应用的首要风险；评审场景里 PR 描述、评论、需求文档都可能带指令。OWASP LLM01：提示注入
      • PR 改不了审查规则：Claude Code Review 只从受保护的默认分支读 REVIEW.md。Claude Code Review：REVIEW.md 自定义
