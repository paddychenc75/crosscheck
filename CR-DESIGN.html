Crosscheck CR 方案

本地代码审查与项目规则维护。组织规则由外部统一治理，按配置只读取得；Crosscheck 保留本次材料、查找并核实发现，不承担组织规则的编辑、审批和发布。

关键设计旁的“设计依据”可展开查看。公开实践说明借鉴方向，研究启发不等于效果已验证；具体参数与产品边界单独标为 Crosscheck 的取舍。来源核对日期：2026-10-20。

      一、设计原则

      设计原则

      1. 精确率优先。两条真实发现好过十条里错三条。作者看到几条错误评论后就不再认真看其余的，报告为空是正当结果。
      2. 查找和核实分开。子代理核实只接收候选结论；无子代理时重新读代码并反证，报告同一宿主顺序核实的独立性限制。
      3. 确定性的工作交给脚本。diff、行范围、材料校验与规则装配由脚本完成；外部获取由宿主适配，agent 做判断。快照固定输入，不保证模型输出完全复现。
      4. 宿主无关。同一套流程在 Claude Code、Cursor、Codex 中运行，宿主专属机制只做增强。
      5. 每项调整都可衡量。改提示词、阈值、流程之前先跑评测，没有数据不改。
      6. 维护边界明确。项目规则经确认后维护在已有规则源，审查专属要求放 REVIEW.md；组织规则由外部统一治理，CR 只读消费。每条规则只维护一份，不自动同步多套格式。
      7. 信号都要回流。人的判断、人工评论和未通过核实的候选保留记录；确认有复用价值的，再进入项目规则建议或评测候选。

      不做什么

      • 查找阶段尽量不漏，核实阶段控制误报；用评测同时观察召回与精确率。
      • 不替代编译器、类型检查器、linter 和 CI，它们能拦住的问题不报。
      • 不审查改动之外的存量代码，不做风格和品味上的评判（除非项目写成了规则）。
      • 不往 PR/MR 发评论，不 approve、request changes、merge，结果只在本地输出。
      • 默认不改文件，只有用户明确要求时才修复，且只改工作区、不提交。
      • 审查过程中从不往 GitLab 写任何东西。只有两种写操作，而且都要你确认：提交项目规则改动的 MR（只创建、不合并），以及同步共享的判断记录。

      设计依据：哪些有公开参考，哪些是本项目的取舍？
      • 公开实践参考：Claude Code Review 官方说明采用多个 agent 并行查找、再核实发现的流程。它支持“查找与核实分开”的方向，不代表官方采用了 Crosscheck 的角色数量、倒序阅读或三遍配置。
      • 换序检查的研究启发：Lost in the Middle（Liu 等，TACL 2023）在多文档问答和键值检索中观察到：相关信息的位置会影响所测模型的表现。它提供了改变阅读顺序的研究动机，但没有直接验证倒序审代码能提高召回，也不能据此断言当前模型有相同程度的位置偏差。
      • Crosscheck 自身取舍：倒序复查、调用方视角和具体遍数来自本项目的 SKILL.md 与角色说明；测试削弱、风险分级由 collect-context.sh 先扫描，是为了复用可重复的检查、减少重复模型调用。它们是待核实的线索，不是确定的缺陷结论。

      效果与代价：多遍检查增加用时和 token；换序及额外视角是否值得，需要在同组用例、相同模型与受控调用预算下对照召回和误报，不能把一般研究当成本项目已验证的收益。脚本扫描成本较低，但不能覆盖所有语义变化。

      三、分层设计

      1. 入口层：怎么使用

      不需要记参数。直接用平时说话的方式告诉它审什么、审多细、审完要做什么；下表右列的参数只是熟练之后的简写，用不用都行。说法有歧义时（比如「看看 128」分不清是 MR 还是 Issue），它会先问一句再开始。

      审什么

      你想审的可以这样说简写
      当前分支的全部改动，包括还没提交的「review 一下」「帮我看看这次的改动」/cr
      另一个分支（不用切过去）「看看 feature/pay 分支」/cr feature/pay
      一个 MR「review MR 128」，或者直接贴 MR 链接/cr 128
      某几个提交「看看最近 3 个提交」/cr HEAD~3..HEAD
      某个目录下的改动「只看 src/orders 下面的改动」/cr src/orders

      审多细（什么都不说就是标准深度，适合大多数情况）

      你想要的可以这样说会怎样简写
      快速过一遍「快速看一下」「简单过一遍」只查 bug 和安全问题，最多报 5 条，最快--quick
      上线前仔细审「仔细看看」「上线前深度审一下」换个顺序多查几遍，并尝试写脚本复现问题；明显更慢、更贵--deep
      只关心某一方面「只看安全问题」「只对照一下团队规范」只启动对应的角色--only security
      连测试一起看「测试也一起看」测试文件也按缺陷审查（默认只检查测试有没有被削弱）--with-tests
      从头完整审一遍「重新审」「全量审一遍」忽略上次的记录。默认只看上次审过之后变了的文件--full

      补充背景（可选，能让结果更准）

      你想告诉它的可以这样说简写
      这次改动想做什么「这次是为了修复分页丢数据」--intent "…"
      方案或计划写在哪「方案在 docs/plan.md」--plan docs/plan.md
      核实用哪个模型「核实换成某某模型」--verifier-model …

      审完之后：直接回复就行，比如「第 2 条不对，上游已经校验过了」「把第 1、3 条修掉」「以后这种别报了」。各种回复怎么处理，见第十节「报告之后」。修复只有你明确要求时才做（简写 --fix），只改工作区、不提交。

      其他功能

      你想做的可以这样说简写
      从人工评审记录里总结规则「从最近 3 个月的 MR 评论里总结一下规则」/cr 提炼规则 --since 90d
      复核规则「复核一下我们的规则」「检查一下我们的规则」/cr 规则复核

      改了插件后跑评测「跑一下评测」/cr 评测

      2. 上下文层（宿主获取，脚本校验与装配）

      • 改动收集（collect-diff.sh）：
        • 不检出、不切分支：被审查的代码不在工作区时，一律用 git show / git grep 从目标 ref 读取。
        • 只留有效代码：过滤 lock、生成、vendored、二进制、测试、日志和各类产物，原因写进 skipped.txt。
        • 算出每个文件新侧的改动行范围（ranges.txt），发现只能落在这些行上。
        • 大改动按路径顺序切成约 1000 行一批，每批独立审查。
        • 增量：先保留当前目标完整 diff，再读取项目规则、外部规范、实际使用的参考资料与意图。材料、来源选择、适用范围或审查配置（含实际模型与插件版本）变化，或无法确认一致时，重审当前目标全部 diff，不扫描全仓。只有材料与配置均可确认一致时，才沿用现有代码增量逻辑；不做条款到文件的精细依赖图。
      • 意图：这次改动想做什么、验收标准是什么、哪些行为变化是刻意的。来源和用法见本节末尾的「意图收集」。
      • 规则装配（collect-rules.sh）：
        • 设计约定：PR/MR 模式从 base 读取项目规则，新规则需先合入 base；工作区模式读取工作区规则。当前 base 不可读时的回退缺口见第四节，不能把工作区副本当成可信 base。
        • 扫描已支持的规则位置，用 paths / globs / applyTo 等范围匹配改动文件，再把适用正文交给角色。无范围的全局规则仍会一起加载；任意自建 rules 目录不会自动识别。
        • 按配置取得指定外部资料，结合项目规则装配。旧 Git extends 用法保留；忽略项不能静默取消外部要求，冲突明确交人判断。
        • 生成现有 rules-index.json 与 task-rules.md；检查项区分来源，保存原文与读取结果。缺失、截断或冲突要说明。
      • 历史判断：保留项目判断记录。外部规范的旧判断先作参考，本轮仍核对代码与原文；项目判断也不能跨不同问题套用。
      • 测试削弱扫描，保留现有检测范围，产出 weakening.txt。即使默认不完整审查测试文件，也照常扫描：
        • 删掉的测试文件或断言；修改断言期望值等可能迎合错误实现的变化；
        • 新加的 skip、xit、@Disabled、t.Skip，以及 only 导致其他测试不再运行；
        • 调低的覆盖率阈值；
        • 新增的 ts-ignore、eslint-disable、nolint；
        • CI 配置里删掉检查步骤、放宽失败条件（如允许失败）。这些是需要核实的削弱线索，不把每次修改期望值都直接认定为错误。
      • 风险分级，产出 risk.txt，只用确定性的信号：命中根 REVIEW.md 配置的高风险路径、迁移文件、鉴权和支付相关路径、diff 大小、是否有测试削弱。用户没指定深度时据此建议深度，只建议、不强制。
      设计依据：项目规则版本、分批与增量
      • 公开实践：Claude Code Review依据分支保护情况从 base 或默认分支读取 REVIEW.md；GitHub Copilot Code Review当前说明从 PR 的 head 读取指令。行业没有统一的版本选择。
      • 本项目取舍：PR/MR 使用 base 规则，工作区审查使用工作区规则，避免改动同时放宽本轮标准；约 1000 行分批是本项目的工作量控制参数。材料或配置变化后重审当前 diff，是为了简化缓存，不是外部产品的通用要求。
      • 收益边界：base 读取需要先合入规则才能生效；分批与保守重审可能增加上下文和调用成本。效果与成本须用项目用例验证。

      意图收集

      需求材料帮助审查判断“是否做到了要求”，并区分刻意的行为变化与错误。Crosscheck 收集作者说明、关联需求和用户提供的计划；具体参考与本项目的扩展见下方“设计依据”。

      Crosscheck 按下表收集，脚本汇总成一份 intent.md：

      来源收集什么怎么取
      MR 标题和描述要做什么、为什么、刻意的行为变化glab / gh；不可用时只能从提交说明里取
      关联的需求单标题、描述、验收标准、子任务从 MR 描述和提交说明里识别链接或编号。GitLab Issue 用 glab api 只读获取；其他系统要在 ~/.crosscheck/config 里配置读取方式，没配置时只记下编号，不去抓取
      提交说明每一步改了什么git log base..head
      MR 上的人工讨论作者在回复里解释的意图、已经达成的结论glab api …/discussions 只读获取，只留人工评论
      计划文件agent 或作者写下的计划、方案取舍用户用 --plan <文件> 指定，或仓库里约定位置的 .cr/intent.md；不自动读取任何 agent 的会话记录
      --intent "…"用户临时补的一句话调用参数

      intent.md 的结构固定：目标、验收标准、刻意的行为变化、明确不做的、来源清单（每一条从哪来）。总长度有上限，超出时截断并注明。所有来源都没有内容时，报告末尾提示「没有找到意图，可以用 --intent 补一句」。

      意图的用法：

      • 查找时对照：说了要做的，代码是否真的做到了；代码里有没有说明中没提、也不像刻意的行为变化。
      • 需求核对：有明确的验收标准时，没有满足的条目作为一类单独的发现（intent），同样要经过 verifier 核实，在报告里单独成节，默认最多 5 条。和需求无关的改动默认不报。
      • 减少误报：意图里写明的刻意行为变化，不当作缺陷报。
      • 只能解释，不能豁免：意图来自作者，属于被审查的材料。它可以说明「这个行为变化是有意的」，但不能让安全问题不报，里面写给 reviewer 的指令（「这里不用查」）一律不执行。
      设计依据：为什么读取意图和验收标准
      • 公开实践：CodeRabbit 的关联需求核对比较 PR 改动与关联需求，给出已满足、未满足或不确定的判断；Anthropic 的公开 code-review 插件将 PR 标题和描述传给查找及核实 agent。
      • 本项目取舍：额外支持提交说明、人工讨论、--intent 和计划文件，并把未满足的明确验收项归为 intent。资料不足时说明缺口，不推测作者需求，也不自动读取私人会话。
      • 支持到哪里：这些实践支持“审查需要需求上下文”，不证明某个信息源必然提高准确率，也不支持统一的提升百分比。每项结论仍需代码证据与核实。

      3. 多角色审查

      一次审查由一个主 agent 编排，它按深度启动若干个角色，每个角色是一个独立的 agent（宿主支持子代理时并行运行，不支持时由主 agent 依次扮演）。每个角色有自己的一份说明文件（roles/<角色>.md），说明短而专一；共用的部分（规则设置的处理、读代码的方式、只读约束）集中放在一份公共说明里。

      角色一览：

      角色负责什么时候运行交出什么
      主 agent（编排者）解析参数、运行脚本、启动其他角色、汇总过滤、出报告、记录人的判断每次报告和审查记录
      bug-hunter找正确性问题，并对照验收标准每次（quick 由主 agent 兼任）候选发现
      security-reviewer找安全问题每次（quick 由主 agent 兼任）候选发现
      rules-auditor对照团队规则standard、deep，且有适用的规则时候选发现及规则检查清单
      simplifier找可以简化的地方standard、deep简化建议
      verifier独立核实每条候选并打分有发现候选或可抽查规则检查项时；每批最多 5 条，一批一个带分数和理由的候选
      rule-miner从人工评论和判断记录里提炼候选规则只在 /cr 提炼规则 时候选规则
      judge评测时判断发现是否对上答案；MR 合并后判断报过的问题在最终代码里是否解决只在跑评测、统计采纳时对上 / 没对上、已解决 / 未解决，附理由

      查找角色的细节：

      角色查什么要求的证据
      bug-hunter逻辑错误、边界、空值、并发、错误处理、资源泄漏、API 误用。local 从改动处向外查，impact 从使用方向内查漏改的地方具体的输入或状态 → 错误的结果
      security-reviewer注入、鉴权越权、密钥、反序列化、SSRF、路径穿越；以及 LLM 类风险：不可信输入拼进提示词、模型输出直接当作命令或 SQL 执行、密钥或个人信息发给模型、无上限的调用、引用不存在的包攻击者可控的值从哪进入、经过哪几步、造成什么后果
      rules-auditor违反各层规则的地方，附原文与出处；有原生编号则保留。检查顺序见下逐字引用规则原文和出处
      simplifier可复用的已有代码、重复、多余的机制、没被用上的新代码已有的等价代码在哪里

      rules-auditor 的检查顺序：

      1. 先读会改变审查方式的部分。根 REVIEW.md 的支持配置由脚本执行；根或目录正文提供相应范围的审查重点、证据和分级要求，分级处理顺序见第四节。另核对 .cr/ignore.md 的有条件抑制。项目抑制不得静默取消外部要求；冲突交人判断。
      2. 作用域与治理权限分开。按装配结果检查目录、项目、组织规则与仓库代理约定。不同来源冲突时提示原文和出处，不按返回顺序覆盖，也不由 CR 自动批准例外。
      3. 筛出这次要查的规则。只留作用域覆盖改动文件、并且能对照代码检查的条目：命名、必须用或禁止用的 API、错误处理约定、代码放在哪里、必须同步修改的地方、日志里不能出现的内容。怎么跑测试、用哪个包管理器这类操作说明跳过。
      4. 逐个改动文件对照改动行。只看这次 diff 改到的行；只凭 hunk 判断不了时打开整个文件。改动行明显违反规则的字面才报，要引申才能套上的不报。
      5. 查反证。核对是否已有处理、是否误读原文。大量现有代码与规范相反时提示疑似过时并给出反证，不静默取消外部规范。
      6. 合并后交出。覆盖检查单位与发现去重依据分开。同一条具体要求、同一文件、同一缺陷在多处重复时才合并，并保留全部相关依据；不同条款或不同失败场景分别保留摘要、证据和建议。同属一份文档不能单独作为合并依据；每条附原文位置与出处，交给 verifier 核实。同时交出检查清单，由脚本核对有没有漏掉的规则（见第五节「保留必要的可追溯性」）。

      深度：

      深度查找核实
      quick主 agent 一次完成 bug 和安全主 agent 自己核实
      standard四个角色并行，大改动按批次运行verifier 子代理，只读代码
      deep再加倒序的 bug-hunter、impact 视角的 bug-hunter、倒序的 security-reviewer；同一候选被几遍查到记为命中次数（不传给 verifier）verifier 可以写最小脚本复现，或运行项目已有的类型检查和测试

      保留现有规则保障：有规则检查清单时，先用 check-rules.sh 核对覆盖和核对码；缺项、无效项或核对码不符时补查一次，仍未通过就在报告里列为未检查。再由 prepare-verify.sh 抽取“未违反”项交给 verifier：standard 默认 3 条、deep 5 条，不足时取全部可抽查项。普通发现候选为零，也不能跳过已有可抽查项。没有可抽查项就如实说明，不伪造抽查结果。

      核实：

      • verifier 只拿到符合结构的候选，不拿到查找者的推理，先尝试推翻，再按评分标准打分。
      • 按顺序执行封顶检查：不在改动行上、base 版本就有、有守卫使其不可达、代码没被用上、CI 会拦住、命中仍有效的历史判断或误报清单等，第一条适用的决定分数上限。外部规范历史不自动抑制本轮发现；材料变化或适用性不确定时重新核对。
      • 候选带 needs_check 时，先核对那一环。
      • verifier 的模型按用户调用时指定（--verifier-model），默认和当前宿主同一个模型；记录实际使用的模型，不把配置值当成调用事实；便于比较结果。
      • 打分必须附依据：核实时读过、能支撑结论的代码位置（文件:行）；排除了哪些可能（守卫、调用方、base 版本是否已有）；deep 模式下的复现命令和结果。脚本会检查依据里引用的位置在被审查的那一版代码里真实存在，引用不存在的依据作废，这条最高 50 分。
      • 每条候选的分数都留档：80 分以上进报告，其余写进 rejected.json，用于校准阈值。

      汇总：核实前合并同根因、同一失败事实且一个局部修复能解决的候选，保留各触发场景与验收出处；规范、简化与其他判断维度分别核实，规范发现仍按同一具体要求汇总，文档单位相同不代表同一个缺陷；核实后丢弃 80 分以下和不在改动行上的；缺陷、规范、简化各自计数上限（默认 10 / 5 / 5，可通过根 REVIEW.md 的 limits 配置调整）；按严重程度和置信度排序。

      设计依据：高置信过滤、规则清单与参数
      • 公开实践：Anthropic 的公开插件要求验证问题、引用被违反的规则，并过滤未验证的发现；Bugbot可显示实际使用及被截断、遗漏的规则。
      • 本项目取舍：rules-index 清单、核对码、缺项补查一次、对“未违反”项抽查，都是 Crosscheck 用于降低漏检风险的机制。80 分门槛、每批最多 5 条、standard 抽查 3 条 / deep 5 条以及报告条数上限，是本项目参数，不是行业标准。
      • 验证边界：核对码只能辅助核对材料，清单只能核对检查结果是否齐全；两者均不能证明模型理解正确。评分不是统计概率，80 分也不是“80% 真实”，参数应通过召回、误报与成本对照调整。

      4. 输出层

      • 报告：开头一张概览表；每条发现包含位置、问题代码原文（由脚本从被审查的那一版摘取，带行号）、失败场景、修复建议（能确定时用 diff），必要时附兼容性说明和之前的判断。
      • 每条发现都附依据，默认折叠，展开可以核对：置信度分数、核实时读过的代码位置、排除了什么、复现的命令和结果（deep 模式）、由哪个角色查到。rules 发现另附原文、位置和出处；有原生规则编号则保留；security 发现另附攻击路径的每一步。读报告的人不用重新查一遍，就能判断这条站不站得住。
      • 分节：缺陷、需求核对、规范、可简化、测试削弱各自成节；复审另列“本轮未能复核”及原因。末尾注明意图和规则来源；因仍有效历史判断而未报的折叠列出，可以核对。

      四、项目规则

      作为目录约定读取的 AGENTS.md、CLAUDE.md 等文件只作用于所在目录；原生 rules 文件按各自的 paths/globs/applyTo 装配。.claude/CLAUDE.md 与 .github/copilot-instructions.md 是明确的全局入口，不能把其下任意目录文件都当成全局。

      项目负责人确认规则，Crosscheck 帮助整理和提出改动。从近期 MR 人工评论中提炼的长期约束，优先维护在项目已有的 rules；审查专属要求放 REVIEW.md。规则与代码一起走项目 MR 流程，组织规范仍由外部维护。

      本轮已补齐项目规则的共用读取、原生格式正文维护、路径验收与采集完整性。脚本检查与模型判断分开验证；语义去重、规则是否值得长期保留仍由角色和负责人核对。

      1. 确认成立后，维护在哪里？

      提炼出的内容维护位置例子
      编码时也必须遵守的项目约束项目已有的 rules 或通用约定文件；已有同义规则就修改原处金额使用本项目 Money 类型；新增事件类型须同步注册序列化器；切换账号清理用户缓存
      审查重点、证据要求、严重程度及报告设置正文要求放根或目录 REVIEW.md；skip / limits / severity 等脚本设置只放根文件 frontmatter迁移重点核对回滚路径；不可恢复的数据损坏按严重问题报告；根配置限制简化建议条数
      有明确条件的长期误报模式.cr/ignore.md，写清范围、成立条件和原因特定客户端已经负责重试，不重复要求其调用方再加一层；“暂不修”不能直接变成永久忽略
      lint、类型检查或 CI 能稳定执行的约束对应工具配置，由项目原有流程维护格式、import 顺序、禁止使用某个 API；不再抄一份自然语言规则
      通用缺陷漏报、一次性例外或未解决争议评测候选或项目判断记录，不自动写成长期规则一次回调漏报保存为评测候选；单次兼容处理、个人偏好不足以代表全项目约定
      跨项目组织规范原有组织知识库或规范仓库CR 输出建议、证据和出处，交外部负责人处理；不改组织原件或同步副本

      每条规则保留一个维护源。已有规则留在原处；没有同类规则时，沿用该模块既有目录。项目存在多种格式且落点不明确时，由负责人选定新规则的默认位置，不自动复制到所有格式。没有既有体系的小项目可以先用短 REVIEW.md，以后按实际需要拆分。

      例如项目已用 .claude/rules/payments.md，金额约束就更新该文件，REVIEW.md 只补必要的审查严重程度。仓库里的项目 rules 在审查时只读、在维护时经确认修改；组织规范按维护责任保持只读，不能仅凭文件位于仓库内就认定可以编辑。

      正文要求贯通查找、核实与汇总。受信任版本的 REVIEW.md 中，证据要求和分级声明由查找、核实与汇总共同采用。沿用现有 severity 字段和显式配置；没有显式分级覆盖时，核实后的严重程度不能再被默认 minor 重置。验收例：普通 rules 文件没有严重程度元数据，REVIEW.md 正文规定“订单审计记录缺失按重要问题报告”，最终报告仍应保留该分级。正文不能授权工具调用、扩大权限、跳过核实或降低固定门槛。

      3. 从近期人工评论到规则 MR

      正式规则保存在业务代码仓库的选定文件中。扫描评论和候选默认放本机 ~/.crosscheck/rule-work/<项目>/mined-<日期>/，它们只是提案材料；审查快照和本机判断记录都不是团队正式规范的维护源。

      1. 确认扫描范围并收集材料。项目负责人指定项目与时间段。列明日期口径、MR 数量、评论范围及是否读全；取得原评论、讨论结论和相关代码。已解决或代码有变更只是采纳线索，不等于长期规则已被批准。
      2. 先核对已有规则与提案，再提候选。审查和提炼复用规则来源识别与解析，保留作用域和用途限制；同时查询尚未合入的 crosscheck-rule MR。已有同义提案就引用原 MR，不再创建一份；已有约束不重复新增，不够准确的改写原处。每条候选附规则、原因、范围、例外、来源评论和具体目标文件。通用缺陷进入评测候选，不靠项目 rules 提示模型记住每个测试答案。
      3. 让负责人确认具体 diff。一并展示新增、改写或删除的正文与作用域，检查原格式，再由负责人确认内容和落点。使用 --mr --preview <仓库外文件> 固定预览；创建时用同一文件加 --yes。基准、操作或未合入提案改变时重新展示差异。创建前再核对有无同义未合入提案，随后按授权创建项目规则 MR，只创建、不合并；不自动修改或关闭已有 MR。
      4. 沿项目原流程审阅和维护。由现有维护者、CODEOWNERS 与分支保护处理合入；之后按规则所在版本生效。保留来源评论链接与修改理由，复核时回到同一文件修改或删除。关闭的候选保留原因，有新证据才重新提出。

      正文保留规则、理由和必要例外，评论证据放在提案或 MR 描述中，不把整段讨论堆进规则文件。沿用已有编号；没有编号也可按文件、标题与原文定位，不要求所有工具改成 PRJ 编号。使用现有 Git 记录，不新增候选数据库或审批状态机。

      业界实践与本项目取舍
      • 区分通用约束和审查要求：Claude Code Review区分 CLAUDE.md 与 REVIEW.md，支持目录级补充；查找、核实及最终汇总都会参考审查要求，包括严重程度。其托管服务与本地审查命令读取入口不同，不能把一种入口的支持推断给所有工具。
      • 小文件与明确范围：Claude rules按主题拆分并用 paths 限定范围；Cursor Agent使用 .mdc 规则；Copilot支持 applyTo 路径说明。格式与加载方式并非统一标准。
      • 不要混淆 Agent 和审查产品：Cursor Bugbot有自己的 .cursor/BUGBOT.md，不能假定它使用 Agent 的 .cursor/rules。Crosscheck 已支持的输入格式，以本项目读取器为准。
      • 保留规则用途：Copilot 官方说明用 excludeAgent 区分编码与审查用途。Crosscheck 默认尊重 code-review 排除，是本项目的兼容取舍。
      • 反馈可以形成可审阅改动：CodeRabbit可根据过去 7 天的审查建议生成 path instructions 并创建 PR；这不等于自动批准所有人工评论。其 Learnings适合增量偏好，正式规范更适合规范文件或审查说明；我们不照搬其知识库存储与自动批准策略。
      • 复用已有提案状态：GitLab MR API支持按状态和标签查询。利用未合入 MR 避免重复提案，是本项目据此作出的流程选择，不需要另建审批系统。
      • 本项目取舍：规则留在已有项目维护源，审查要求放 REVIEW.md；候选由负责人确认后经项目 MR 合入，组织规范只读。MR 来源、正反例和作用域用于复核，不设置统一评论数量门槛，也不把某个行数当作有效性的硬界限。
      • 优势与代价：开发与审查共用项目约束、改动可追溯；代价是人工确认与多工具格式兼容仍需验证。规则冲突交负责人处理，不按加载顺序擅自覆盖外部要求。上述机制有官方依据，具体落点与流程是 Crosscheck 的设计选择。

      2. 配置什么，不配置什么

      配置内容首版做法
      从哪里取选 Git、文件或宿主已有连接；先接一个真实知识库。连接和认证复用宿主，不另写 MCP 客户端。
      读哪些内容指定规范文档、目录或规则包。项目可以选择既有来源，不能通过 PR 注册任意命令、地址或凭证。
      用于什么明确指定的规范作为 rules；搜索到的设计说明、事故资料作为 context，帮助理解但不自动变成规范。
      适用于哪里复用路径作用域；没有范围时按本次配置的范围使用。保留来源标识，避免同号规则混淆。

      配置语法与第一个知识库接口一起确定。只统一 CR 收到的材料，不设计通用平台字段映射语言或动态适配器注册框架。

      3. 保留必要的可追溯性

      • 保存本次实际读到的原文、链接 / 路径和可用版本信息，不只留模型摘要。
      • 固定文档清单要核对是否读齐；目录接口按实际分页读取；正文被截断或无法确认读全时注明。搜索结果只代表本次检索所得，不代表全部组织规范。
      • 没有统一规则编号也能使用；内部按来源与文档 / 已有规则编号区分检查项。原编号只作可读引用，不能覆盖别的来源同号规则。
      • 同一篇文档里的不同要求可以产生多条发现。只合并确实相同的问题；无法确认重复就分别保留，不新建永久条款身份体系。

      4. 边界情况用简单策略处理

      情况首版处理
      材料、意图或审查配置变化重审当前目标的全部 diff，不计算精细受影响文件图；不是扫描全仓存量代码。
      读取失败、只读到部分或被截断继续代码检查；列出缺失内容，说明对应规范未检查完。上次相关发现保留为“本轮未能复核”，不算解决。
      多份规范冲突保留出处并提示冲突，不按返回顺序自动覆盖，也不新增复杂优先级语言。
      旧反馈或迁移前记录是否仍适用不确定仅作参考，重新核对；首版不自动迁移组织规则抑制。
      外部批准、强制性或例外不明确给出代码事实与原文，交人判断。CR 不授予例外，也不提供组织合规认证。

      代价：材料变化时可能多跑一次审查，部分旧发现需要重新确认；换来更少的状态、映射和维护成本。等真实规模与成本问题出现，再考虑精细缓存和历史迁移。

      设计依据：外部资料只读接入与失败可见
      • 公开实践：GitHub Copilot提供 MCP 工具配置并建议只读工具白名单；CodeRabbit通过 MCP 取得外部工具和资料。Bugbot说明本次使用了哪些规则及哪些被截断或省略。
      • 本项目取舍：认证和连接复用宿主，仅保存本次原文、出处和读取结果；指定规范与搜索背景资料分开，缺失就提示。组织维护留在外部，是本产品的范围选择，不是 MCP 协议或行业共同要求。
      • 限制：配置好连接不等于本轮已经读到资料；工具返回全文、权限及截断情况仍需实际验证。不宣称组织规范全覆盖或自动合规。

      六、代码结构

      不预先拆成五个新模块。保留现有脚本入口、角色和输出文件，先把组织来源读取从规则装配中分离；需要多少辅助文件由实际实现决定。

      现有部分本轮最小改动
      collect-rules.sh保留项目读取和装配；组织资料通过一个可替换的获取 / 导入入口传入。旧 Git 路径继续支持。
      宿主接入说明说明如何用已连接工具读取指定资料并保存；工具名、参数只留在接入处，不写进审查角色。
      check-rules / aggregate / 报告检查项区分来源；保留原文引用和读取失败提示；不同条款不因同属文档而误合并。
      增量与历史材料或配置变化时重审当前目标；无法确认一致就不复用。外部规范历史仅供参考，不建立精细迁移机制。
      mine-reviews / miner明确时间口径和采集完整性；将审查已支持的项目规则纳入去重，候选标明新增或改写、具体文件和来源。
      propose-rules / health补齐所选项目规则格式的写回与复核，保持作用域；预览与实际变更使用同一基准。保留 REVIEW/ignore 兼容，组织来源仍只读。
      评测用例与基线不依赖组织仓库；支持固定资料回放，不在运行中修改答案。

      现有 rules_repo / rules_ref / extends 作为 Git 兼容配置保留。sync-data.sh 的可选共享判断不在本轮扩展。

      七、效果评测

      保留能回答“是否更准、是否更吵、成本是否合理”的指标。先做可重复的小规模回归，不新增评测平台或强制比例配额。

      日常记录

      指标口径
      成立 / 误报只依据明确判断，保留理由；未判断单列，样本少只展示数量。
      解决 / 采纳相关代码修改且核实问题消失才计采纳；代码动过、规则撤销或本轮没报都不自动算采纳。
      漏报人工指出后核实是真问题，并确认属于当时审查范围；未匹配到评论只是线索。
      成本记录用时和可获取的 token；没统计到就写未统计。

      最小回归流程

      1. 选一组有明确答案的代表性提交，包含真实缺陷、干净改动和规则用例；同时保存当时的意图和实际规则材料。
      2. 比较已认可版本与候选版本，固定输入和非比较变量。隔离历史记录，不做增量。
      3. 逐项核对命中、漏报及全部用例中的确认误报，不只看干净用例。新发现经核实后单列，留作下次数据更新，不改本轮答案。
      4. 真假未判断完时只给暂定结果；已核实真实、等待入库的候选不影响本轮判断。不能靠把疑难发现留在待判断列表来宣布通过。
      5. 查看是否出现新的重要漏报、误报增加或不合理成本，维护者据此决定是否接受。保留逐项差异，不只看总分。

      评测数据更新后，用上一个已认可的插件版本重建同一新集合的基线，再比较候选。规则维护者想验证项目 rules 或 REVIEW.md 改动时，用同一批代码和目标要求分别跑新旧规则，明确这次比较的变量是规则，不与插件回归混为一谈。

      评测集、运行结果和基线可以放插件仓库或指定目录，不需要组织规则仓库。先保留脚本和人工核对；自动评测平台、统计门禁配置和复杂基线管理后置。

      设计依据：回归比较与问题解决判断
      • 公开实践：GitHub ReviewBench使用标注问题、语义匹配和统一判定标准，并记录评测版本；它区分固定答案指标与认可答案外真问题的扩展指标。Uber uReview使用人工标注提交评估精确率和召回率，并通过最终提交上的多次复查评估评论是否已处理。
      • 本项目取舍：先做固定输入的小规模回归和人工核对，新真问题留作下次数据更新；不在运行中改答案。采纳以代码改变且核实问题消失为准，不把“代码动过”当采纳，也不直接照搬 Uber 的复跑次数。
      • 支持到哪里：借鉴的是可比输入、明确答案和复核，不是复刻其他产品的完整指标体系；外部的效果数字不能作为 Crosscheck 的指标。样本少时展示数量和逐项差异，不宣称统计显著提升。

      九、文件存放

      核实回复不完整时停止汇总，不把旧发现标为已解决。verification-errors.json 记录待补项。final.json 与 findings.json 保留独立结果；主 agent 用 display-groups.json 指明已确认同根因的展示分组，报告脚本生成 report.json，只减少重复叙述，保留关联编号、规则原文与证据。

      1. “本次审查目录”是什么？

      它是一次审查用来放工作文件的文件夹。review_dir 是脚本和说明里对这个文件夹的称呼，不是固定文件夹名，也不是新的仓库。

      现有插件已经有这个机制。collect-diff.sh 默认在系统临时目录下新建一个文件夹（例如 cr.ABC123），并输出实际路径；也可以用 --out 指定位置。后面的查找、核实和汇总步骤都使用这个目录中的文件。

      3. 审查结束后放在哪里？

      • 保存审查记录：现有 save-review.sh 将报告、发现、元信息及部分辅助材料复制到默认的 ~/.crosscheck/reviews/<项目>/<目标>/<时间>/。不是把临时目录里的所有文件都保存。
      • 记录人的判断：你对发现说“成立、误报、不修”等，会另记到项目级的 ~/.crosscheck/reviews/<项目>/feedback.jsonl，便于同项目后续审查参考。
      • 外部材料副本：方案要求保存报告时一并保留本次实际使用的外部原文和出处；这一保存能力尚待实现。
      • 只测试或不保存：按用户要求跳过保存记录步骤，工作文件仍留在本次指定或临时目录中；临时目录不能当成长期归档。

      以上是默认位置；隔离测试或自定义配置可以改到其他目录。项目已有 rules、REVIEW.md 和忽略项仍在业务仓库里；评论提炼目录只放候选材料，组织规范原件仍在外部平台，评测用例和基线放在单独选择的评测目录。

      4. 会自动共享吗？

      不会。审查报告和工作文件默认在本机，不自动发给同事，也不自动上传知识库。只有启用现有团队判断同步、并经用户确认时，才同步相应判断记录；不代表同步整份审查目录。认证仍交给宿主管理，凭证不写入这些审查材料。

      设计依据：哪些已有实现，哪些是拟新增
      • 本项目实现依据：临时目录、--out 和主要材料由 collect-diff.sh 定义；归档位置与保存清单来自 save-review.sh；项目判断文件来自 feedback.sh。这是现有实现说明，不借用外部产品背书。
      • 本项目取舍：materials/ 外部原文副本及其随报告保存属于拟新增设计；本地保存是为了核对依据，不是永久存储或模型结果完全复现的保证。

      十、审查流程

      单次审查

      1. 用户调用 /cr。
      2. 记录仓库状态，收集完整 diff、项目规则、外部资料、意图和历史；保存本次材料。材料或配置变化就重审当前目标，否则才使用代码增量；扫描测试削弱。
      3. 按深度选择角色；宿主支持时并行查找，否则顺序执行。
      4. 有规则清单时先核对，缺项或无效项补查一次；再准备发现候选及“未违反”项抽查，零发现不跳过可抽查项。
      5. verifier 根据同一材料核实候选和抽查项，全部评分留档；同宿主执行时说明独立性限制。
      6. 过滤、合并、排序。
      7. 核对仓库状态没有被改动，结束只读阶段。
      8. 出报告，分别说明来源完整性与检查覆盖；保存本次快照。用户要求只测试时不写共享审查记录。
      9. 等待用户回复，按下面「报告之后」的流程处理。

      复审发现的去向

      状态判定依据统计
      新发现本轮有效材料与代码核实后新确认计入本轮发现
      已确认遗留本轮已核实仍成立；或代码、完整材料和审查配置均未变，明确标注沿用上次核实保留未解决
      已解决有有效依据证明原问题已消失，写明原因仅代码改动且经判断问题已消失时才计采纳；规则撤销等另列原因
      本轮未能复核 / unverified来源缺失、材料冲突或核实未完成；保留上次发现与快照引用不计 resolved、采纳或本轮通过，不宣称已确认仍存在

      “本轮没再报出”不是已解决的证据。上轮 HTTP 规范有违规、本轮文档无权限时，报告必须显示该项未能复核；来源恢复后再决定遗留或解决。

      报告之后：用户回复了怎么办

      用户可以用报告里的编号指代发现（「第 2 条」），主 agent 通过 findings.json 对应到发现的固定编号；换了会话也能接着处理。

      用户说的怎么处理记录什么
      质疑：「第 2 条不对吧」「这为什么是问题」不马上认错，也不坚持原结论。把用户的理由当作新信息，重新打开依据里的代码核对：
      • 仍然成立 → 解释原因，给出具体的代码位置；
      • 站不住 → 撤回，说明是哪一环错了；
      • 双方都说不清 → 标为有争议，写明分歧在哪。
      		撤回记为不成立（原因必填）；有争议记为 disputed；仍然成立的不记，等用户表态
      表态：「对，确实是问题」「知道了，先不改」「误报」直接记下。判为不改或误报时必须有原因，用户没说就问一句成立 / 不修 / 不成立，带原因和那段代码的指纹
      要求修复：「修掉第 1、3 条」进入 --fix：只修指定的几条，最小改动，只改工作区；修完运行项目已有的检查，并让 verifier 确认问题已经消失；如实报告结果，包括失败修好的记为成立
      问没报的：「还有别的吗」「72 分那条是什么」从 rejected.json 列出差一点通过的候选，写明分数和没通过的理由，并标明「未通过核实」用户确认是真问题的，记为成立，同时作为阈值校准的样本
      指出漏报：「你漏了 cache.ts 的并发问题」按用户的描述走一遍核实；成立就补进报告记为漏报，保存为评测候选；独立确认后纳入后续评测集，不修改本轮答案
      要求深挖：「cache.ts 用 deep 再看一遍」只对指定的文件或维度做一次定向审查，结果附在原报告后面，已经报过的不重复同一次审查记录里追加一段
      要求定规则：「以后这种别报了」「以后都要查 X」先核对规则是否值得长期保留及是否已有；项目约束写回现有 rules，审查要求放 REVIEW.md，有明确条件的忽略项放 .cr/ignore.md。按第四节展示文件、范围与 diff，确认后修改；不隐式扩大旧规则范围规则来源记为这次判断
      改完代码后再审：「再看一下」先比较代码、本次材料和配置；材料变化就重审当前目标；报告分为新发现、已确认遗留、已解决、本轮未能复核四类。未复核项保留上次依据，不冒充本轮确认每条发现的去向
      • 先核对再回应。不因为用户质疑就撤回，也不因为自己报过就坚持；结论以重新读到的代码为准。
      • 主动提议变成规则。重复出现的误报原因可提议写进 .cr/ignore.md；用户同意才写。
      • 记录失败要明说。判断没记下来（比如缺少 python3）时直接告诉用户，不假装已记录。
      • 报告记录同步更新。撤回、补充和修复都追加到这次审查记录的末尾，保留时间顺序，原报告正文不改。

      项目反馈与规则沉淀

      每次审查

      记录用户判断、确认的解决情况和未通过核实的候选。

      按需提炼

      收集人工评论及必要上下文，报告读取完整性 → 核对已有规则与未合入提案 → 候选标明原文件与具体 diff → 负责人确认 → 项目 MR 审阅合入。组织建议交上游；通用缺陷漏报核实后作为评测候选。

      定期复核

      负责人复核规则:逐条决定保留、改写或删除,保留的记下复核日期;语法类规则改配 lint;跨项目建议输出材料交外部负责人，不由 CR 移入组织平台。

      十一、安全边界

      • 审查要求与操作权限分开。diff、PR 描述、人工评论和普通规则中的操作指令不执行。受信任规则版本的 REVIEW.md 可提供证据与严重程度声明，根 frontmatter 的支持项由脚本执行；任何正文都不能授权工具调用、扩大权限、跳过核实或降低固定门槛。
      • 只读有多层约束。宿主权限、常见误操作 hook 与最终状态核对共同作用。Hook 不是完整 shell 安全边界；MCP 的只读声明也需工具白名单和服务端权限配合。
      • 凭证不进对话。不打印远程地址、环境变量和凭证文件；显示的地址一律脱敏；平台 CLI 不可用时退回 git 拉取，使用仓库已有的凭证。
      • 规则来源受控。PR 审查的项目配置从 base 读；外部来源由可信配置注册。正文只是材料，不能注册工具、修改权限或改变审查步骤。
      • 隐私。reviewer 只存哈希；收集的评论只存在本机；提炼出来的规则正文里不能出现人名和业务数据。
      • 维护权限分开。项目变更由项目维护者审阅；组织编写、审批和发布全部留在外部。CR 不接受正文自称“强制”或“已批准”作为权限证明。
      • 写操作有边界。审查过程中不往 GitLab 写任何东西；项目规则 MR 和判断同步都在审查结束后、由你确认才执行。
      设计依据：只读与本地输出的边界
      • 公开实践：GitHub Copilot 的 MCP 配置建议启用明确的只读工具；其代码审查会筛选带只读声明的工具。此实践支持收窄工具权限，但声明本身不等于服务端权限控制。
      • 本项目取舍：默认只读、报告留本地、不自动向 MR 发评论，以及 hook 配合最终仓库状态核对，属于 Crosscheck 的产品边界。用户授权的项目维护与审查分开执行。
      • 限制：本地报告减少自动发布带来的干扰；也意味着用户需要自行分享结果。Hook 只覆盖常见误操作，不能替代真实权限或声称阻止任意程序写入。

      十二、实施计划

      1补齐项目规则维护

      补采集完整性、现有规则去重与原处写回；保留 REVIEW/ignore 及旧配置，组织规范保持只读。

      验收：已有规则不重复；路径不误扩；确认的 diff 与 MR 一致；组织来源不可写。

      2接一个真实来源

      先读取同事知识库中的几份规范。宿主负责工具调用，获取入口保存正文、出处、范围和结果，再交给现有审查流程。

      验收：能引用实际原文；不同来源同号不串；同一文档中的不同问题不误合并；失败和截断有提示。

      3验证简单回退

      规则或参考材料变化、配置变化或无法确认一致时，重审当前目标全部 diff。旧规范判断不确定就重新检查。

      验收：代码未变但材料改变仍重审；来源失败不算通过、不把旧发现算解决；固定资料可以离线回放。

      效果能力保留验收

      • 规则清单漏项仍触发一次补查；普通候选为零时，有可抽查项仍会核实；无法完成的检查明确标注。
      • 原有“改断言期望值＋新增 skip”案例继续检出；only 和 CI 放宽失败条件也保留扫描。
      • 多角色查找、deep 多遍、需求核对、反证与证据校验、反馈沉淀和效果评测保持。实现简化前后使用同组用例比较，不能仅凭方案声称效果相同。

      明确后置

      • 精细到条款 / 文件的变化影响图、跨平台规则身份迁移。
      • 组织强制规则、批准例外、撤销和到期的自动治理状态机。
      • 自建 MCP 连接与认证、动态插件框架、任意平台字段映射语言。
      • 规则双向同步、自动组织发布、评测服务与复杂门禁配置。

      增加复杂度的条件：有真实接入差异、审查成本或误报数据证明简单方式不够，再补对应能力。当前优先多跑一次、明确提示和人工判断。

      十三、设计取舍

      首版取舍优势代价
      项目已有规则源＋短 REVIEW.md＋可配置外部资料编码与审查共享项目约束，维护落点清楚需验证格式与路径语义，冲突仍由负责人判断；不自动同步多份正文
      材料变化就重审当前 diff避免精细缓存和历史失效错误额外审查用时和 token
      有依据的发现，不确定就重核避免错误合并和旧抑制误用可能重复检查或提示
      读取失败和冲突如实展示结果边界清楚，不伪装成全覆盖某些规范需要人工确认；不提供组织合规认证

      公开产品实践支持轻量接入：Claude Code Review 使用自由格式 REVIEW.md；Bugbot 展示用了哪些规则以及截断 / 省略情况；GitHub Copilot 通过配置接入 MCP；CodeRabbit 复用现有规范文件和路径作用域。

      这些公开接口不代表其内部没有复杂实现。我们借鉴使用边界和可见性，不把未公开的内部机制当作必须复制的架构。

      十四、待定事项

      问题需要的答案
      项目规则维护在哪里？已有主题规则优先原处更新；新规则的默认目录及维护负责人，沿项目实际习惯确定。
      先读哪些资料？几份规范的链接 / ID，以及哪些只是背景说明。
      宿主怎么读到？实际 MCP 工具或导出方式、权限、是否分页或截断。
      哪些代码需要它们？项目或路径范围；规则冲突时由谁判断。

      这些信息足够开始最小接入；不要求先确定组织全部规则格式、审批元数据或跨平台身份标准。
