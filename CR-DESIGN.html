crosscheck CR 方案

一套在本地运行的 AI 代码审查方案：多个专项角色查找问题，由独立的 verifier 核实，只报告经得起核实的发现；把人的判断和人工评审持续沉淀成规则，规则分层维护、有完整的生命周期；每一项调整都用评测来衡量。

流程演示

按角色分成五条流程：开发者审查一次改动，项目负责人每月沉淀规则和定期复核规则，规则包负责人发版，插件维护者跑评测。文件名、分数和结果都是演示数据；可以用左右方向键切换步骤。

      一、原则与边界

      设计原则

      1. 精确率优先。两条真实发现好过十条里错三条。作者看到几条错误评论后就不再认真看其余的，报告为空是正当结果。
      2. 查找和核实分开。查找负责不漏，核实负责不错；verifier 只看到结论，看不到查找者的推理。
      3. 确定性的工作交给脚本。取 diff、算行范围、找规则、拉 MR 信息由脚本完成，结果可复现；agent 只做判断。
      4. 宿主无关。同一套流程在 Claude Code、Cursor、Codex 中运行，宿主专属机制只做增强。
      5. 每项调整都可衡量。改提示词、阈值、流程之前先跑评测，没有数据不改。
      6. 知识必须经过人审。机器只产出候选规则；生效要人批准，生效后持续统计、到期淘汰。
      7. 信号都要回流。人的判断、人工评论、漏报、被否决的候选，最后都进入规则或评测集。

      不做什么

      • 不追求召回率。会漏报，这是有意的取舍。
      • 不替代编译器、类型检查器、linter 和 CI，它们能拦住的问题不报。
      • 不审查改动之外的存量代码，不做风格和品味上的评判（除非项目写成了规则）。
      • 不往 PR/MR 发评论，不 approve、request changes、merge，结果只在本地输出。
      • 默认不改文件，只有用户明确要求时才修复，且只改工作区、不提交。
      • 审查过程中从不往 GitLab 写任何东西。只有两种写操作，而且都要你确认：提交规则改动的 MR（只创建、不合并），以及同步共享的判断记录。

      三、各层设计

      1. 入口层：怎么使用

      不需要记参数。直接用平时说话的方式告诉它审什么、审多细、审完要做什么；下表右列的参数只是熟练之后的简写，用不用都行。说法有歧义时（比如「看看 128」分不清是 MR 还是 Issue），它会先问一句再开始。

      审什么

      你想审的可以这样说简写
      当前分支的全部改动，包括还没提交的「review 一下」「帮我看看这次的改动」/cr
      另一个分支（不用切过去）「看看 feature/pay 分支」/cr feature/pay
      一个 MR「review MR 128」，或者直接贴 MR 链接/cr 128
      某几个提交「看看最近 3 个提交」/cr HEAD~3..HEAD
      某个目录下的改动「只看 src/orders 下面的改动」/cr src/orders

      审多细（什么都不说就是标准深度，适合大多数情况）

      你想要的可以这样说会怎样简写
      快速过一遍「快速看一下」「简单过一遍」只查 bug 和安全问题，最多报 5 条，最快--quick
      上线前仔细审「仔细看看」「上线前深度审一下」换个顺序多查几遍，并尝试写脚本复现问题；明显更慢、更贵--deep
      只关心某一方面「只看安全问题」「只对照一下团队规范」只启动对应的角色--only security
      连测试一起看「测试也一起看」测试文件也按缺陷审查（默认只检查测试有没有被削弱）--with-tests
      从头完整审一遍「重新审」「全量审一遍」忽略上次的记录。默认只看上次审过之后变了的文件--full

      补充背景（可选，能让结果更准）

      你想告诉它的可以这样说简写
      这次改动想做什么「这次是为了修复分页丢数据」--intent "…"
      方案或计划写在哪「方案在 docs/plan.md」--plan docs/plan.md
      核实用哪个模型「核实换成某某模型」--verifier-model …

      审完之后：直接回复就行，比如「第 2 条不对，上游已经校验过了」「把第 1、3 条修掉」「以后这种别报了」。各种回复怎么处理，见第九节「报告之后」。修复只有你明确要求时才做（简写 --fix），只改工作区、不提交。

        • 不检出、不切分支：被审查的代码不在工作区时，一律用 git show / git grep 从目标 ref 读取。

        • 算出每个文件新侧的改动行范围（ranges.txt），发现只能落在这些行上。
        • 大改动按路径顺序切成约 1000 行一批，每批独立审查。
        • 增量：同一目标再审时，按文件 diff 的哈希只看变了的文件；并用 git grep 找出引用了被改符号、但自身没变的文件，一起重审。
      • 意图：这次改动想做什么、验收标准是什么、哪些行为变化是刻意的。来源和用法见本节末尾的「意图收集」。
      • 规则装配（collect-rules.sh）：
        • PR/MR 模式下从 base 分支读取规则文件，PR 改不了自己的审查设置。
        • 按第五节的分层合并：读取 REVIEW.md 头部的 extends 和 disable，装配组织规则包，处理覆盖关系。
        • 解析规则编号，交给 rules-auditor；把组织规则仓库当时的 commit 记进 meta.txt，保证结果可复现。
      • 历史判断：把这个项目里对相关文件做过的判断（不成立、不修、有争议、成立）连同「那段代码现在是否原样还在」写进 history.json，交给 verifier。
      • 测试削弱扫描，产出 weakening.txt：
        • 删掉的测试文件或断言；
        • 新加的 skip、xit、@Disabled、t.Skip；
        • 调低的覆盖率阈值；
        • 新增的 ts-ignore、eslint-disable、nolint；
        • CI 配置里删掉的检查步骤。
      • 风险分级，产出 risk.txt，只用确定性的信号：命中 REVIEW.md 声明的高风险路径、迁移文件、鉴权和支付相关路径、diff 大小、是否有测试削弱。用户没指定深度时据此建议深度，只建议、不强制。

      意图收集

      没有意图，审查只能判断代码「有没有写错」，判断不了「有没有做对」，也分不清哪些行为变化是作者刻意的。业界的做法大致分三类：

      • PR 描述和提交说明：所有工具都读。Augment 引用的评测里，不提供问题描述时错误建议的比例大约翻倍。
      • 关联的需求单：CodeRabbit 和 Qodo 从 PR 描述里的链接或编号（如 Closes PROJ-123）找到 Jira、Linear、GitHub Issue，读取标题、描述、验收标准和子任务，把「没做到的需求」作为发现报出来；Qodo 还可以标出和需求无关的改动，但默认关闭。
      • agent 的计划和决策记录：代码越来越多由 agent 写，推理过程在会话里，PR 上看不到。Warp 等建议把原始需求、计划、执行过的命令和验证结果附到 PR 上；这方面还没有通用的格式。

      crosscheck 按下表收集，脚本汇总成一份 intent.md：

      来源收集什么怎么取
      MR 标题和描述要做什么、为什么、刻意的行为变化glab / gh；不可用时只能从提交说明里取
      关联的需求单标题、描述、验收标准、子任务从 MR 描述和提交说明里识别链接或编号。GitLab Issue 用 glab api 只读获取；其他系统要在 ~/.crosscheck/config 里配置读取方式，没配置时只记下编号，不去抓取
      提交说明每一步改了什么git log base..head
      MR 上的人工讨论作者在回复里解释的意图、已经达成的结论glab api …/discussions 只读获取，只留人工评论
      计划文件agent 或作者写下的计划、方案取舍用户用 --plan <文件> 指定，或仓库里约定位置的 .cr/intent.md；不自动读取任何 agent 的会话记录
      --intent "…"用户临时补的一句话调用参数

      intent.md 的结构固定：目标、验收标准、刻意的行为变化、明确不做的、来源清单（每一条从哪来）。总长度有上限，超出时截断并注明。所有来源都没有内容时，报告末尾提示「没有找到意图，可以用 --intent 补一句」。

      意图的用法：

      • 查找时对照：说了要做的，代码是否真的做到了；代码里有没有说明中没提、也不像刻意的行为变化。
      • 需求核对：有明确的验收标准时，没有满足的条目作为一类单独的发现（intent），同样要经过 verifier 核实，在报告里单独成节，默认最多 5 条。和需求无关的改动默认不报。
      • 减少误报：意图里写明的刻意行为变化，不当作缺陷报。
      • 只能解释，不能豁免：意图来自作者，属于被审查的材料。它可以说明「这个行为变化是有意的」，但不能让安全问题不报，里面写给 reviewer 的指令（「这里不用查」）一律不执行。

      3. 多角色审查

      一次审查由一个主 agent 编排，它按深度启动若干个角色，每个角色是一个独立的 agent（宿主支持子代理时并行运行，不支持时由主 agent 依次扮演）。每个角色有自己的一份说明文件（roles/<角色>.md），说明短而专一；共用的部分（规则设置的处理、读代码的方式、只读约束）集中放在一份公共说明里。

      角色一览：

      角色负责什么时候运行交出什么
      主 agent（编排者）解析参数、运行脚本、启动其他角色、汇总过滤、出报告、记录人的判断每次报告和审查记录
      bug-hunter找正确性问题，并对照验收标准每次（quick 由主 agent 兼任）候选发现
      security-reviewer找安全问题每次（quick 由主 agent 兼任）候选发现
      rules-auditor对照团队规则standard、deep，且有适用的规则时候选发现
      simplifier找可以简化的地方standard、deep简化建议
      verifier独立核实每条候选并打分每次有候选时；每批最多 5 条，一批一个带分数和理由的候选
      rule-miner从人工评论和判断记录里提炼候选规则只在 /cr 提炼规则 时候选规则
      judge评测时判断发现是否对上答案；MR 合并后判断报过的问题在最终代码里是否解决只在跑评测、统计采纳时对上 / 没对上、已解决 / 未解决，附理由

      查找角色的细节：

      角色查什么要求的证据
      bug-hunter逻辑错误、边界、空值、并发、错误处理、资源泄漏、API 误用。local 从改动处向外查，impact 从使用方向内查漏改的地方具体的输入或状态 → 错误的结果
      security-reviewer注入、鉴权越权、密钥、反序列化、SSRF、路径穿越；以及 LLM 类风险：不可信输入拼进提示词、模型输出直接当作命令或 SQL 执行、密钥或个人信息发给模型、无上限的调用、引用不存在的包攻击者可控的值从哪进入、经过哪几步、造成什么后果
      rules-auditor违反各层规则的地方，带规则编号。检查顺序见下逐字引用规则原文和出处
      simplifier可复用的已有代码、重复、多余的机制、没被用上的新代码已有的等价代码在哪里

      rules-auditor 的检查顺序：

      1. 先读会改变审查方式的部分。REVIEW.md 里的审查设置（跳过的路径和类别、严重程度、证据要求），以及 .cr/ignore.md 的抑制条目。被抑制的内容后面一律不报。
      2. 按层读规则，越具体越先。目录级 REVIEW.md → 项目级 REVIEW.md → 组织规则包（只读 extends 引用、且没被 disable 的）→ 外部规则（CLAUDE.md、AGENTS.md 等）。同一件事几层说法不同时，以先读到的、更具体的那层为准。
      3. 筛出这次要查的规则。只留作用域覆盖改动文件、并且能对照代码检查的条目：命名、必须用或禁止用的 API、错误处理约定、代码放在哪里、必须同步修改的地方、日志里不能出现的内容。怎么跑测试、用哪个包管理器这类操作说明跳过。
      4. 逐个改动文件对照改动行。只看这次 diff 改到的行；只凭 hunk 判断不了时打开整个文件。改动行明显违反规则的字面才报，要引申才能套上的不报。
      5. 查反证。违反处有针对同一条规则的抑制注释（如 eslint-disable-next-line、nolint、noqa）→ 不报；同一模块里大量现有代码都和规则反着写 → 不报违规，改为提示「规则可能过时」。
      6. 合并后交出。同一条规则在同一个文件里的多处违反合并成一条，写明共几处、在哪几行；每条带规则编号、原文和出处，交给 verifier 核实。同时交出检查清单，由脚本核对有没有漏掉的规则（见第五节「确保审查时真的用上规则」）。

      深度：

      深度查找核实
      quick主 agent 一次完成 bug 和安全主 agent 自己核实
      standard四个角色并行，大改动按批次运行verifier 子代理，只读代码
      deep再加倒序的 bug-hunter、impact 视角的 bug-hunter、倒序的 security-reviewer；同一候选被几遍查到记为命中次数（不传给 verifier）verifier 可以写最小脚本复现，或运行项目已有的类型检查和测试

      核实：

      • verifier 只拿到符合结构的候选，不拿到查找者的推理，先尝试推翻，再按评分标准打分。
      • 按顺序执行封顶检查：不在改动行上、base 版本就有、有守卫使其不可达、代码没被用上、CI 会拦住、命中历史判断或误报清单等，第一条适用的决定分数上限。
      • 候选带 needs_check 时，先核对那一环。
      • verifier 的模型按用户调用时指定（--verifier-model），默认和当前宿主同一个模型；实际使用的模型记进 meta.txt，便于按模型对比评测结果。
      • 打分必须附依据：核实时读过、能支撑结论的代码位置（文件:行）；排除了哪些可能（守卫、调用方、base 版本是否已有）；deep 模式下的复现命令和结果。脚本会检查依据里引用的位置在被审查的那一版代码里真实存在，引用不存在的依据作废，这条最高 50 分。
      • 每条候选的分数都留档：80 分以上进报告，其余写进 rejected.json，用于校准阈值。

      汇总：同一位置同一缺陷的候选合并；丢弃 80 分以下和不在改动行上的；缺陷、规范、简化各自计数上限（默认 10 / 5 / 5，REVIEW.md 可调整）；按严重程度和置信度排序。

      4. 输出层

      • 报告：开头一张概览表；每条发现包含位置、问题代码原文（由脚本从被审查的那一版摘取，带行号）、失败场景、修复建议（能确定时用 diff），必要时附兼容性说明和之前的判断。
      • 每条发现都附依据，默认折叠，展开可以核对：置信度分数、核实时读过的代码位置、排除了什么、复现的命令和结果（deep 模式）、由哪个角色查到。rules 发现另附规则编号、原文和出处；security 发现另附攻击路径的每一步。读报告的人不用重新查一遍，就能判断这条站不站得住。
      • 分节：缺陷、需求核对、规范、可简化、测试削弱各自成节；末尾注明意图取自哪些来源；因历史判断而没报的折叠列出，可以核对。
      • 末尾：查了哪些维度、深度和范围、跳过了多少文件、本次消耗、记录的链接。
      • 记录：报告、发现、被否决的候选、元数据保存到用户目录，下一次审查据此做增量。
      • 只在本地输出，不往 PR/MR 发任何内容。
      • --fix：只应用通过核实的发现，最小改动，只改工作区、不暂存不提交，修完运行项目已有的检查并如实报告结果。

      5. 私有化 GitLab

      支持私有化部署的 GitLab。和代码托管平台有关的设置都写在 ~/.crosscheck/config 这一个文件里：

      # ~/.crosscheck/config
gitlab_hosts=code.company.com            # 按 GitLab 处理的域名,多个用逗号分隔;部署在子路径时写成 company.com/gitlab
rules_repo=https://code.company.com/eng/crosscheck-rules.git
rules_ref=v1.4.0
data_repo=https://code.company.com/eng/crosscheck-data.git  # 可选:共享人的判断
      环节怎么处理
      识别平台按顺序判断：--platform 参数 → 环境变量 CR_PLATFORM → 配置里的 gitlab_hosts → 域名里含 gitlab → MR 链接里含 /merge_requests/。都判断不了时报错，并提示在配置里加上域名
      登录用 glab auth login --hostname code.company.com 登录一次，token 由 glab 自己保存；crosscheck 不读取、不保存 token
      没有 glab 或没登录改用 git fetch origin merge-requests/<编号>/head 拉取代码，用的是仓库已经配好的 git 凭证。代码照常审查，但拿不到标题、描述、人工讨论和关联的需求单，报告里会注明
      自签名证书由用户在 glab（ca_cert 或 skip_tls_verify，按域名设置）和 git（http.sslCAInfo）里配置；crosscheck 不修改这些设置
      内网访问运行环境要能连上 GitLab。在沙箱或连不上内网的环境里，脚本会直接说明拉取失败的可能原因，不反复重试
      部署在子路径例如 https://company.com/gitlab/group/proj：在 gitlab_hosts 里写成 company.com/gitlab，解析 MR 链接时先去掉这段前缀，再取项目路径
      API 版本只用 REST API v4 的只读接口：MR 信息、diff 基准、讨论、Issue
      同一个 GitLab 上的其他东西组织规则仓库、关联的 GitLab Issue、MR 上的人工讨论都复用同一个登录，不需要分别配置

      四、反馈沉淀

      把审查中产生的反馈（人的判断、人工评论、漏报、差一点通过的候选）整理成规则和评测用例。不训练或微调模型，只改规则和评测集。业界对应的做法：Cursor 的 learned rules、字节的数据飞轮、Qodo 的 auto best practices、CodeRabbit 的 learnings。

      信号来源

      编号信号来源用途
      S1人的判断（成立 / 不成立 / 不修 / 有争议），必须带原因feedback.jsonl反复出现的「不成立」原因 → 候选的「不要报告」条目
      S2MR 上的人工评论mine-reviews.sh候选的「每次都要检查」条目
      S3漏报：人工评论指出了、crosscheck 没报的对比 S2 和当时的 findings.json进评测集，也可以生成候选规则
      S4采纳：报告之后那一行代码被改了审查记录里每条发现的去向衡量规则和类别的价值
      S5差一点通过的候选（70–79 分）rejected.json校准阈值

      规则的生命周期

      candidate 人批准 active 负责人复核后不要 deprecated 确认 retired
      candidate：证据不足，90 天后过期 active：语法类规则 → 改成 linter 规则（毕业）

      生成

      rule-miner 角色把信号聚类成候选规则，每条必须同时满足：

      • 能对照代码检查；
      • 至少 3 条证据，来自至少 2 个 MR、至少 2 位 reviewer；
      • 写明作用域；
      • linter 能查的、模型本来就知道的通用常识，都不收。

      批准、统计、淘汰

      候选经用户确认后写进对应层级的规则文件。之后由负责人定期复核决定去留,见第五节。

      五、规则分层与维护

      一句话：规则放在离代码最近、又能被复用的那一层；每条规则都有编号、作用域、来源和负责人；由负责人定期复核决定它的去留，而不是只增不减。

      1. 分层

      从上往下越来越具体，生效优先级越来越高；下层可以按编号关掉上层的规则。

      层级位置放什么不放什么谁来改
      L0 插件内置references/、roles/审查方法本身：检查方向、误报清单、评分标准任何具体的编码约定插件维护者，评测不回退才合入
      L1 组织级GitLab 上的独立规则仓库，地址写在 ~/.crosscheck/config，同步到本地使用内部框架和公共库的用法、平台规范（RPC、配置中心、日志）、跨项目踩过的坑模型本来就知道的语言常识；linter 能查的每个规则包一个负责人（CODEOWNERS）
      L2 项目级仓库根目录的 REVIEW.md只有这个项目才有的约定：必须同步修改的地方、领域不变量项目背景、怎么跑测试（放 CLAUDE.md / AGENTS.md）项目维护者，走 MR
      L3 目录级子目录的 REVIEW.md只对某个模块成立的约定和根目录重复的内容模块负责人
      抑制.cr/ignore.md团队明确不想再被提醒的模式（反向规则）一次性的例外项目维护者
      外部规则CLAUDE.md、AGENTS.md、Cursor / Copilot 规则等由别的工具的使用者维护，crosscheck 只读：只取能对照代码检查的条目，不改写、不分配编号，按引用原文的哈希做统计不归 crosscheck 管
      候选GitLab 上带 crosscheck-rule 标签的 MR（改 REVIEW.md、.cr/ignore.md 或规则包）提炼出来、还没批准的规则—机器生成，你确认后创建 MR；项目维护者或包负责人在 GitLab 上审批；合入前不生效

      每一层都是可选的。一条规则都没有时，审查照常进行：bug、安全、简化三个维度不依赖规则，只是少了「对照团队约定」这一项。缺了某一层时的表现：

      缺什么会怎样
      所有层都没有不启动 rules-auditor，报告里没有「规范」一节，审查更快、更省；末尾写「没有找到适用的规则」。规则检查清单的核对视为通过，不会报错
      没配置组织规则仓库跳过 L1，其余照常；报告末尾注明
      配置了仓库，但项目没写 extends不装配任何组织规则包（显式引用才生效），其余照常
      没有 REVIEW.md用默认的审查设置：默认的跳过规则、严重程度定义和条数上限（缺陷 10、规范 5、简化 5）；风险分级只用迁移文件、敏感路径和 diff 大小这些通用信号
      只有 CLAUDE.md 这类外部规则rules-auditor 照常运行，从中挑出能对照代码检查的条目
      没有 .cr/ignore.md不抑制任何模式，误报清单和历史判断照常生效

      反馈沉淀不依赖已有规则：从判断记录和人工评论里提炼出的第一批候选，经批准后就成为项目的第一份 REVIEW.md。「没有找到适用的规则」的提示只在报告末尾写一行，并说明可以从哪里开始，不会反复打扰。

      2. 各层怎么维护

      所有层共用同一条流程：提出 → 写入前检查 → 有人审 → 合入生效 → 负责人定期复核。各层的区别在谁来审、什么时候生效、怎么删。

      层级谁维护怎么改什么时候生效怎么删多久看一次
      L0 插件内置插件维护者改 references/、roles/；合入前必须跑 /cr 评测，召回不降、误报不升；写进插件的 CHANGELOG用户更新插件之后同样要过评测每次发版
      L1 组织级每个规则包的负责人（CODEOWNERS）任何人往规则仓库提 MR → CI 跑 rules-lint(格式、编号、负责人、正反例是否齐全)→ 包负责人审批合入 → 打 tag 发版并写 CHANGELOG各人的 rules_ref 指向新 tag、运行 sync-rules.sh 之后先标为 deprecated 发一个版本：规则不再生效，报告里提示即将删除；下个版本再删。编号不复用每季度,包负责人复核
      L2 项目级项目维护者在项目里提 MR 改 REVIEW.md；本地先跑 rules-lint.sh，也可以放进项目 CI合入默认分支之后（PR/MR 审查从 base 分支读）。本地审查自己的分支时，工作区里的修改立即生效，方便试用直接删，MR 里写明原因；编号不复用每季度复核(/cr 规则复核)
      L3 目录级模块负责人同 L2，只写这个目录特有的约定同 L2同 L2；模块被删除或搬走时，复核清单会提示作用域已失效随 L2 一起复核
      抑制项目维护者多数来自「不成立」的判断：用户同意后追加到 .cr/ignore.md，每条写原因和日期，走 MR同 L2复核时由负责人判断是否还需要随 L2 一起复核
      外部规则那个文件原本的维护者（不归 crosscheck 管）crosscheck 不改这些文件。审查时只报告问题（可能过时、和 REVIEW.md 冲突、只和审查有关），建议去原文件修改，或把只和审查有关的条目挪进 REVIEW.md原文件改了就生效由原文件维护者决定不在复核清单里,由原文件维护者负责
      候选机器生成；项目维护者或包负责人审批提炼出候选后列给你看，你选中的生成一个带 crosscheck-rule 标签的 MR，分配好正式编号；L1 的候选提到规则仓库。没有 glab 时生成分支和 diff，由你自己推送MR 合入之后，和目标层相同90 天没人处理的 MR 提醒关闭；被关闭的 MR 写明原因，rule-miner 下次读到就不再提同样的候选每月提炼之后集中处理一次

      3. 组织规则仓库：位置与结构

      放在 GitLab 上的一个独立仓库里。仓库地址不写死在插件或各个项目里，统一写在一个单独的配置文件里，以后换仓库、换分支只改这一处：

      # ~/.crosscheck/config
rules_repo=https://code.company.com/eng/crosscheck-rules.git     # 规则仓库地址,不要带账号和 token
rules_ref=v1.4.0                                                 # 跟踪的 tag(也可以写分支)
rules_dir=~/.crosscheck/org-rules                                # 本地克隆的位置(可省略)
      • 同步：sync-rules.sh 第一次克隆、之后 git fetch 到 rules_ref。用本机已经配置好的 git 凭证，脚本不读取、不打印凭证，显示地址时去掉账号部分。审查开始时如果本地副本超过一天没同步，提示一句，不自动拉取。
      • 覆盖：环境变量 CROSSCHECK_RULES_DIR 优先于配置文件，方便临时指向一个正在修改的本地副本，在合入前先试用新规则。
      • 没配置时：跳过 L1，只用 L2 和 L3，报告末尾注明「未配置组织规则仓库」。
      • 负责人：写在规则仓库自己的 CODEOWNERS 里，每个规则包一个负责人；规则变更走这个仓库的 MR。

      仓库内的结构参考了几种成熟的做法：Semgrep 规则库（每条规则配正反例，用测试保证规则不退化）、ESLint 共享配置（项目用 extends 引用，版本加 CHANGELOG 发布）、Cursor / Claude Code / Copilot 的规则文件（每个文件用头部声明适用范围）。

      做法为什么
      按负责人划分目录，一个包一个目录CODEOWNERS 按路径生效，目录就是负责的边界；包不会因为没人管而变成规则堆
      一个包一个 rules.md，每个包不超过 20 条规则是给模型读的，按包装配进上下文；一条规则一个文件会让装配和阅读都变碎
      每条规则配正反例MR 上的 CI 检查每条规则的正反例是否齐全;「反例应该被报出来、正例不应该」需要模型判断,由插件维护者跑评测时检查(每对正反例都是一个评测用例)。这样改写规则时能发现它是不是变得过宽或失效
      头部写 applies_to和 Cursor、Copilot 的规则文件一样按路径生效，改动不涉及的包不装配，节省上下文
      打 tag 发版并写 CHANGELOG项目跟踪的是 tag，不是 main 的最新提交；规则变更有记录，出问题可以回退
      MR 上跑 CI编号重复、缺负责人、缺正反例的规则合不进去
      提供 REVIEW.md 模板新项目一开始就有 extends 和推荐的写法

      4. 合并与冲突

      • 优先级：L3 目录级 > L2 项目级 > L1 组织级；抑制（.cr/ignore.md）对所有层生效。
      • 下层和上层说法不一致时，以下层为准，并在报告末尾提一句「项目规则覆盖了 ORG-xxx」。
      • 同一层里互相矛盾时，两边都不报，在报告末尾提示。
      • 外部规则和 REVIEW.md 矛盾时，以 REVIEW.md 为准。
      • 只有 REVIEW.md 可以调整审查本身（跳过、严重程度、条数、证据要求），并且不能取消核实、不能降低阈值、不能触发修改或往外发内容；其他规则文件里指挥审查的文字一律不采用。

      5. 确保审查时真的用上规则

      规则没起作用有两种情况：没读到（没装配进来、没交给角色、角色没打开）和读了没用上（规则太多被稀释、被跳过）。只在说明里写「请先读规则」保证不了。业界的做法是不让 agent 自己去找规则：Anthropic 把 REVIEW.md 的内容直接交给查找和核实的 agent；CodeRabbit 在每条评论发出前，按路径加载适用的规则；Cursor 的规则作为额外指令注入。crosscheck 在此基础上再加一层核对，分六步保证：

      保障怎么做防的是什么
      1. 装配交给脚本collect-rules.sh 按分层和作用域算出这次适用的规则，额外输出一张适用表 rules-index.tsv：每条规则的编号、所在层、原文的哈希、覆盖了哪几个改动文件。哪些规则必须检查由脚本决定，不由 agent 判断没装配进来、作用域算错
      2. 规则直接放进任务脚本为每个角色生成任务文件，适用的规则原文直接写在里面，排在 diff 之前；REVIEW.md 里「每次都要检查」的条目放在最前面。规则少而准：只装配作用域命中的包，每个文件不超过 20 条角色没打开规则文件、规则太多被稀释
      3. 能用脚本执行的设置不交给 agentREVIEW.md 头部用固定格式写跳过的路径、条数上限、按规则编号指定的严重程度，由脚本直接执行：跳过的路径在收集 diff 时就排除，上限和严重程度在汇总时套用。正文里的文字说明仍然交给 agentagent 忘了跳过某个目录、没按团队的严重程度定级
      4. 交检查清单，脚本核对rules-auditor 除了发现，还要交一份清单：适用表里的每条规则，对哪些文件检查过，结果是违反、没违反还是不适用（不适用要写原因）。check-rules-coverage.sh 对照适用表核对，有遗漏就只针对漏掉的规则补跑一次；仍然漏掉的，在报告里列为「未检查」规则被悄悄跳过
      5. 引用由脚本核对每条 rules 发现带规则编号，引用的原文由脚本对照规则文件逐字核对；编号不存在、引用对不上、作用域不覆盖这个文件的，直接判为 0 分，不进报告编造规则、张冠李戴
      6. 评测里放规则用例组织规则包里每条规则的反例和正例进入评测集：反例必须报出对应编号，正例不能报改了提示词或换了模型之后，规则检查悄悄失效

      REVIEW.md 头部的固定格式（正文照常用文字写）：

      怎么知道 agent 真的读了。检查清单是 agent 自己交的，可能照着规则列表填满却没认真看，所以还需要不依赖 agent 自述的证据。分「读到」和「用上」两层看：

      要确认的证据能确定到什么程度
      读到了：规则确实进了角色的上下文派发任务时检查。脚本给规则块加一个本次审查的指纹（规则内容的哈希）。主 agent 启动 rules-auditor 和 verifier 时，宿主的 hook 检查任务内容里有没有这个指纹；没有就拒绝启动，并提示「任务里缺少规则，请按任务文件原样转交」确定。规则写在任务里，角色一定能看到。需要宿主支持在启动子代理前运行 hook，Claude Code 支持；其他宿主视 hook 能力而定
      核对码。脚本在规则列表的最末尾放一个本次随机生成的核对码，角色交清单时必须带上它。核对码对不上或缺失，说明规则没读到底（被截断或跳过了后半部分）较强。agent 无法事先知道核对码
      用上了：规则真的被拿去对照代码清单里要有证据。每条「没违反」都要写检查了哪些行，脚本核对这些行确实在该规则作用域内的改动范围里；「不适用」要写原因提高造假成本，不能完全排除
      抽查。verifier 从「没违反」里随机抽几条独立复查（deep 模式抽得更多）。抽查发现了违反，就说明这次的规则检查不可靠：对漏掉的规则重跑一次，并在报告里注明能发现系统性的敷衍
      评测。评测里每条规则的反例必须报出来;人工评审指出过、crosscheck 却没报的规则问题,会作为漏报进评测集能发现某条规则长期没起作用

      「读到」可以用机制保证；「用上」只能做到漏检会被发现，没办法百分之百证明模型认真用了每一条规则。所以报告里会如实写出验证到了哪一步。

      报告末尾会写出规则的使用情况和验证状态：

      规则:适用 14 条(组织 8 · 项目 6),已检查 14 条,违反 1 条
验证:任务含规则 ✓ · 核对码一致 ✓ · 抽查 3 条无异常 ✓
未检查:无

      没有安装 hook 时，前两项做不到，会写成：

      验证:任务含规则 未验证(未安装 hook)· 核对码一致 ✓ · 抽查 3 条无异常 ✓

      外部规则（CLAUDE.md 等）没有编号，核对粒度是文件：每个适用的外部规则文件都要在清单里出现，并列出从中挑出了哪几条能对照代码检查的条目。

      7. 规则从哪里来

      人工直接写

      团队发现某类问题反复漏掉或反复误报时，直接改 REVIEW.md，走 MR。

      来自判断记录

      同一类发现被判为不成立 2 次以上，建议写进 .cr/ignore.md；反复被判为成立的同类问题，建议写成「每次都要检查」的规则。

      来自人工评论提炼

      第四节的 rule-miner 产出候选，用户确认后写入。默认写进 L2；在多个项目里都出现的，建议直接进 L1。

      不管从哪条路来，工具都不会合入规则：审查后顺手定的单条规则，改到工作区，由你检查后自己提交；每月批量提炼的候选，在你确认后创建一个带 crosscheck-rule 标签的 MR（只创建、不合并），由项目维护者或包负责人在 GitLab 上审批。

      8. 写入前的检查（rules-lint.sh）

      确定性的部分由脚本检查，语义判断由 agent 补充。

      • 脚本：编号存在且唯一；组织规则包有负责人和正反例；scope 至少匹配到一个现有文件；单个 REVIEW.md 不超过 20 条；disable 都写了原因；extends 引用的包存在。
      • agent：和现有规则是否重复（包括其他层）；是否能对照代码检查；是不是 linter 就能查的（是的话建议改配 lint 规则）。

      9. 负责人定期复核

      不靠统计指标。规则的去留由负责人定期主动复核决定。原因有两个:命中次数来自各人本机的审查记录,要统计全团队就得把记录集中起来,本地工具做不到、维护成本也高;更重要的是,一条规则长期没被报过,可能是没用了,也可能是大家都遵守了,它正在起作用,按命中次数删规则会误删最有效的那些。

      多久一次。每季度一次;团队小、规则在十几条以内的,半年一次也够。审查报告里 rules-auditor 提示「规则可能过时」(代码库大量和规则反着写)时,可以提前复核那一条。业界参考:CodeRabbit 建议每季度人工清理一次 learnings;Cursor Bugbot 自动停用持续收到负面反馈的规则——我们的规则要人审批,不做自动停用。

      复核清单(/cr 规则复核,脚本 rules-health.sh):按规则文件和负责人列出每条规则、上次复核的时间(元数据里的 reviewed=,没有就看 added=),超过 6 个月没复核的排在最前,并附几项只读仓库就能做的检查提示。这些提示只是线索,不下结论:

      检查提示怎么判断通常意味着
      作用域失效scope 已经匹配不到任何文件模块删了或搬走了,改作用域或删除
      引用失效规则里用 `…` 提到的文件、函数、包在代码库里找不到要求使用的东西没了,规则多半过时;禁止的东西没了,说明大家都遵守了,不用动
      重复同层或跨层有几乎一样的规则合并成一条,保留更具体的那层;别的项目也有同样规则的,可以考虑移进组织规则包
      缺元数据没有编号,或没有 added / reviewed 日期补上
      太长单个文件超过 20 条合并、挪到目录级,或删掉不重要的

      复核的结果写成规则改动,用 propose-rules.sh 预览、确认后创建 MR:还对的用 confirm 记下 reviewed=本月;要改的用 replace;不要的用 remove(命名、格式这类建议先改配 lint 规则再删)。组织规则先标 status=deprecated 发一个版本,下个版本再删。复核不读审查记录,也不需要团队共享任何数据。

      六、度量与评测

      线上指标（/cr 统计）

      判断、去向、校准三个维度分开统计，互不折算；目标量级参考 Uber 和字节公开的生产数据。

      指标目标
      成立率（只算有人明确判断过的，标出样本数）≥ 75%
      同一个 MR 内被采纳的比例≥ 60%
      置信度校准：各分数段实际成立的比例分数越高，成立率越高
      被人工指出、crosscheck 漏报的数量持续下降
      每次审查的用时和 token按深度分开看

      这些数据怎么收集

      难点在需要人判断的那几项。原则是：能自动的全部自动收集，需要人的尽量降低门槛，样本少时如实写出样本数，不硬算比例。

      指标数据从哪来要不要人怎么做
      用时、token、角色数保存记录时脚本写入；token 由 hook 从宿主的会话记录里读不要每次审查自动记下。没装 hook 时 token 写「未统计」
      差一点通过的候选rejected.json不要每次审查自动存档
      同一个 MR 内被采纳的比例MR 合并后的最终代码不要运行 /cr 统计 时，对已经合并的 MR 只读拉取最终版本：先用脚本看报过的那段代码（按上下文指纹）有没有被改；改了的再交给 verifier 判断问题是否确实解决。Cursor（合并时用 LLM 判断）和 Uber（对最终提交重跑）都是这个思路。只算「改了且解决」，不把「代码动过」当成采纳
      成立率、置信度校准人的判断要降低表态的门槛：报告末尾提示「回复『1 对，2 误报：上游已重试』就能记录」；用户让修的、用 --fix 修好的自动记为成立。样本不足 10 条时只显示数量、不算比例
      漏报MR 上的人工评论部分要每月提炼时，脚本拉取人工评论并按文件和行号对上当时的发现；对不上的由 agent 判断是不是同一个问题，结果给人确认后计入

      不做团队看板。人的判断默认只在本机；团队开启共享后，由你手动同步到 GitLab 上的数据仓库，统计就能按团队汇总（见第八节）。

      离线评测（/cr 评测）

      测召回

      从 fix: 类 commit 往回找到引入 bug 的那次改动，看能不能报出来。

      补漏报

      S3 收集到的漏报：人工评论指出了、crosscheck 当时没报的问题。

      测误报

      干净的 commit，理想结果是空报告。

      评测集怎么建：不追求一次做全，先做一个约 20 个用例的小集合，用脚本找、人来确认，大约一两个小时。

      用例脚本做什么人做什么
      有 bug 的提交（约 10 个）在团队的仓库里找提交说明含「fix」「修复」、改动文件少的提交，用 git blame 找到当初引入这几行的那次提交，列成候选逐个确认「这确实是那次改动引入的 bug」，写一句期望 crosscheck 报出的问题
      干净的提交（约 6 个）挑合并后 30 天内没有相关修复、MR 上也没有人工指出问题的提交扫一眼确认没有明显问题
      规则正反例（若干）直接取组织规则包里的 examples/不用
      漏报（之后持续补充）每月提炼时自动加入候选确认后加入

      评测集怎么定

      评测集要能代表团队平时真实的改动，答案要可靠，还要防止调提示词时「对着考卷调」。参考 GitHub ReviewBench 的做法（答案来自人工评审、后续修复提交、静态检查和多个模型，合并去重后再由没参与标注的资深工程师复核），定下面几条：

      1. 覆盖哪些情况：按下面的比例挑，不让某一类或某一个仓库占大多数。

      维度怎么分布（起步的 20 个用例）
      仓库和语言2–3 个有代表性的团队仓库，覆盖主要语言；单个仓库不超过一半
      问题类型bug 约 10 个；安全 1–2 个（历史上有就用，没有就先不放，不编造）；规则用例直接取规则包的正反例，不占这 20 个
      干净的改动约 6 个，用来测误报
      改动大小小（100 行以内）、中、大（500 行以上，能测到分批）都要有，大约 4 : 4 : 2
      时间最近 6–12 个月的提交，代码风格和现在一致

      2. 什么算一个「期望问题」：每个期望问题都要同时满足：

      • 真实存在，写得出具体的失败场景；
      • 由这次改动引入，并且落在改动的行上；
      • 不是编译器、类型检查器或 linter 就能拦住的；
      • 有证据：通常是后来修复它的那个提交，或 MR 上的人工评论。

      不收的：只改配置或文档的提交、超过 2000 行的提交、需要外部系统才能判断对错的问题、拿不准的问题。

      3. 谁来确认：脚本找候选，熟悉这段代码的人确认并写一句期望描述；有争议的再请第二个人看，两人意见不一致的用例不收。

      4. 用例的格式：每个用例一个文件，放在规则仓库的 evals/cases/：

      {
  "id": "shop-api-9b7e44d1",
  "repo": "shop-api",
  "base": "3f2a1c0",
  "head": "9b7e44d",
  "source": "fix-commit:a81c2d3",
  "expect": [
    {"file": "src/orders/paginate.ts", "lines": "40-44", "category": "bug",
     "severity": "major", "desc": "total 是 pageSize 的整数倍时丢掉最后一页"}
  ],
  "confirmed_by": ["a3f9c2e1", "7c21d0b4"]
}

      干净用例的 expect 为 [],source 写 clean;从漏报来的写 missed。确认人只存哈希。

      5. 防止「对着考卷调」：

      • 规则用当时的版本。审查本来就从 base 提交读规则，所以评测时用的是这个用例当时的项目规则，不会用到后来专门为这个问题加的规则；组织规则包固定在评测配置指定的版本。
      • 留一部分不看细节。期望问题超过 50 个之后，分出三分之一作为留出集：调提示词时只看开发集里每个用例的失败原因，留出集只看总分，最终判断以留出集为准。起步阶段数量太少，先全部当开发集用。

      6. 规模按用途定：计数按「期望问题数」，不按用例数（一个用例里可能有好几个问题）。数量少时误差很大：召回实测 70% 时，10 个期望问题对应的真实值大约在 40%–89% 之间，50 个时大约 58%–82%，100 个时大约 61%–79%。所以：

      阶段规模能用来判断什么
      起步约 20 个用例发现明显的倒退（比如召回从 7/10 掉到 4/10），作为回归门禁
      两三个月后约 50 个期望问题（靠每月补充漏报）开始可以比较门槛、模型这类决定
      做重要决定时至少 50 个期望问题差距小于误差范围时，结论写「看不出差别」，不硬下判断

      参考规模：Kodus CodeReviewBench 30 个 PR、95 个已知问题；GitHub ReviewBench 219 个 PR；SWR-Bench 1000 个 PR。

      7. 怎么维护：用例的增删走规则仓库的 MR；每月补充漏报，补的时候照顾上面的比例；代码库大改后已经不成立的用例删掉；评测集一有改动，先用当前版本重跑，更新基线。

      怎么判断「报对了」：先由脚本比较文件和行号范围有没有重叠，重叠的再由 LLM 判断描述的是不是同一个问题；每次人工抽查几条，确认判断方式本身可靠。ReviewBench 也是用 LLM 判断，再由工程师复核。

      成本：跑一次评测等于审查 20 次，所以只在改插件、换模型、调门槛时跑，不定期跑。模型每次输出会有波动，差距小的结论要多跑一两次再下判断。

      评测的流程

      评测是可选的，衡量的是 crosscheck 这个工具本身（提示词、评分标准、模型改了之后变好还是变坏），和某个项目的代码质量无关。所以它主要由插件维护者负责，不是每个项目都要做：

      谁要不要做做什么
      普通开发者不用正常使用，不受影响
      项目负责人可选想了解 crosscheck 在自己项目上的效果，或验证 REVIEW.md 改得对不对时，用本项目的用例跑一次。插件维护者建评测集时，可能请熟悉代码的人确认几个用例
      组织规则包负责人自动每条规则的正反例由规则仓库的 CI 自动检查，不需要单独跑评测
      插件维护者强烈建议从 2–3 个有代表性的团队仓库里挑用例建评测集，每次改插件前后各跑一次。不做也不会坏，只是改插件只能凭感觉

      基线是什么：上一个被认可的插件版本，在同一份评测集上跑出的成绩。每次评测都和它比，才知道这次改动让结果变好还是变坏。基线存放在规则仓库的 evals/baseline.json，团队共用一份：不同的维护者在不同的机器上跑，比较的都是同一个参照。

      下面的流程由插件维护者在改动合入之前运行。

      1. 什么时候跑。改了角色说明、评分标准或 SKILL.md；换了宿主模型或 verifier 模型；想调 80 分的门槛；想改 deep 模式的做法。日常审代码不跑。
      2. 运行。说「跑一下评测，和上次的基线比」（简写 /cr 评测）。对每个用例，按「base..head」这段提交审查一次：
        • 不检出、不改仓库，和普通审查一样只读；
        • 用一个隔离的记录目录，不读历史判断、不做增量，避免以前的记录影响结果；
        • 深度和模型固定，和基线保持一致，只改这次要比较的那一项；
        • 记下每个用例的发现、被否决的候选、用时和 token。
      3. 对答案。对每个用例里期望报出的问题：先由脚本找文件相同、行号范围重叠（前后允许 3 行）的发现，再由 LLM 判断说的是不是同一个问题，得出「命中」或「漏掉」。
      4. 处理答案之外的发现。有 bug 的用例里多报的、干净用例里报出的，先由 LLM 判断是否站得住，再由人抽查：确实是误报的计入误报；其实是真问题的，记为「新发现」，补进这个用例的期望，不算误报（ReviewBench 也这样处理答案之外的有效发现）。
      5. 计分。召回 = 命中数 / 期望数；误报 = 平均每个干净用例报了几条；精确率 = 站得住的发现 / 全部发现；再加上平均用时和 token。按 bug、安全、规则分维度各算一份。
      6. 和基线对比。除了总分，逐个用例列出变化：哪些用例新抓到了、哪些新漏掉了、哪些新增了误报。总分不变但有用例从命中变成漏掉，同样要看原因。
      7. 决定能不能合入。召回不降、误报不升、成本增加在预算内（比如不超过 30%，超出要写明理由）。差距只有一个用例时，结果可能是模型波动，重跑一次再判断。
      8. 归档。完整结果存在本机的 ~/.crosscheck/eval/runs/<时间>/。改动合入时，把这次的成绩通过 MR 更新到规则仓库的 evals/baseline.json，成为新的基线，分数写进 CHANGELOG。

      评测报告的样子：

      评测:20 个用例 · 对比基线 2026-10-12(v0.1.6)· 本次改动:verifier 评分标准
                 基线      本次      变化
召回             7/10      8/10      +1(case-07 新抓到)
误报 / 干净用例   0.50      0.33      下降
精确率           78%       83%       +5%
平均用时         6.1 分钟   6.8 分钟   +11%
平均 token       210k      238k      +13%
新漏掉:无 · 新增误报:无 · 新发现:1 条(已补进 case-12)
结论:可以合入(召回不降、误报不升,成本增加在预算内)

      评测集本身的维护：每月从人工评论里补充漏报用例；代码库大改后已经不成立的用例删掉；评测集有改动时，先用当前版本重跑一次，得到新的基线，再拿来比较。

      回归门禁 改 roles/、references/、SKILL.md 之前，必须对比基线跑一遍评测：召回不能下降，每个干净 commit 上的误报不能上升，成本的变化写进 CHANGELOG。

      八、存储布局

      按「谁需要看到」分成三处:本机目录、GitLab 上的仓库、GitLab 本身。没有服务端,也不往任何外部服务上传。原则是:需要团队共用、需要有人审的放 GitLab,只通过 MR 改;只对自己有用、或者含有未提交代码的留在本机。审查记录里有代码片段,从不上传。

      1. 本机:~/.crosscheck/(只有自己能看到)

      ~/.crosscheck/

      九、主流程

      单次审查

      1. 用户调用 /cr。
      2. 收集 diff、意图、规则（从 base 读、分层合并）、历史判断、测试削弱、风险分级，记下仓库状态。
      3. 按深度和风险选择角色，并行查找。
      4. verifier 独立核实，全部评分留档。
      5. 过滤、合并、排序。
      6. 核对仓库状态没有被改动，结束只读阶段。
      7. 出报告，保存记录。
      8. 等待用户回复，按下面「报告之后」的流程处理。

      报告之后：用户回复了怎么办

      用户可以用报告里的编号指代发现（「第 2 条」），主 agent 通过 findings.json 对应到发现的固定编号；换了会话也能接着处理。

      用户说的怎么处理记录什么
      质疑：「第 2 条不对吧」「这为什么是问题」不马上认错，也不坚持原结论。把用户的理由当作新信息，重新打开依据里的代码核对：
      • 仍然成立 → 解释原因，给出具体的代码位置；
      • 站不住 → 撤回，说明是哪一环错了；
      • 双方都说不清 → 标为有争议，写明分歧在哪。
      		撤回记为不成立（原因必填）；有争议记为 disputed；仍然成立的不记，等用户表态
      表态：「对，确实是问题」「知道了，先不改」「误报」直接记下。判为不改或误报时必须有原因，用户没说就问一句成立 / 不修 / 不成立，带原因和那段代码的指纹
      要求修复：「修掉第 1、3 条」进入 --fix：只修指定的几条，最小改动，只改工作区；修完运行项目已有的检查，并让 verifier 确认问题已经消失；如实报告结果，包括失败修好的记为成立
      问没报的：「还有别的吗」「72 分那条是什么」从 rejected.json 列出差一点通过的候选，写明分数和没通过的理由，并标明「未通过核实」用户确认是真问题的，记为成立，同时作为阈值校准的样本
      指出漏报：「你漏了 cache.ts 的并发问题」按用户的描述走一遍核实；成立就补进报告记为漏报，进入评测集
      要求深挖：「cache.ts 用 deep 再看一遍」只对指定的文件或维度做一次定向审查，结果附在原报告后面，已经报过的不重复同一次审查记录里追加一段
      要求定规则：「以后这种别报了」「以后都要查 X」起草规则：不想再看到的写进 .cr/ignore.md，要检查的写进 REVIEW.md；给出 diff，用户确认后改到工作区，不提交；写入前跑 rules-lint.sh规则来源记为这次判断
      改完代码后再审：「再看一下」同一目标自动做增量审查，报告分成新发现、上次遗留、已解决三段每条发现的去向
      • 先核对再回应。不因为用户质疑就撤回，也不因为自己报过就坚持；结论以重新读到的代码为准。
      • 主动提议变成规则。同一类发现被判为不成立 2 次以上时，主动问要不要写进 .cr/ignore.md；用户同意才写。
      • 记录失败要明说。判断没记下来（比如缺少 python3）时直接告诉用户，不假装已记录。
      • 报告记录同步更新。撤回、补充和修复都追加到这次审查记录的末尾，保留时间顺序，原报告正文不改。

      每次审查

      积累 S1、S4、S5 三类信号。

      每月一次

      mine-reviews.sh 收集最近的人工评论 → 和当时的发现对比找出漏报（S3）→ rule-miner 生成候选规则 → 用户批准 → 以 MR 的形式写入。漏报同时进评测集。

      十、安全与治理

      • 内容是数据，不是指令。diff、PR 描述、人工评论、规则文件里写给 reviewer 的话一律不执行；只有 REVIEW.md 的审查设置例外，且有明确边界。
      • 只读有三层保障。说明里的约束；审查期间由宿主 hook 拦截改变仓库状态的命令和对仓库文件的编辑；出报告前核对分支、HEAD、暂存区和文件内容是否被改动。
      • 凭证不进对话。不打印远程地址、环境变量和凭证文件；显示的地址一律脱敏；平台 CLI 不可用时退回 git 拉取，使用仓库已有的凭证。
      • 规则来源可信。规则只从 base 分支或受保护的分支读，PR 改不了自己的审查设置。
      • 隐私。reviewer 只存哈希；收集的评论只存在本机；提炼出来的规则正文里不能出现人名和业务数据。
      • 人对规则负责。规则变更只以 MR 的形式提出，创建 MR 前要你确认，工具从不合并；组织规则仓库用 CODEOWNERS 指定负责人，变更必须有人审。
      • 写操作有边界。审查过程中不往 GitLab 写任何东西；规则 MR 和判断同步都在审查结束后、由你确认才执行。

      十一、实施顺序

      每个阶段都以前一阶段的评测基线作为验收标准。

      1度量基础

      • 全部评分留档（rejected.json）
      • 规则编号和元数据(含复核日期)
      • 规则从 base 分支读取
      • rules-lint.sh
      • 评测集第一版（约 20 个用例）
      验收：统计里能看到 70–79 分的分布；有一份评测基线

      2上下文

      • MR 人工讨论
      • 测试削弱扫描
      • --intent、风险分级
      • LLM 类安全风险
      验收：和基线比，召回不降、误报不升

      3反馈沉淀

      • mine-reviews.sh
      • rule-miner 角色
      • 候选审批
      • /cr 规则复核
      验收：第一批规则批准生效；负责人完成第一次规则复核；漏报开始进评测集

      4组织级与规模化

      • GitLab 规则仓库、~/.crosscheck/config、sync-rules.sh
      • extends / disable
      • 组织规则包的定期复核
      • verifier 模型按调用指定
      • 增量的依赖扩散
      验收：至少一个规则包被 2 个项目引用；不同 verifier 模型的效果有评测数据可比

      十二、关键决策

      问题决定理由
      结果输出到哪里只在本地输出，不接 CI，不往 MR 发评论以开发者自审为主；不往外发内容，就不会有误报出现在团队面前
      规则怎么组织L0 内置 / L1 组织 / L2 项目 / L3 目录，加上抑制和外部规则规则放在离代码最近又能复用的一层，各层有各自的负责人
      各角色用什么模型配置里按角色指定:model.finder(查找角色,可以用更便宜的模型)、model.verifier(核实)、model.helper(rule-miner、judge);不写就用宿主当前的模型。调用时说「核实换成某某模型」覆盖这一次查找只负责不漏,错的由核实筛掉,所以查找用便宜的模型、核实用强的模型,成本低、精确率不受影响;换模型后用评测比较效果
      组织规则仓库放在哪GitLab 上的独立仓库，地址统一写在 ~/.crosscheck/config，负责人写在仓库的 CODEOWNERS 里修改只改一处；规则变更走 MR，有人负责
      私有化 GitLab支持。自建域名、子路径部署写在 ~/.crosscheck/config 的 gitlab_hosts 里；登录交给 glab，没有 glab 时用 git 拉取和规则仓库地址放在同一个配置文件里，换域名只改一处
      数据放在哪规则、评测集和基线放 GitLab；候选规则直接是 MR；人的判断默认本机，可选同步到数据仓库；审查记录只在本机没有服务端，用 GitLab 仓库代替；需要共用和评审的进仓库，个人的留本机
      规则怎么增减机器只产出候选,人批准;去留由负责人定期复核决定,不看命中次数命中次数需要集中各人的记录,而且零命中可能说明规则正在起作用;人批准的规则由人复核最自然
