# 维护:统计、用历史 bug 检验

这些都在审查之外进行,只读。

## 审查统计

用户说「看看 review 的统计」「效果怎么样」时运行:

```
sh <skill_dir>/scripts/stats.sh [--all] [--days <n>] [--repo <目录>]
```

把输出原样给用户看:判断、去向、校准、差一点通过和成本。样本不足的比例不要自己算;「代码已改」不等于问题解决了。「差一点通过」里 70–79 分的候选,可以建议用户挑几条看看,判断 80 分门槛是不是太严。不要根据这些数字自行改变审查的行为;要调整就写进 `REVIEW.md`。目前不收集合并后问题是否解决(采纳率),等有真实使用数据再加。

## 规则维护

沉淀规则、检查规则、整理 `REVIEW.md` 都由单独的命令做,只能显式调用:Claude Code 里 `/crosscheck:cr-rules`(拷贝安装时 `/cr-rules`),Codex 里 `$cr-rules`,Cursor 里 `/cr-rules`;带上「检查」或「整理 REVIEW.md」选择要做的事。用户用自然语言提出(「从 MR 里总结规则」「检查一下我们的规则」「帮我写个 REVIEW.md」)时,告诉他用这个命令,不要在 cr 里代为执行。审查后用户说「以后这种别报了」这类单条规则,仍按 `after-report.md` 处理。

## 用自己的历史 bug 检验

各家公开的评测数字互相矛盾,最可靠的是拿自己仓库里真实修过的 bug 来测。用户想知道「crosscheck 在我们的代码上抓不抓得到」时:

1. 从 `git log` 里挑几个修 bug 的提交(提交说明里有 fix、修复,或关联了缺陷单),找到引入 bug 的那次改动。挑几个没有问题的普通改动做对照。
2. 对每个引入 bug 的改动运行一次审查(`/cr <引入bug的提交>^..<引入bug的提交>`,用户要求只测试时不保存记录),看报告里有没有那个 bug;对照组看有没有报出站不住的问题。
3. 列出结果:抓到几个、漏了几个(漏的写出 bug 是什么)、对照组误报几条。

样本很少时只报数量,不算比例。漏掉的 bug 可以提示用户:要不要为这类问题写一条规则。
