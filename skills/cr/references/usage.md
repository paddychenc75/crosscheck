# 常用说法

用户问「cr 能做什么」「怎么用」时,用下面的内容介绍,不需要全部列出,挑和用户情况相关的。

**审查**

| 想做的 | 可以这样说 |
|---|---|
| 审当前分支的全部改动(含未提交的) | 「review 一下」「帮我看看这次的改动」 |
| 审另一个分支 | 「看看 feature/pay 分支」 |
| 审一个 MR | 「review MR 128」,或者直接贴 MR 链接 |
| 审某几个提交 | 「看看最近 3 个提交」 |
| 只看某个目录 | 「只看 src/orders 下面的改动」 |
| 快速过一遍 | 「快速看一下」(只查 bug 和安全,最多 5 条) |
| 上线前仔细审 | 「仔细看看」「上线前深度审一下」(更慢、更贵) |
| 只关心某一方面 | 「只看安全问题」「只对照一下团队规范」 |
| 测试也一起看 | 「测试也一起看」 |
| 从头完整审一遍 | 「重新审」「全量审一遍」 |
| 告诉它改动的目的 | 「这次是为了修复分页丢数据」「方案在 docs/plan.md」 |

**审查之后**

| 想做的 | 可以这样说 |
|---|---|
| 表态 | 「1 对,2 误报:上游已经重试」「3 先不改」 |
| 修复 | 「把第 1、3 条修掉」 |
| 看没报的 | 「还有别的吗」「70 多分的那些是什么」 |
| 定规则 | 「以后这种别报了」「以后都要检查 X」 |

**维护**

| 想做的 | 可以这样说 |
|---|---|
| 从 MR 评论里总结规则 | 「从最近一个月的 MR 评论里总结一下规则」 |
| 检查规则还好不好用 | 「检查一下我们的规则」 |
| 看效果和采纳率 | 「看看 review 的效果」 |
| 同步团队判断 / 组织规则 | 「同步一下 review 数据」「同步一下组织规则」 |
| 跑评测(插件维护者) | 「跑一下评测」「找几个评测用例」 |

配置文件(`sh <skill_dir>/scripts/config.sh path` 查位置)里常用的设置:私有化 GitLab 的域名 `gitlab_hosts`、组织规则仓库 `rules_repo` / `rules_ref`、共享判断的 `data_repo`、读取需求单的 `issue_cmd`、评测用例的仓库位置 `repo.<名字>`。

组织资料可由宿主只读取得并传 `--materials <JSON>`，或配置 materials_file。组织规则只读，项目规则维护仍可用；评测位置用 eval_cases / eval_baseline，正反例用显式 --examples，不再默认发布到组织规则仓库。见 materials.md。
