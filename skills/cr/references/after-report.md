# 报告之后:用户回复了怎么办

用户可以用报告里的编号指代发现(「第 2 条」「2 误报」)。编号对应最近一次审查记录里 `findings.json` 的 `no` 字段,由此拿到发现的 `id`;换了会话也可以:用 `sh <skill_dir>/scripts/stats.sh` 或直接读 `~/.crosscheck/reviews/<项目>/<目标>/latest` 指向的记录。

合并展示的主条保留原编号并列出关联编号。用户只指定某个编号时只处理该条；明确对整组表态时逐条核对并记录各关联编号，不能因主条被否定就自动认定所有关联规范也不成立。

**原则:先核对再回应。** 不因为用户质疑就撤回,也不因为自己报过就坚持;结论以重新读到的代码为准。

## 记录判断

```
sh <skill_dir>/scripts/feedback.sh <判断> <id> "<原因>"
```

| 用户的说法 | 判断 | 原因 |
|---|---|---|
| 「这条不对」「误报」「这里本来就是这样」 | `invalid` | 必填,写用户给的理由;用户没说就问一句 |
| 「知道了,但不改」「先不管」 | `wontfix` | 必填 |
| 「对」「确实是个问题」「改了」 | `valid` | 可选 |
| 双方说不清、需要别人定 | `disputed` | 可选,写分歧在哪 |

一次回复里有好几条(「1 对,2 误报:上游已重试,3 先不改:下个版本」)时逐条记录。

- **你自己撤回也要记。** 用户追问后你重新检查,发现这条确实站不住而撤回时,用 `invalid` 记下原因。撤回而不记录,下次换个分支或 MR 它还会出现。
- **记录失败要明说。** 脚本报错(比如没有 python3)时,告诉用户这次判断没有被记录,不要假装记过了,也不要去手动改记录文件。
- **主动提议变成规则。** 判为不成立后,问用户要不要把这类情况写进对应目录 `REVIEW.md` 的「不要报」一节;同一类发现被判为不成立 2 次以上时(`history.json` 或统计里能看到),更应该提。用户同意才写(见下面「定规则」)。

## 各种回复

| 用户说的 | 怎么处理 |
|---|---|
| 质疑:「第 2 条不对吧」「这为什么是问题」 | 把用户的理由当作新信息,重新打开依据里的代码核对(复杂的可以启动一个 verifier,任务里附上用户的理由)。仍然成立 → 解释原因,指出具体的代码位置;站不住 → 撤回,说明是哪一环错了,记 `invalid`;双方都说不清 → 记 `disputed`,写明分歧 |
| 表态 | 按上表记录 |
| 要求修复:「修掉第 1、3 条」 | 进入 SKILL.md 第 7 步,只修指定的几条 |
| 问没报的:「还有别的吗」「72 分那条是什么」 | 从这次记录的 `rejected.json` 列出分数在 70 以上的候选,写明分数和没通过的理由,标明「未通过核实」。用户确认是真问题的,记 `valid`,它也会成为校准门槛的样本 |
| 指出漏报:「你漏了 cache.ts 的并发问题」 | 按用户的描述走一遍核实(启动一个 verifier,或自己按 verifier.md 做)。成立就补进报告,并告诉用户这条可以作为「用自己的历史 bug 检验」的样本(见 `maintenance.md`) |
| 要求深挖:「cache.ts 用 deep 再看一遍」 | 只对指定的文件做一次定向审查:`collect-diff.sh <target> --depth deep --full`,查找和核实时只看那几个文件。结果附在原报告后面,已经报过的不重复 |
| 要求定规则:「以后这种别报了」「以后都要查 X」 | 起草一句能对照代码检查的规则,加一句原因:都写进对应目录的 `REVIEW.md`:长期误报加在「不要报」一节(写清在什么条件下不报),团队约定加在规则里。先把要加的文字给用户看,用户确认后改到工作区(不提交),由用户自己提交 |
| 改完代码后:「再看一下」 | 同一目标重新运行 `/cr`,自动做增量审查 |

撤回、补充和修复都追加在这次对话里说明;保存过的报告正文不改。需要留档时,在 `<记录目录>/report.md` 末尾追加一节「后续」,写明时间和变化。
