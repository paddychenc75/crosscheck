# 置信度评分

给每条候选发现打 0 到 100 分。低于 **80** 分的发现不会展示,但分数和理由会存进 `rejected.json`,用来校准这个门槛。

`confidence` 是证据充分程度的操作性评分,80 是展示门槛,不是经过概率校准的 80% 正确率。它表示证据是否足以支持保留下来的结论,不表示影响大小。影响用 `severity` 表达(定级见 `finding-schema.md` 的「严重程度」);风格、微优化等不值得报告的内容按误报清单排除。已确认的 minor 问题不能仅因影响小降到 80 以下。

| 分数 | 含义 |
|---|---|
| **0** | 误报。读过代码后不成立。 |
| **25** | 可能是真的,但你无法从代码中确认。 |
| **50** | 只有局部证据,尚不能支撑候选的完整结论。 |
| **75** | 大部分链条已有证据,但决定结论的一环仍是假设。 |
| **100** | 已确认。已追踪代码路径或复现(复现须经 `run-check.sh` 运行),足以支持所报场景。 |

证据介于两行之间时,取中间的值。

## 封顶检查

按顺序逐项检查。第一条适用的决定分数上限。第 2 项只打标记、不封顶,之后的项目照常检查。

1. `line` 不在 `ranges.txt` 中 `file` 的任一改动范围内 → **0**,除非你能把它重新定位到真正导致问题的那个改动行。
2. 同一输入、状态或事件序列,在相同契约下于 base 已产生所报的同一错误结果 → **原有问题**,不封顶。先核实缺陷是否真实存在,照常按证据打分(`confidence` 表示缺陷真实存在的把握),输出 `"pre_existing": true`,在 `verdict` 写明 base 里对应的代码(路径和行号)。`pre_existing` 的发现不计入本次发现,展示方式见 `report-format.md`,同样须过 80 分门槛。比较两版路径、结果及改动的因果关系;别处已有同类缺陷不能否定本次新增的触发路径,另一个输入得到新结果也不能把未变的旧错误算成新增问题。被本次改动变得更可能触发或范围变大的,仍按本次引入处理,不标 `pre_existing`。
3. 别处的守卫、校验、类型约束或调用方契约使失败场景不可达 → **0**。在 `verdict` 中指出该守卫。
   - **例外:本次改动破坏了接口自己的约定或原有的保护。** 实现违反了接口、注释或类型写明的约定(例如文档写「不返回 null」却可能返回 null),或者去掉了 base 里已有的保护(锁、事务、过滤条件、校验、await),使正确性依赖于「现在恰好没人这样调用」——这是本次引入的缺陷,不按「当前调用方不会触发」否决。照常评分,在 `failure_scenario` 写清被破坏的约定或保护,以及按约定合法的调用会得到什么错误结果。这一条的严重程度上限只适用于后果还没在现有调用方里出现的情况:只是将来的调用方可能出错,最高 `major`(报告里显示为「重要」);若现有调用方已经会因此出错,后果已经出现,按 `finding-schema.md` 的「严重程度」定级。
   - 同样适用于代码本身不会被执行的情况:没有任何调用方、没有被注册或导出、所在分支的条件恒为假。先去搜调用方和注册点确认;确认之后,`bug` 和 `security` 候选 → **0**,并在 `verdict` 里说明它没有被用上。
   - 问题所在的行只是注释、排版、被注释掉的代码,或者是原样移动过来的旧代码 → **0**。具体情形见 `false-positives.md` 的「不是有效代码」。
4. 项目已在运行的编译器、类型检查器或 linter 会拒绝它 → **0**。CI 会拦住它;review 评论不增加任何价值。
5. 历史判断与当前事实分开:`same_code` 只是局部文本相同。重新核对同一场景、调用环境、输入契约和历史原因;「不成立」的反证当前仍成立才按证据打 **0**,「不修」不封顶、不改变事实结论。当前仍适用的历史处理决定可填 `history_match`、`history_context` 并用 `suppressed_by: "history"` 抑制重复展示,脚本另存处理原因。前提变化或无法核对则不自动抑制,照常评分;用 `previously` 解释重新提出的原因。
6. 它匹配 `false-positives.md` 中的某一条 → **0**,`suppressed_by` 写 `false-positives`;匹配覆盖这个文件的 `REVIEW.md` 里「不要报」一节的某一条 → **0**,`suppressed_by` 写 `review`,并在 `verdict` 里引用那条抑制的原文。
7. 一条 `rules` 发现,其引用的文字实际上不在规则里,或该规则的作用域不覆盖此文件 → **0**。(脚本会再核对一遍。)
8. 一条 `intent` 发现,对应的验收标准在 `intent.md` 里找不到,或者写得含糊、无法对照代码判断 → **0**。
9. 场景需要现有调用方及公开接口契约均不能产生的输入 → 最高 **25**。缺少本地调用点不等于公开接口的合法输入不可能;仍须核对契约,不能假定攻击者可控或上游没有校验。
10. 你相信它,但没有打开能证明它的代码 → 最高 **50**。去读代码,不要停在这里。
11. `REVIEW.md` 正文对这类问题提出了证据要求,而这条发现不满足 → 最高 **50**。
12. 没有在 `evidence` 里写出读过的代码位置 → 最高 **50**。脚本会核对这些位置真实存在,引用不存在的同样最高 50。
13. `verification` 写了 `executed`,但引用的运行编号没有对应的运行记录 → 最高 **60**,并按读代码推断展示。(脚本执行。)读代码推断本身不设上限。

运行结论与分数:有记录只证明执行过。`reproduced` 要有 `observation` 将实际输出与候选路径/后果对应,非零退出不自动加分;缺此说明最高 75。`refuted` 表示当前场景被反证,脚本设为 0,不能展示为确认。`inconclusive` 保留记录,依代码证据独立评分,证据完整可以通过,但不标「已复现」。未执行的 `inferred` 同样按代码证据评分。脚本只校验引用、字段及状态一致性,不能证明解释语义正确。

## 怎样才能得到 80 分以上

- 你打开了改动的代码**以及**与它交互的代码,失败可以从那里写的内容推出,并且这些位置都写进了 `evidence`。
- 已有接口契约、实现和相关测试足以证明所报故障时,不额外要求完整生产工程或实际复现。缺失信息若决定输入可达性、授权边界或外部实现语义,仍限制结论;接口名称、无界容器或相邻测试本身不等于证据完整。
- 区分正确性上限与性能推测:沿已确认的输入、入队或传递路径,合法输入会触及运行时上限并确定性崩溃或丢数据时,不再要求证明生产中的发生频率。仅凭容器无上限或复杂度变高、尚未建立可达输入和失败机制的,不能据此放行性能担忧。
- 对 `security`:你能说出可控输入的证据及其到达所报安全边界的每一步,并核对沿途的校验与绑定。评分针对修正后保留的结论:例如已确认外部提供的值被当成查询或命令的语法,而非独立数据传入时,缺少后续部署材料限制的是实际执行及损失的断言;不能反过来补出路由开放、绕过授权或数据已泄露。若只有危险 API 名称、字符串拼接形式或规则违反,却没有输入来源和边界语义的证据,仍不足以放行。
  - 核实时分清两件事:改动处已经发生的安全边界破坏,与后续利用结果。可控值的来源、传递路径和危险构造都已由代码及契约确认、只是后续部署、执行或损失范围未知的,就核实这个能独立成立且值得修复的缺陷,把过度断言的摘要、场景和严重程度修正到已证实的范围,并写明尚不能确认的后果。缺的若是输入是否可控、是否已校验,或安全 API 的实际语义,则缺陷本身未证实,仍受上限约束。不能只把未证实的攻击改称「风险」就放行,也不能用一条确定的编码规则违反冒充安全结论。
- 对 `intent`:验收标准写得明确,代码里确实没有做到,你能指出应该在哪里做而没做。
- 对 `rules`:规则被逐字引用,适用于此路径,且改动的行明显违反了它。

看似合理不等于证据。一条听起来像典型 bug、但你并未追踪过的发现,最高 50 分。
