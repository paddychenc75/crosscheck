# 报告的写法

报告的内容全部来自 `final.json` 和 `report-lines.sh` 输出的说明行,不要自己增删发现、改分数或改编号。

`report-lines.sh` 每行以一个标签开头,标签不写进报告:

| 标签 | 放在哪 |
|---|---|
| `MERGED:` | 只在目标已合入时出现:标题之后、`SCOPE` 之前单独一行,原样写 |
| `SCOPE:` | 报告第一行,紧跟标题(有 `MERGED:` 时在它之后);其中「对比基准:」写明基准来自哪一版 |
| `INTENT:` | 第二行 |
| `WEAKEN:` | 「测试和检查被削弱」一节,每行一条 |
| `RULES:`、`RULES_NOTE:` | 末尾说明行,`RULES_NOTE` 每条一行 |
| `TRIMMED:` | 末尾说明行 |
| `SKIPPED:`、`CHECKED:` | 末尾说明行 |
| `INCOMPLETE:` | 末尾说明行,`CHECKED` 之后、`消耗:` 之前;只在有输出时写。整行原样放入,「流程不完整:」是内容的一部分,例如 `流程不完整:缺 finders/reviewer.json` |
| `MARK:` | 不单独成行:`<编号><TAB><标记>`,标记写进该条发现的标题 |
| `DISCUSSED:` | 不单独成行:`<编号><TAB>讨论中已有人提出,代码仍未改`,写在该条发现的问题描述下面 |
| `FEEDBACK:` | 报告最后,`记录:` 一行之前 |
| `PREEXIST:` | 「改动代码里的原有问题」一节,每行一条(写法见下面「整体结构」之后的说明);没有时省略该节 |

严重程度显示为:`critical` → 严重,`major` → 重要,`minor` → 轻微。维度显示为:`bug`、`安全`、`需求核对`(intent)、`规范`(rules)。

发现带 `raised_in_discussion: true` 的,在该条下加一行备注「讨论中已有人提出,代码仍未改」。

## 整体结构

报告的骨架(章节的顺序、每节放什么)在 `templates/report.md`,照它写;下面是填写规则。

`<N>` 是缺陷(bug、安全)和需求核对的条数之和,不含 `pre_existing` 的发现。概览表只列缺陷和需求核对;两者都没有时不要概览表。某一节没有内容时省略该节。

`PREEXIST:` 每行一条,写成 `path:line — 摘要(原有,不是本次引入)`,不编号、不进概览表、不计入 N、不进 MR 说明。

**增量审查**(`final.json` 的 `scope` 为 `incremental`):标题写成 `— <N> 条发现(新增 <a> · 遗留 <b> · 已解决 <c>)`;概览表多一列「状态」(新增 / 遗留);逐条发现分成「新发现」和「上次遗留(仍然存在)」两段,遗留的标题末尾加 `· 首次报告于 <since>`;再加一节「已解决(<c>)」,列出 `final.json` 的 `resolved`:`- \`path:line\` — <摘要>(<resolved_reason>)`。

**没有任何发现通过核实时**,仍然用上面的结构:标题写 `— 0 条发现`,保留 SCOPE、INTENT 和末尾各行(`RULES`、`CHECKED`、消耗、记录等),只是没有概览表和逐条发现;有 `PREEXIST:` 行时仍展示「改动代码里的原有问题」一节。说明已检查部分没有确认发现,不要声称代码整体没有问题;也不要写没经过核实的判断(比如「这个值会由框架自动带上」)。不要为了填充篇幅而添加观察、表扬或泛泛的建议。不要列出被否决的候选,除非用户问起(见 `after-report.md`)。

## 每条发现

标题里的第三项是 `MARK:` 给出的标记:`已复现`(经 `run-check.sh` 运行、有运行记录)或 `读代码推断`。照抄,不要自己改。

每条发现的格式见 `templates/report.md` 末尾的「每条发现」。

- **问题代码**必须是原文,不要凭记忆写。用 `sh <skill_dir>/scripts/snippet.sh <review_dir> <file> <line> [前面几行] [后面几行]` 摘,输出原样放进代码块,语言标记按文件类型写。默认前后各 3 行,一般不超过 12 行;问题涉及相隔较远的两处时,摘两段。命令报错说代码不在本地时,从 `diff.patch` 里摘对应的行。
- **修复建议**:`suggestion` 里有确切的替换代码时写成 `diff`,`-` 行与问题代码原文一致;只有文字时照文字写,不要自己编代码;没有 `suggestion` 时写「修复方式需要结合上下文判断」并说明要考虑什么。
- **兼容性**:有 `compat` 时,在修复建议下加一行 `**兼容性**:<compat>`。
- **之前的判断**:有 `previously` 时,在问题下加一行说明,例如 `之前(10-09)判为不成立:上游已校验;本次重新报告是因为 <原因>`。
- **依据**:默认折叠。`evidence` 每项写成「读过:文件:行(note)」,`ruled_out` 每项写成「排除:…」,有 `repro` 时写「运行 <run>:命令 → 退出码,跑了几个测试、失败几个(tests_run 为 null 时不写测试数)」,下面原样贴 `tail`(日志末尾,不要自己改写或总结),`found_by` 写成「查到:…」,reviewer 的发现注明是哪一遍(`pass`)。
- **规范**发现在问题里逐字引用 `rule_quote` 和出处 `rule_file`,`also_lines` 有值时写明共几处。
- **其他位置**:`also_at` 有值时,在位置那一行下面写「同一问题还出现在」,逐个列出,例如 `a.ts:12`、`b.ts:30`。修复建议只针对主位置写。
- **需求核对**发现在问题里写出是哪一条验收标准(来自 `intent.md`)。
