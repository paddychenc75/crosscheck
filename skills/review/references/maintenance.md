# 维护:用历史 bug 检验

这些都在审查之外进行,只读。

## 规则维护

沉淀规则、检查规则、整理 `REVIEW.md` 都由单独的命令做,只能显式调用:Claude Code 里 `/crosscheck:improve`(拷贝安装时 `/improve`),Codex 里 `$crosscheck:improve`(拷贝安装时 `$improve`),Cursor 里 `/improve`;统一维护 rules 和 `REVIEW.md`,默认整理本地材料,明确说从历史 MR 沉淀才采集;所有新增、修改、删除、合并和用户补充先生成 `rules-draft.md`,确认后写工作区、不提交。用户用自然语言提出(「从 MR 里总结规则」「检查一下我们的规则」「帮我写个 REVIEW.md」)时,告诉他用这个命令,不要在 review 里代为执行。审查后用户说「以后这种别报了」「以后都要查 X」这类当场加的一条规则,仍在 review 里按 `after-report.md` 处理。

## 用自己的历史 bug 检验

按提交范围审历史 bug 时,工作区通常不是被审查的版本,deep 也不运行检查,结果都是读代码推断。

各家公开的评测数字互相矛盾,最可靠的是拿自己仓库里真实修过的 bug 来测。用户想知道「crosscheck 在我们的代码上抓不抓得到」时:

1. 从 `git log` 里挑几个修 bug 的提交(提交说明里有 fix、修复,或关联了缺陷单),找到引入 bug 的那次改动。挑几个没有问题的普通改动做对照。
2. 对每个引入 bug 的改动运行一次审查(`/review <引入bug的提交>^..<引入bug的提交>`,默认保存,仅明确说本次不保存时首次采集即传 `--no-store`),看报告里有没有那个 bug;对照组看有没有报出站不住的问题。
3. 列出结果:抓到几个、漏了几个(漏的写出 bug 是什么)、对照组误报几条。

样本很少时只报数量,不算比例。漏掉的 bug 可以提示用户:要不要为这类问题写一条规则。
