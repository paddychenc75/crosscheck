# 常用说法

用户问「review 能做什么」「怎么用」时,用下面的内容介绍,不需要全部列出,挑和用户情况相关的。

**审查**

| 想做的 | 可以这样说 |
|---|---|
| 审当前分支的全部改动(含未提交的) | 「review 一下」「帮我看看这次的改动」 |
| 审另一个分支 | 「看看 feature/pay 分支」 |
| 审一个 MR | 「review MR 128」,或者直接贴 MR 链接 |
| 审某几个提交 | 「看看最近 3 个提交」 |
| 只看某个目录 | 「只看 src/orders 下面的改动」 |
| 指定对比基准 | 「对比 develop」「要合到 release/1.2」;或者直接给提交:「对比基准是 abc1234」「从 abc1234 开始比」。只对这一次生效 |
| 换个对比基准 | 「换个基准」。默认仅本次使用;想固定规则可说「以后固定对比 develop,记住」或「以后跟随每个 MR 的目标分支,记住」 |
| 快速过一遍 | 「快速看一下」(最多 5 条) |
| 上线前仔细审 | 「仔细看看」「上线前深度审一下」(更慢、更贵) |
| 只关心某一方面 | 「只看安全问题」「只对照一下团队规范」 |
| 测试也一起看 | 「测试也一起看」 |
| 从头完整审一遍 | 「重新审」「全量审一遍」 |
| 告诉它改动的目的 | 「这次是为了修复分页丢数据」「方案在 docs/plan.md」 |
| 给需求链接 | 「需求单是 <链接>,需求文档是 <链接>」「这是 hotfix,没有需求单」 |

**审查之后**

| 想做的 | 可以这样说 |
|---|---|
| 表态 | 「1 对,2 误报:上游已经重试」「3 先不改」 |
| 修复 | 「把第 1、3 条修掉」 |
| 看没报的 | 「还有别的吗」「70 多分的那些是什么」 |
| 定规则 | 「以后这种别报了」「以后都要检查 X」 |
| 补充需求资料 | 「需求文档是 <链接>」「这个没有需求单」 |

**维护**

| 想做的 | 可以这样说 |
|---|---|
| 规则维护 | 用命令 `/crosscheck:improve`(Codex 里 `$crosscheck:improve`,拷贝安装时 `$improve`):不带参数会先列出三件事让你选,带「沉淀」是从 MR 评论里沉淀规则,带「检查」是检查现有规则,带「整理 REVIEW.md」是起草或整理 REVIEW.md。不能用自然语言触发 |
| 用历史 bug 检验 | 「拿我们修过的 bug 测一下能不能抓到」 |

想预先配置私有化 GitLab 的域名、查找和核实用的模型、读 MR 的代码托管工具、读需求单和需求文档的工具时,打开插件里的 `config/defaults.conf`:所有设置都列在里面,默认全部注释掉,每项一两句话说明用途和不写时的行为。团队统一的写在这一份里,个人的写到 `~/.crosscheck/config`(`sh "<plugin_dir>/scripts/config.sh" path` 查位置),格式相同。三个工具(`tools.code_host`、`tools.requirement`、`tools.doc_reader`)各写一句话告诉 agent 用什么、怎么用,想让它自动识别需求链接就在那句话里写一个链接示例。`tools.code_host` 是只读的代码托管工具:写了以后,贴 MR / PR 链接时由它读标题、描述和讨论,不再用 gh / glab;要给完整链接,只给编号时照旧用 gh / glab。

当次明确指定的基准优先,默认仅本次使用。否则沿用明确保存的项目规则;PR/MR 使用各自目标分支,本地尝试从分支创建记录识别切出来源。分支基准审查前先拉取 origin 最新版本,失败才用已有缓存并说明。Git 不永久保存切出来源;创建记录缺失、过期或有歧义时才问基准,同一问题顺带提示“是否记住为这个项目的默认规则？默认不记住”,可以一句话回答,不回答记住就不保存。固定分支规则与跟随每个 MR 目标的规则不同,只记规则、不记提交。自动识别不保存规则,报告会写实际基准和来源。已合入的 MR 也能审,审的是合入前的改动;分支不存在、无共同祖先或算不出合入前版本时先停下,由用户给基准后继续,非交互不猜基准、不生成报告。
