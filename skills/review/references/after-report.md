# 报告之后:用户回复了怎么办

用户可以用报告里的编号指代发现(「第 2 条」「2 误报」)。编号对应最近一次审查记录里 `findings.json` 的 `no` 字段,由此拿到发现的 `id`;换了会话也可以:直接读 `~/.crosscheck/reviews/<项目>/<目标>/latest` 指向的记录。

**原则:先核对再回应。** 不因为用户质疑就撤回,也不因为自己报过就坚持;结论以重新读到的代码为准。

## 记录判断

```
sh <skill_dir>/scripts/feedback.sh <判断> <id> "<原因>"
```

| 用户的说法 | 判断 | 原因 |
|---|---|---|
| 「这条不对」「误报」「这里本来就是这样」 | `invalid` | 必填,写用户给的理由;用户没说就问一句 |
| 「知道了,但不改」「先不管」 | `wontfix` | 必填 |
| 「对」「确实是个问题」「改了」 | `valid` | 可选 |
| 双方说不清、需要别人定 | `disputed` | 可选,写分歧在哪 |

一次回复里有好几条(「1 对,2 误报:上游已重试,3 先不改:下个版本」)时逐条记录。历史判断供后续审查参考,代码或判断前提变化时重新核实,不承诺相同问题永不重复。默认报告无可反馈的展示条目时不提示编号示例;用户问起隐藏或否决条目后仍可按下表用 id 反馈。

- **你自己撤回也要记。** 用户追问后你重新检查,发现这条确实站不住而撤回时,用 `invalid` 记下原因。撤回而不记录,下次换个分支或 MR 它还会出现。
- **记录失败要明说。** 脚本报错(比如没有 python3)时,告诉用户这次判断没有被记录,不要假装记过了,也不要去手动改记录文件。
- **主动提议变成规则。** 判为不成立后,问用户要不要把这类情况写进对应目录 `REVIEW.md` 的「不要报」一节;同一类发现被判为不成立 2 次以上时(`history.json` 里能看到),更应该提。用户同意才写(见下面「定规则」)。

## 各种回复

| 用户说的 | 怎么处理 |
|---|---|
| 质疑:「第 2 条不对吧」「这为什么是问题」 | 把用户的理由当作新信息,重新打开依据里的代码核对(复杂的可以启动一个 verifier,任务里附上用户的理由)。仍然成立 → 解释原因,指出具体的代码位置;站不住 → 撤回,说明是哪一环错了,记 `invalid`;双方都说不清 → 记 `disputed`,写明分歧 |
| 表态 | 按上表记录 |
| 要求修复:「修掉第 1、3 条」 | 进入 SKILL.md 第 7 步,只修指定的几条 |
| 问没报的:「还有别的吗」「72 分那条是什么」 | 从这次记录的 `rejected.json` 列出分数在 70 以上的候选,写明分数和没通过的理由,标明「未通过核实」。用户确认是真问题的,用它的 `id` 记 `valid` |
| 问没展示的:「还有哪些没展示」 | 从这次记录的 `findings.json` 列出没有 `no` 的条目。它们已通过核实,只是超过了条数上限,可以用 `id` 表态 |
| 指出漏报:「你漏了 cache.ts 的并发问题」 | 按用户的描述走一遍核实(启动一个 verifier,或自己按 verifier.md 做)。成立就补进报告,并告诉用户这条可以作为「用自己的历史 bug 检验」的样本(见 `maintenance.md`) |
| 要求深挖:「cache.ts 用 deep 再看一遍」 | 只对指定的文件做一次定向审查。审的是当前分支时,用路径作为 target:`collect-diff.sh <路径> --depth deep`(记录单独存放,不影响整个分支的增量)。PR/MR、其他分支或提交范围:`collect-diff.sh <target> --depth deep --full`,查找和核实时只看那几个文件,**不运行 `save-review.sh`**(否则这次会成为整个目标的增量基准,其他文件上的发现就丢了),出结果前照常运行 `check-state.sh`。结果附在原报告后面,已经报过的不重复 |
| 要求定规则:「以后这种别报了」「以后都要查 X」 | 在 review 里当场加一条,写进对应目录的 `REVIEW.md`(接近 15 条或只对某类文件生效时改放 `.agents/rules/`),写法见下面「定规则」 |
| 改完代码后:「再看一下」 | 同一目标重新运行 `/review`,自动做增量审查 |
| 补充需求资料:「需求文档是 <链接>」「这个没有需求单」「这次是为了…」 | 用 `python3 <skill_dir>/scripts/sources.py set <记录目录> <键> <值>` 记下:`intent`(一句话)、`local_docs`(本地文档路径,多个用换行分隔)、需求来源的类别(`requirement`、`doc`,值是链接、`skip` 或 `none:<类型>`;给了新链接且配置了工具时,按 `references/collection-protocol.md` 的需求协议读取内容,下次审查会用上)。之后不用再说,review 会沿用。`intent`、`local_docs` 的值传空字符串可清除 |

「改动代码里的原有问题」没有可反馈的 `id`;按历史判断抑制的条目不在本次 `findings.json` 中。不要把它们的编号当作本次发现交给 `feedback.sh`;需要变更历史判断时先找到对应的原始发现 `id`,找不到就说明无法记录。

撤回、补充和修复都追加在这次对话里说明;保存过的报告正文不改。需要留档时,在 `<记录目录>/report.md` 末尾追加一节「后续」,写明时间和变化。

## 定规则

审查时当场定的少量必查和不要报(「以后这种别报了」「以后都要查 X」)写进对应目录的 `REVIEW.md`。`REVIEW.md` 已接近 15 条,或这条规则只对某类文件、跨目录生效时,改放 `.agents/rules/<主题>.md` 并写 `paths`(格式参照 `skills/improve/templates/rule.md`),先跟用户说一声。从 MR 评论批量沉淀、成主题的规则也进 `.agents/rules/`,那是 `improve` 命令的事,这里不做。

- **「以后都要查 X」**:写成能对照代码检查的一句「在 <范围> 里必须 / 禁止 …」,加一句原因,再写「不要报」的边界(什么情况下不算违反)。字段参照 `skills/improve/templates/rule.md`,但在 `REVIEW.md` 里保持简短,加在「每次都要检查」一节。
- **「以后这种别报了」**:写清「在什么条件下不报」,不能写成一整类问题都不报(不能只写「不报空指针」)。范围尽量限定到目录或文件模式。加在「不要报」一节。
- **先查重。** 写之前看对应的 `REVIEW.md` 和 `.agents/rules/` 里有没有说同一件事的。有就告诉用户,不重复写。
- **加来源。** 在新加的那一行末尾写来源注释,例如 `<!-- 来源:审查 mr-128 发现 20261028101500-3 -->`(目标名和发现的 `id`,即 `findings.json` 里的 `id` 字段;不是报告里的序号 `no`),之后用 `improve` 检查时能追溯。
- **先给用户看,确认后只改工作区,不提交**,由用户自己提交。
- **提醒用户:** 写进 `REVIEW.md` 的「不要报」会对整个目录的所有人生效,所以要写窄。建议单独提交,让评审人能看到这一行。
