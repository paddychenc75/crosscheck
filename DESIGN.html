      一、设计原则

      1. 精确率优先。两条真实发现好过十条里错三条。作者看到几条错误评论后就不再认真看其余的，报告为空是正当结果。
      2. 查找负责不漏，核实负责不错。查找阶段放开去查，查到一半的也交；verifier 看不到查找时的推理，先尝试推翻、再打分，必须给出依据。
      3. 确定性的工作交给脚本。diff、行范围、规则装配、依据和规则引文校验、过滤排序、增量都由脚本完成，agent 只做判断。
      4. 规则就是文件。项目的 REVIEW.md 和已有的 CLAUDE.md、AGENTS.md、Cursor / Copilot 规则直接用，不需要编号、元数据或专门格式。
      5. 记住人的判断。表态时写下原因，同一段代码不再重复报同样的误报；团队共享的写进 REVIEW.md。
      6. 机制保持简单。只留业界验证过有效的；在有真实使用数据之前，不为“可能有用”加机制。

      不做什么

      • 不替代编译器、类型检查器、linter 和 CI，它们能拦住的问题不报。
      • 不审查改动之外的存量代码；不报风格、命名、可读性、日志措辞和影响很小的性能优化（除非项目写成了规则）。
      • 不往 PR/MR 发评论，不 approve、request changes、merge；不提交 MR、不改 MR 描述；review 不生成 PR / MR 描述，描述由独立的 describe 在本地生成（也只读平台）。
      • 默认不改文件，只有用户明确要求时才修复，且只改工作区、不提交。
      • 不往 GitLab / GitHub 写任何东西。审查后仅按明确请求修复本地代码、或确认后修改工作区规则，不得改托管平台记录。
      • 不做组织级的规则分发、团队数据同步和评测平台。
      • 不追求召回率，会漏报，这是有意的取舍；不自动改规则，也不自动停用规则，增删由负责人确认。
      设计依据：这些原则从哪来
      • 精确率优先：Uber 发现开发者对低质量建议很快失去信任，整类砍掉评分最差的评论；OpenAI 接受召回略降，换取信号质量。Uber：uReview；OpenAI：A Practical Approach to Verifying Code at Scale

      • 确定性的交给脚本：简单的语法规则 linter 最好，LLM 补语义判断；CodeRabbit 用工具结果过滤模型的误报。Addy Osmani：Agentic Code Review；CodeRabbit：架构（沙箱、工具结果过滤误报）

      • 描述单独成技能，只在本地生成：review 只回答“有没有问题”，描述回答“这次改了什么、影响哪些地方、怎么验证”，读者和时机都不同，所以拆成 /describe，review 不带描述。描述把影响面放在一句话之后（接口、迁移、配置、函数签名四层，删除优先，没发现就写“未发现”），怎么验证整段由脚本从代码推出并标注“由代码推断，未执行”，预期没有出处就不写，不问作者“怎么验证的”。描述只列事实和链接、不下结论，不发布、不改平台上的描述，由作者自己复制粘贴；采集直接调用 review 的脚本（origin 绑定、只读、基准问答一致），描述目录不放在 reviews/ 下，采集后恢复“进行中”标记和需求来源记录，所以两者互不依赖、互不影响。每次生成都问一次需求单链接，和 review 的 intent.required 无关。
      • 脚本、角色、编排三层：脚本做有唯一答案的事（取 diff、算行范围、装配规则、校验、过滤排序、增量、调平台 API），角色做需要判断的事，SKILL.md 只负责把你的话翻译成选项、调度角色、按格式出报告。过滤、排序、增量、编号原来写在 SKILL.md 里让 agent 执行，现在都在脚本里，结果可复现、能写测试。
      • 脚本入口是 sh，实现是 python3：每个 .sh 只检查参数后交给同名的 .py 模块，一个模块只做一件事，公共函数只在 crlib.py 有一份。核心流程需要 python3 3.8+（只用标准库），没有时 collect-diff.sh 一开始就停下并提示安装；规则装配、依据校验、汇总都涉及 JSON 和文本处理，用 awk 和 sed 拼既难读也容易出错。git 必需，gh / glab 只在对应功能里才需要。
      • 插件共享配置：审查流程在 skills/review/ 下，PR/MR 描述在 skills/describe/ 下（采集直接调用 review 的脚本，不依赖审查结果），规则维护在 skills/improve/ 下，三者共用插件级 config/defaults.conf 和 scripts/config.py；直接拷贝安装必须保留共享目录与 skills 的相对布局。不依赖宿主专属功能；三个宿主的 plugin.json 只是安装清单，hook 缺了流程也不变。代价是用不上宿主特有的能力，好处是只维护一套流程，三个宿主行为一致。
      • 报告里的代码是摘出来的：问题代码由 snippet.sh 从被审查的那一版带行号摘取，不让 agent 凭记忆写，否则容易和原文有出入，被审查的代码不在工作区时还可能摘到另一个版本。修复建议的代码来自发现本身，经 verifier 过目；没有确切替换代码时用文字。报告开头有概览表，先看有几条、多严重、在哪里。
      • 只审有效代码：脚本跳过测试、测试数据、日志、覆盖率报告、备份和 lock、生成、vendored、二进制文件；文件名规则偏保守（不把 spec/ 一概当成测试，它也可能放接口定义），宁可多审一个文件也不漏产品代码。测试默认不审，--with-tests 可打开。文件内部由角色判断：注释和排版、原样移动、被注释掉的和没被用上的代码不按缺陷报，评分标准里有对应的封顶检查。
      • 意图在调用时给，不放进仓库：计划和意图描述的是“这一次改动”，提交进仓库会在合并后过期，还会被之后的审查读到，所以只从 MR 描述、需求单、提交说明和 --intent / --doc 取。只有意图里有明确的验收标准才做需求核对，没有就不猜“应该做什么”。意图可以解释某个行为变化是有意的，不能让安全问题不报。
      • 测试削弱由脚本扫出来：删除测试、断言减少、新增 skip / only / 抑制注释、降低覆盖率阈值、放宽 CI 检查，不是缺陷，但评审的人必须看到，所以单列一节，不占缺陷条数，也不经 verifier。

      三、审查流程

      步骤谁做产出
      0. 审查前先问（有要问的才有）主 agent 一轮问完；用配置的工具读取链接对比基准（无法自动确定才问，默认不记住）、需求单和需求文档的链接和内容（同一分支记住）、可选的 PRD 等资料（可跳过）
      1. 收集改动collect-diff.sh（内部调用 collect-context.sh、settings.sh、feedback.sh history）diff.patch、ranges.txt、intent.md、sources.json、analysis-facts.json、weakening.txt、history.json；增量时 prev-findings.json
      2. 装配规则collect-rules.shrules.txt、rules-index.json
      3. 并行查找reviewer、rules-auditor（并行）candidates.json
      4. 核实prepare-verify.sh 分批 → verifier × Nverify/result-*.json
      5. 汇总aggregate.shfinal.json、findings.json、rejected.json
      6. 报告check-state.sh、report-lines.sh、主 agent、save-review.sh报告和审查记录
      7. 修复（仅要求时）主 agent工作区改动，修好的记为成立

      对比基准

      和 GitHub / GitLab 一样，diff 从源分支与目标分支远端最新的 merge-base 算起：

      • 分支基准取远端最新：选定分支后先从 origin 拉取再算（只更新 origin/ 下的远程跟踪分支，不动工作区）；拉取失败使用本地缓存并提示可能过期。平台提供已合入 MR 的冻结 diff 时使用合入前版本。报告的 SCOPE 行写明实际基准及选择来源。
      • 已合入的 MR 用合入前的版本：用 merge commit 合入后目标分支已包含 head，merge-base 就是 head、diff 为空。脚本在目标分支的 first-parent 链上找到合入它的提交，用它的第一个父提交算基准；squash / rebase 合入照常算；找不到合入提交（如快进合入）时输出 BASE_FAILED 并停止，请用户指定有效基准。
      • 用户可以指定：--base 指定分支，--base-sha 指定提交（短哈希也行，必须是 head 的祖先，优先于任何自动计算）。都只对这一次生效，不改项目的记录。
      • 空 diff 一定提示：MR 或用户指定的基准算出 0 个文件时输出 NOTE，说基准可能不对，不当成“0 条发现”。
      • 能确定就直接审，不确定才问：当次明确基准优先，其次是用户明确保存的项目规则。没有这些时，PR / MR 使用目标分支，本地从分支创建和切换记录寻找可验证的切出来源，取来源分支远端最新版本算 diff。Git 不永久保存来源，记录缺失、过期或有歧义才问；不拿 upstream 或最近共同祖先当来源证据。
      • 默认不记住：回答基准问题默认仅本次使用，顺带提示“是否记住为这个项目的默认规则？默认不记住”。明确要求才保存“跟随每个 MR 目标分支”或“固定对比分支 X”，不保存提交哈希，自动推断也不保存。换基准默认不改旧规则。必要的基准、需求与可选资料合并一轮问。
      • 计算失败先恢复基准：分支缺失、没有共同祖先或无法推断合入前版本时，输出 BASE_FAILED 并停止，交互中让用户选有效分支或提交再继续。非交互缺少来源时可用推荐项并标“基准未确认”，实际计算失败仍停止，不生成误导报告。

      读外部 MR：tools.code_host

      gh、glab 之外的代码托管平台（内部自建的）也能审 MR：

      • 一句提示词配置：在 config/defaults.conf 或个人配置里用一句自然语言写明用哪个只读工具读 MR、链接长什么样。配置后链接形式的 MR / PR（GitHub、GitLab 的链接也一样）都由它读；只给编号时仍走 gh / glab。
      • agent 只交文本：agent 用这个工具读出标题、描述、讨论、目标分支名和源引用，写成固定格式的 code-host.json。编号、仓库、平台和网址从用户给的链接解析，不让 agent 报。
      • 脚本校验，能算的不信：code_host.py 要求仓库和本地 origin 一致、分支名合法（git check-ref-format）；自己只读 fetch source_ref，head 以 fetch 到的为准；讨论作者只存哈希、过滤机器人；基准不取 agent 的，和其他路径一样拉取最新的目标分支再算。
      • 失败退回纯 git：核对不过或工具报错（status 为 failed）时只用 git 拉取代码，NOTE 和报告里都写明“MR 信息没有读到”，不悄悄丢掉标题。
      • 只读靠约束：配置模板和 SKILL.md 都写明这个工具只用来读；插件看不出远端的 MR 有没有被改过。

      深度

      档位查找核实上限
      quick主 agent 自己按 reviewer 说明做第 1–3 遍主 agent 自己核实5 条
      standard（默认）reviewer（同一上下文分遍：正确性、安全、需求核对）、rules-auditor 并行verifier 子代理，只读代码，每批最多 3 条缺陷 10 条；需求核对、规范各 5 条
      deep同 standard，reviewer 多做一遍影响面（从使用方往回查）verifier 可以跑项目已有的类型检查和测试来复现同 standard

      改动较大时按约 1000 行一批（CR_BATCH_LINES 可调），reviewer 和 rules-auditor 每批各跑一次；quick 不分批。超过 4 批（CR_LARGE_BATCHES）先问你，确认后加 --allow-large 再跑。条数上限可被 REVIEW.md 的 limits 覆盖，不指定深度按 standard。deep 下 verifier 只能运行项目已经定义的只读和构建类命令，不装包、不改已跟踪的文件、不访问网络。

      流程是否走完

      • 进行中标记：真正开始审查时在记录目录写 pending，保存成功后删除；下次审查同一目标时标记还在，就提示上一次没有保存、很可能提前结束，然后照常重新审查。
      • 非交互运行：没有人在场时（claude -p、codex exec、CI）必须前台启动子代理，等每个子代理的最终 JSON 都回来再进入下一步，全部返回之前不写报告、不保存记录。
      • 代码块编号和调用方交给脚本：analysis_facts.py 给每个改动块编号（H1…），提取改了哪些函数、接口、类型和配置键，用 git grep 按名字找本仓库里的调用方，写进 analysis-facts.json 供 reviewer 引用；依赖注入、反射、跨服务调用搜不到。它失败不阻止审查，但会在 NOTE 里披露，并记为流程缺项，报告里写“流程不完整”。
      • 实际用的模型：消耗行列出会话记录里实际出现的模型名；配置的查找或核实模型没有出现在记录里时，报告多一行“模型与配置不一致”。

      被审查的代码不在工作区时

      • 审查阶段不检出：审 PR/MR、其他分支或提交范围时，meta.txt 的 head_checked_out=no，所有角色用 git show <code_ref>:<path> 读文件、git grep 搜索，不读磁盘；这时 verifier 不跑检查。code_ref=UNAVAILABLE（head 提交拉不到本地）时只能基于 diff 本身审查，报告里注明。
      • 读不到 MR 信息就用 git 拉取：gh / glab 没装或没登录时，脚本用 git fetch origin merge-requests/<n>/head（GitHub 是 pull/<n>/head）把代码拉下来，用的是仓库已配置好的凭证。代价是拿不到标题、描述和目标分支，报告里说明。
      • “没登录”常是环境没带上：agent 的终端多半不读 .zshrc。脚本只用 grep -q 看 rc 文件里有没有出现相关变量名、当前环境里是不是空的，不读取、不保存、不输出任何值，然后建议把它们挪到 ~/.zshenv，这一次改用 git 拉取。
      • 自建 GitLab 的平台判断：域名常不含 “gitlab”，所以顺序固定为 --platform → 环境变量 → 配置的 gitlab_hosts（支持带子路径）→ 域名和链接形态。
      • 远程地址去掉凭证再显示：所有要显示或保存远程地址的地方都经过同一个函数；拉取失败时不转述 git 的原始报错，因为其中可能带着完整地址。
      • --fix 是唯一需要切换分支的地方：工作区有未提交改动就不切换、不修；干净时先问你，同意后才切换；永远不替你 stash。
      设计依据：查找怎么分工、对比基准和读外部 MR
      • 分遍复用材料，成本按用量判断：reviewer 在同一上下文保留已读材料，减少重复调查。提示缓存按前缀匹配；fresh agent 通常不共享父对话，但工具、系统提示等共同前缀仍可能命中缓存，取决于宿主和请求构造。子代理数不等于成本倍数，实际成本还取决于输入、输出和缓存读写。Anthropic：Prompt caching
      • 分工按任务边界：两个查找角色分别处理缺陷判断和规则原文。Anthropic 官方 code-review 命令当前并行运行两个规则检查和两个 bug finder；Greptile v5明确并行探索多个假设。并行与单上下文分遍各有取舍，外部方案不直接决定本插件的角色数量。
      • 安全一遍默认开：照搬 Anthropic security-review 的排除清单，默认不报只导致服务不可用的问题、缺少限流、开放重定向、只在测试代码里出现的。
      • 规则单独查：“只认写下来的规则、必须引原文”和 reviewer 的判断标准差别最大，Anthropic、Amp、Uber、Qodo 也都单独拆出来。
      • 不报可读性和小重构：Uber 的数据显示这类建议的评分一直最差，宿主也自带 /simplify。
      • 流程不能省：用公开 PR 评测时，便宜的宿主模型常觉得改动简单就不启动子代理、自己读一遍出结论。所以 standard、deep 只要能启动子代理就必须启动，改动再小也一样；按流程走完时，干净对照基本没有误报。
      • 留标记、下次发现：会话提前结束时进程已经不在了，没有谁能事后补写“失败”；开始时写下标记、保存后删除，下次就能发现上一次没走完。非交互运行没有人在场，后台启动的子代理会在会话结束时丢掉，所以必须前台启动。
      • 实际模型从会话记录里读：宿主不支持为子代理指定模型时会照常用宿主的模型，用户读报告时只看到自己配置了什么，所以由脚本读出实际模型，对不上就提示；只读模型名，不读对话内容。
      • 基准以远端最新为准：GitHub、GitLab 的 PR / MR 都按目标分支当前最新的状态与源分支的 merge-base 算 diff；本机缓存的 main 可能是几天前的，当前分支已经合入更新的 main 时，别人的提交会被算成这次的改动。GitHub：PR 里的分支比较；GitLab：合并请求的改动
      • 已合入的 MR 不能出空 diff：合入后 merge-base 等于 head，报成“0 条发现”最误导，所以取合入前的版本，算不出来就停下来问。
      • 有依据才自动选，记忆由用户决定：PR / MR 有明确目标，本地 reflog 可以提供创建来源线索，但会过期，也不能代表未来一直合入同一分支。因此自动选择不持久化，缺少可靠线索才问，明确要求记住才保存规则；同一仓库的不同工作流可以使用不同基准。Git：reflog 的本地记录与过期机制
      • 读外部 MR 的适配层是三样东西：主流做法是在平台之上加一层适配器，每家平台一套实现，统一成同一组能力；crosscheck 跑在 agent 里，不内置任何平台的客户端，能调用的是用户自己的工具，所以适配层是一句提示词、一个固定格式和脚本校验。Qodo：各 Git 平台的功能支持；Claude Code Action：由运行环境访问平台，把 PR 信息交给模型
      • 大改动分批：一个角色读几千行 diff，后面的文件得到的注意力明显少于前面的。切分由脚本按路径顺序做（同目录的文件落在一起、单个超限的文件独占一批），不让 agent 临场决定，结果可复现。代价是成本随批次数线性增长，小改动只有一批，和不分批完全一样。分批按行数而不是依赖关系，路径相距很远的关联改动会落在不同批次，各批仍能看完整的 diff.patch，跨批的问题更依赖 deep 的影响面那一遍。
      • 不检出、不 stash：读代码用 git show 和 git grep 就能读到任意提交的完整内容；检出会动你的工作区，有未提交改动时要么切换失败，要么得 stash，流程一中断，改动就留在 stash 里不容易想起来。代价是看不到目标分支上未提交的改动，以及 deep 下 verifier 不能跑检查。回退到 git 拉取，是因为曾有 agent 在 glab 未登录时从远程地址里取出 token 自己去调 API，还把带凭证的地址打印出来；有了这条退路就没有理由这样做。
      • 拉取不阻塞：算基准前的拉取关闭交互式输入，ssh 10 秒连不上就放弃，离线或沙箱里用本地已有的那份并说明它最后更新于多久之前；CR_FETCH=0 可显式关闭。所有路径（当前分支、其他分支、git 回退、tools.code_host）都经同一个函数拉取并取 origin/<目标分支>，不各自 fetch。--base-sha 变了算全量重审：同一个文件的 diff 可能没变，但“拿什么比”变了。
      • 查找不自己过滤：评测里漏掉的问题大多是查找阶段根本没提出来，而不是被核实否决。所以 reviewer 不读误报清单，拿不准的都交给 verifier；这和 Qodo 的多 agent 方案“先尽量找全、再统一核实”一致。

      四、审查角色

      每个角色只做一件事，交出的东西都有固定格式，脚本负责核对。

      角色做什么交出什么不做什么
      reviewer查正确性、安全、需求核对；deep 再查影响面缺陷候选，每条标明哪一遍查到的不判对错；拿不准的照交，标 needs_check
      rules-auditor对照写下来的规则，只看改动的行规则候选，带规则文件和逐字引文不凭空造规则；规则里没写的不查
      verifier在独立上下文里重读代码，先推翻再打分0–100 分、读过的位置、排除的可能不看发现的来源和旧分数；不改代码
      • 查找和核实分开：reviewer、rules-auditor 只负责找，verifier 只负责判，不在同一个上下文里。
      • 规则发现要逐字引文：引文由脚本核对，对不上的不报。
      • 80 分是操作性门槛：低于 80 分的不报但留档；它不是概率，也不是行业标准。

      reviewer 在同一个上下文里分遍查，是为了复用已读的代码和调用链理解，少做重复调查，也省去多个 agent 之间的协调。业界两种做法都有（Anthropic 官方命令并行跑多个 finder，Greptile v5 并行探索多个假设，Bugbot 公开的是按需自主调查），这是 CrossCheck 当前的取舍，不是已证明的最优：还缺同预算下和多个子代理对比的数据。

      设计依据：角色分工
      • 查找与核实分开：查找角色提交候选，verifier 独立读代码确认。这样核实者不容易沿用候选的推理。Anthropic：Claude Code Review
      • 同一上下文分遍是取舍：分遍可以复用已读代码，减少重复调查和协调成本；成本要看实际的输入、输出和缓存用量，不能按 agent 数量算。官方 code-review 命令当前并行运行两个规则检查和两个 bug finder，Greptile v5 并行探索多个假设，Bugbot 的复盘说明按需自主调查带来提升、没有公开 agent 数量。同预算下的对比数据还没有。Anthropic：Prompt caching；Anthropic 官方 code-review 命令；Greptile v5；Cursor：Building Bugbot
      • 80 分是操作性证据门槛：本插件按依据完整性和反证检查给出 0–100 分，以 80 分过滤候选；它不是真实概率，也不是已校准的行业标准。Anthropic 官方命令文件当前没有数值 80 门槛，而其README仍写 80，不能据此宣称行业统一标准。
      • verifier 的执行证据：Meta TestGen-LLM 只保留能编译、稳定通过、确实提高覆盖率的测试；有 agent 跑了 0 个测试、退出码 0 就报告“全部通过”，所以执行声明要核对原始记录。Meta：TestGen-LLM（可执行的过滤器）；综述：agent 自报“测试通过”的核实
      • 原有问题单独标出：Anthropic 内部的代码审查给发现加 Pre-existing 标签：问题真实，但不是这次改动引入的，不当作作者要修的缺陷，也不丢掉。我们同样把它们和本次引入的问题分开展示。Anthropic：Solving code review at Anthropic
      • 隔离不是完全盲审：verifier 只拿结构化候选，不拿发现者的推理、来源角色、旧分数；启动查找角色时也不把 diff 或编排者的印象贴进任务，每个角色自己读材料。候选的描述、失败场景、修复建议和相关历史仍可能影响判断，隔离只减少先入为主，不保证核实正确。没有子代理的宿主做不到真隔离，主 agent 先把自己查找阶段的结论放到一边，重新打开文件，先为反方辩护再打分，效果弱于子代理。
      • 没有场景就没有发现：每条发现必须写“具体的输入或状态 → 错误的结果”，写不出来的只是怀疑。这逼着查找角色去读代码而不是凭印象，也让 verifier 能逐步对照代码走一遍。安全类要写出攻击者可控的值从哪进、经过哪几步，规则类要逐字引用规则原文和出处。
      • 查找预算有界，但要说清楚：reviewer 每批最多交 15 条，这是查找预算，不是展示上限。回复里声明预算是否达限、覆盖是否受限；达到 15 条或主动声明受限时，报告和保存记录都标“流程不完整”，不杜撰没交候选的数量。reviewer 还对每块有效改动对照 base 过一遍最常漏的几类：去掉或缩小的保护（锁、事务、await、过滤、校验）、读-改-写的并发、包装层绕回自己、违反写明的约定、新实现处理空输入不一致、搬移时丢掉的行为。
      • 同一根因只报一条：同一种有缺陷的写法被复制到几处、一个改法能处理全部时，reviewer 只交主位置，其余写进 also_at，verifier 逐处核对，脚本去掉不在改动行上的位置；修法或失败场景不同的各自提交。脚本只合并关键字段完全等价的重复项，位置接近或摘要相似不算同根因；模型确要多对一合并时必须给理由并指向原件，这个理由是模型判断，不是脚本证明。
      • 封顶检查，不靠 verifier 当时的感觉：评分标准里有一组按顺序执行的封顶检查（行号不在改动范围内、别处有守卫使场景不可达、CI 本来就会拦住、命中误报清单等），第一条适用的直接决定分数上限。例外：本次改动破坏了接口自己写明的约定、或去掉了原有的保护（锁、事务、过滤、校验、await）时，不能用“现在没人这样调用”否决，因为下一个按约定调用的人就会出错。想调松紧，改 references/scoring-rubric.md。
      • 严重程度按后果的类型定：数据丢失或写入错误数据、崩溃或未处理的异常（含按约定的正常输入稳定返回 500）、约定违反导致调用方出错、安全边界破坏属于严重；异常已被处理、数据没写错但调用方拿到错误结果或状态码属于重要。评测里本该严重的问题被报成重要，是因为 verifier 因“影响范围窄”“后果还没出现”一路降档，所以只有后果的类型判断错了才改级别；影响窄、触发少只说明难触发，不改变后果的类型。
      • 依据要校验，没通过的要留档：每条通过的发现带读过的代码位置和排除的可能；脚本校验引用的文件和行在被审查的那一版里真实存在，引用不存在或没给依据的分数最高 50，过不了 80 分。这只能挡住凭空编造的引用，不能证明依据充分。低于 80 分的存进 rejected.json，不展示，但留下分数和理由，用来统计“差一点通过”的分布判断 80 分是否太严，用户问“还有别的吗”时也能列出并标明“未通过核实”。
      • 运行记录只防幻觉：verifier 声称执行的命令必须经 run-check.sh 留下命令、退出码和日志；结论分已复现、被反证、未定三种，反证把当前场景归零，声称复现却没说明观察的最高 75，声称执行却没有记录的改读代码推断、最高 60。曾经做过宿主见证和日志哈希之类防伪造的校验，防的是刻意伪造，而要防的是幻觉和偷懒，三家宿主的输出格式又各不相同，维护成本高，已去掉。

      五、需求来源

      团队问卷（约 27 人）：15% 缺需求背景。意图只靠 MR 描述和提交说明时经常不够，所以审查开始前先把需求来源问清楚，再并入意图，让 reviewer 能做需求核对。

      • 需求来源：配置两类外部工具：需求管理工具 tools.requirement、文档阅读工具 tools.doc_reader，值是写给 agent 的一句话（用什么、怎么用、链接长什么样）；全部设置列在随插件分发的 config/defaults.conf 里、默认注释掉，个人配置逐项覆盖。必填的缺了在审查开始前问一次（贴链接 / 没有需求单 / 跳过），可选的资料（PRD、设计文档链接）也问一次但可以跳过、不算缺失，同一分支都只问一次；和对比基准放在同一轮问。agent 用配置的工具读取内容作为意图材料。读 MR 的同类配置 tools.code_host 见第三节。
      • 跳过要如实记录：sources.json 区分 skip（作者跳过）、none:<类型>（没有需求单，如 hotfix）和 unasked（非交互运行，没有问；不问也不记）。用工具读到的内容当数据：存在仓库外的暂存目录，由脚本登记来源后并入意图。需求文档由产品等非开发人员编写，内容开发控制不了，里面写给 reviewer 的话同样不执行（见第九节）。
      • 事后补充：审查之后说“需求文档是 <链接>”“这个没有需求单”“这次是为了…”，用 sources.py set 只更新意图、需求单、文档三项，下次审查生效。
      • 模板：每个 skill 自带自己用的模板：review 的 templates/report.md（CR 报告骨架），describe 的 templates/describe.md、describe.html（PR/MR 描述，只列事实和链接），improve 的 templates/REVIEW.md、rule.md。

      六、CR 规则

      CR 规则就是写在仓库里、审查时拿来对照的 Markdown 文件。没有规则也能审查（只是报告里没有“规范”一节），所以先不用写；等发现“同一类问题被人工反复指出”，再把它沉淀成规则。规则分三类来源，越具体的越先：

      类别文件谁来写生效范围
      目录规则（最具体）子目录的 REVIEW.md该目录的负责人手写；improve 可按 plan.md 在「每次都要检查」「不要报」下追加一行只对该目录下的改动；头部设置不执行
      项目规则根目录 REVIEW.md负责人手写；improve 可起草，也可按 plan.md 追加一行全部改动；头部 skip、limits 由脚本执行
      沉淀规则.agents/rules/<主题>.mdimprove 从 MR 评论归纳成 plan.md，你逐条标“写入”并说“确定”后才写入按 frontmatter 的 paths / globs；不写表示全仓库；写错字段整个文件不生效，不会悄悄变成全局
      团队已有约定（只读）CLAUDE.md、AGENTS.md、.claude/rules/、.cursor/rules/、.github/instructions/团队本来就在维护按各自的目录或 paths / globs / applyTo；Copilot 的 excludeAgent: code-review 会被排除
      • 冲突怎么办：目录规则优先于项目规则，再优先于沉淀规则和团队约定。同一层里两条互相矛盾时，两条都不报，改发一条“规则冲突”的说明交给人处理。这一步由 rules-auditor 判断，脚本只负责排序。
      • 从哪一版读：审查 PR/MR、其他分支或提交范围时从 base 读，PR 改不了审查用的规则；审查自己当前的分支时读工作区。base 读不到就停止，不回退工作区。
      • 任何规则都不能越权：不能取消核实、降低 80 分门槛或授权写操作。REVIEW.md 头部只认 skip 和 limits；正文里的严重程度定义和证据要求照常采用。
      • 「出问题长什么样」：模板里有一节，由这块代码的负责人写它失败时会变成什么样（文档写错事实、配置接错路由或开关、迁移不可回滚）。它帮助判断后果类型，不改变严重程度的定义，也不用来挑风格、命名上的小毛病；不写也能审查。
      • 「不要报」：标题为「不要报」（或 Do not report）的一节写团队不想再被提醒的情况，只对它所在的目录或文件生效，本身不算要检查的规则；规则发现引用它会作废。
      • 团队已有的规则文件怎么用：内容完全相同的文件只输出一次（常见于 CLAUDE.md 和 AGENTS.md 互为副本）；这些文件大多是写给 agent 的操作指令（怎么跑测试、用哪个包管理器），rules-auditor 只挑能对照代码检查的陈述，并且要求改动行明显违反字面内容才报。不读 .cursorrules、.windsurfrules、GEMINI.md 这类少见的文件。
      • 多个项目共用规则：放进各项目的 REVIEW.md / AGENTS.md，用团队已有的方式同步，插件不另设分发机制。

      REVIEW.md 写什么、怎么写

      REVIEW.md 是只给审查用的短清单，每一条都应该是“光看代码不会知道”的信息。官方文档："Keep REVIEW.md to instructions that change review behavior, and leave general project context in CLAUDE.md."（只放会改变审查行为的内容，通用的项目背景放 CLAUDE.md）。Anthropic 的博客说得更直接："The good ones are short."（出处见本节末尾的“设计依据”）。

      官方文档按“遇到什么问题，就加哪类指令”来写。对应到 CrossCheck 的模板：

      遇到的问题在 REVIEW.md 里写什么对应哪一节短例子
      不重要的问题被标成重要重新定义什么算重要严重程度风格、命名、重构建议最高为轻微；scripts/ 下只在几乎确定且严重时才报
      小毛病太多限制轻微问题的条数头部 limitslimits: { minor: 3 }（官方示例：“Report at most five Nits per review.”）
      对生成文件、CI 已查的内容出评论列出要跳过的路径和类别头部 skip；不要报skip: ["**/generated/**"]；不要报：lint、格式、类型错误（CI 已经查）
      团队的规则没被查把每次都要看的写进去每次都要检查新增或修改图标组件时，必须判断是否需要加 rtl 类名
      发现经常有误要求先给证据严重程度说某段代码的行为有问题，要附 file:line，不能只凭变量名猜
      想让审查按真正的后果判断写这块代码失败时是什么样（Anthropic 博客）出问题长什么样订单和支付出错，表现为漏单、重复扣款；博客里文档是 "it lies"，配置是 "it misroutes"

      不该写进 REVIEW.md 的：

      • linter、CI 已经能查的：让工具去查，最多在“不要报”里写一句“CI 已查，不要报”。
      • 泛泛的规范，如“写干净代码”：说不出违没违反，见下面“一条好规则长什么样”。
      • 大段背景或设计介绍：放 CLAUDE.md。
      • 写给写代码 agent 的操作说明（怎么跑测试、用哪个包管理器）：放 CLAUDE.md / AGENTS.md。
      • 成批的、按文件类型或路径限定的规范：放 .agents/rules。

# Review 约定

## 严重程度

只有会导致行为错误、数据泄漏或无法回滚的问题才算重要及以上。风格、命名、重构建议最高为轻微。`scripts/` 下只在几乎确定且严重时才报。

## 每次都要检查

- 新增或修改图标组件时,必须判断是否需要加 rtl 类名(带方向的图标如箭头、返回要加;左右对称的如关闭、搜索不用)。原因:阿拉伯语、希伯来语界面方向相反。
- 日期格式化统一用 `src/utils/date.ts`,不要直接调用 dayjs。原因:时区统一在那里处理。

## 不要报

- `order_client` 已负责瞬时失败重试时,不要求调用方再加重试;最终失败仍须处理。
- `*.stories.tsx` 里写死的演示数据。

      怎么长出来，放到哪里

      • 从反复出现的评论里搬进来：Anthropic 的博客建议 "Add a REVIEW.md, and move repeated review comments into it"，先在一个仓库里调几周再推广（"tune REVIEW.md for a few weeks, then widen"）。Copilot 也建议先加一条或一小组，看下一轮审查有没有被遵循，再加下一批。不要一次写满。
      • 放哪的标准，看数量和范围：REVIEW.md 放一份短而完整的核心清单（严重程度、出问题长什么样、skip / limits、少量项目特有的必查、不要报）；.agents/rules 放成批的、按文件类型或路径限定的、带 MR 来源的规则，也就是 improve 沉淀的产物。机制上，严重程度、出问题长什么样、skip、limits 只有 REVIEW.md 里才会被读到。
      • 什么时候拆：REVIEW.md 超过约 15 条，或某一条只对某类文件、跨目录生效，就拆到 .agents/rules。“约 15 条”是我们自己的约定，不是官方数字，参照 Copilot 的“从 10–20 条起步”。官方没有给条数建议；它的做法是内容太长时用 @ 引入其他文件（最多 8 个文件，合计 150,000 字节）。.agents/rules 目录是我们的扩展，官方没有。

      一条好规则长什么样

      先看标准，再看样例。标准来自各家官方文档和 Google 的研究，括号里是出处简称，完整链接在本节末尾的“设计依据”里；标“CrossCheck 的做法”的是我们自己的约定，不是这些资料的说法。

      1. 具体、可衡量。别人拿着规则和 diff，不用问你就能说出违没违反。Greptile 写明 "Rules must be specific and measurable"："Write clean code"、"Follow best practices" 不行，"Functions must not exceed 50 lines" 可以。Copilot 也明确不支持 "Be more accurate"、"Don't miss any issues" 这类空泛要求。（Greptile、Copilot）
      2. 一条只讲一件事，不主观。Google AutoCommenter 发现，一个链接覆盖多条准则、主观有争议的话题、正确但价值低的评论，是“没用”评论的主要来源；屏蔽 22 条不可执行的规则并改写摘要后，有用率从约 54% 升到 80%。（Google AutoCommenter）
      3. 写清范围。Copilot 用 applyTo 限定路径，避免语言规则用错文件；CodeRabbit 的 path_instructions 每条对应一个路径；Claude Code Review 的子目录 REVIEW.md 只对该路径生效；Bugbot 的嵌套 BUGBOT.md 只在改动文件位于其下时生效。（Copilot、CodeRabbit、Claude Code Review、Bugbot）
      4. 短的祈使句，配正反例。Copilot："Short, imperative directives rather than long narrative paragraphs"，并建议 "Include code snippets showing both correct and incorrect patterns"；Qodo："Include brief code examples when helpful with before/after patterns"；Greptile："Include examples in your rule for best results"。（Copilot、Qodo、Greptile）
      5. 写清什么算严重、什么不要报。Claude Code Review 的 REVIEW.md 示例分 "What Important means here"、"Cap the nits"、"Do not report"、"Always check" 四节，并建议把 CI 已经检查的、生成文件列进不要报；对容易误判的一类发现，要求先给证据，例如 "behavior claims need a file:line citation"。CrossCheck 的做法：REVIEW.md 模板有“严重程度”“出问题长什么样”“不要报”三节，每条沉淀规则的“不要报”必填。（Claude Code Review）
      6. 项目特有、少而精、逐步加。Qodo："Focus on project-specific guidelines"，文件 under 800 lines，因为 "Long files tend to contain generic guidelines already known to AI"；Copilot 建议从 10–20 条具体指令起步，"Add new instructions one at a time or in small groups"，单个文件约 1,000 行为上限；CodeRabbit："Observe a few reviews first"，只在某处一直被漏掉时才加。CrossCheck 的做法：单个文件约 15 条或 4000 字符为上限，超过就按目录或主题拆开（这是我们自己的约定，不是官方数字，参照 Copilot 的“10–20 条起步”）。（Qodo、Copilot、CodeRabbit）

        用法做什么
        不带参数先列出三件事（沉淀、检查、整理 REVIEW.md），让你选一件再开始，不会直接动手。
        说“沉淀”，或带时间范围从最近一个季度已合并 MR 的人工评论和 CrossCheck 的判断记录里挑候选。脚本按准入清单核对：证据是原文、至少 2 个 MR、评论后代码确实改了或讨论已解决、能写成“必须/禁止”单句并有严重级别和“不要报”边界、不和已有规则重复。通过的生成 plan.md，每块的“去向”可以是 .agents/rules，也可以是某目录 REVIEW.md 的一节，所以一次沉淀可能同时写出规则文件和 REVIEW.md 里的一行。plan.md 和被丢弃的原因一起存在本机 ~/.crosscheck/mining/<项目>/ 下，不放进仓库。你和 agent 对话修改 plan.md，每次改完跑预演 rules-write.py <work_dir> --check，说“确定”才跑 --apply 写入工作区。--check 和 --apply 必须二选一。
        带“检查”逐条看现有规则：能不能检查、有没有范围和“不要报”的边界、是否重复或过长、是否长期误报。结果是一份修改建议，你同意后才改。
        带“整理 REVIEW.md”这是另一个用法，整份根目录文件的起草或整理，和“沉淀”往 REVIEW.md 追加一行是两回事。没有就按模板起草，有就整理设置和结构，口径是简洁：只留会改变审查行为的内容，约 15 条以内，背景和操作说明建议移走。路径只用仓库里确实存在的；“出问题长什么样”用项目里的事实填，拿不准就提醒负责人补；“不要报”从反复被判不成立的记录里找。同样先给 diff，同意后才改。
        • 什么时候维护：同一类问题被人工指出两次以上，就沉淀；审查里反复出现你认为不该报的，写进“不要报”；规则文件超过上限或长期没命中，就用“检查”整理。每次只加少量规则，下一轮审查看有没有被遵循，再决定要不要继续加。
        • 写到哪：审查时当场定的一条（“以后这种别报了”“以后都要查 X”）由 review 写进对应目录的 REVIEW.md，要写清范围和不报的条件，并带来源；从 MR 评论批量沉淀的，由 improve 先写进 plan.md，每块有“去向”：.agents/rules/<主题>.md、<目录>/REVIEW.md#每次都要检查 或 <目录>/REVIEW.md#不要报。建议值是：规则类进 .agents/rules；“不要报”类且范围正好是单个目录的进该目录的 REVIEW.md，其余进 .agents/rules。去向可以在对话里改，放哪的标准见上面“REVIEW.md 写什么、怎么写”：少量核心的进 REVIEW.md，成批的、按路径限定的进 .agents/rules。
        • plan.md 里有什么：每条候选一个块：候选编号与来源 MR、去向、动作、规则、原因、严重级别、范围、反例 / 正例、不要报。所有字段都能改。动作默认“待定”，要你逐条标“写入”或“跳过”；说“全部写入”才批量改。预演只打印、不写文件：WRITE: <文件> +<n>行、SKIP: 块 <n> 已在 <文件> 里、ERROR: 块 <n> <字段>: <原因>、PENDING: <k> 块还是待定；任一块有 ERROR，整批都不写。
        • plan.md 是唯一来源：你改的就是落盘的。--apply 往 .agents/rules/ 里的规则文件追加块；对 REVIEW.md 只在指定章节下追加一行，章节不存在就新建，不改头部。写入后该块的动作变成“已写入”，重复执行不会重复写。证据留在 candidates.json，来源 MR 的注释由脚本按候选编号写，不信任 plan.md 里改过的文字；不能在 plan.md 里凭空加没有候选编号的规则。不 git add、不提交。
        • 写入由 plan.md 把关，“待定”不写：动作是“待定”的块不会写；脚本核对证据来源、字段格式和规则句，预演有 ERROR 整批不写。准入清单里“项目特有”“工具抓不到”“不主观”这几项靠归纳时模型自评，脚本管不了，所以不让整批默认通过，模型自评的几项仍要你再看一遍。

        规则发现怎么保证可信

        rules-auditor 报出 rule_file + rule_quote 脚本核对引文和范围 对上了 verifier 确认违反

        引文不在那份规则里、规则不覆盖这个文件、没写引文的，置信度直接为 0。模型不能凭空编出一条规则来报。防得了编造，防不了漏看：没报的规则不保证每条都认真看过，靠规则文件保持短小来减少漏看。

        设计依据：REVIEW.md 怎么写，怎样的规则才好用，怎样维护，规则发现怎么保证可信
        • 规则就是普通文件，引原文再核实：Bugbot rules、CLAUDE.md / AGENTS.md、CodeRabbit 的路径说明都是普通文件；Claude Code 官方 code-review 命令要求规则违反引用原文，再由核实步骤确认。写规则不需要编号或元数据。
        • 核对引文，不证明“读过”：证明“规则在上下文里、每条都有结论”的机制证明不了判断是对的，还会给流程增加容易出错的环节；逐字引文由脚本和 verifier 核对就够了。
        • 好规则的标准（一手资料）：上面六条标准的原文都来自这些官方文档和论文：
          • Claude Code Review：REVIEW.md 自定义——子目录 REVIEW.md 只对该路径生效；示例分 "What Important means here"、"Cap the nits"、"Do not report"、"Always check" 四节；建议把 CI 已检查的、生成文件列进不要报；要求 "behavior claims need a file:line citation"。

          • GitHub Copilot：定制代码评审——"Short, imperative directives rather than long narrative paragraphs"；"Include code snippets showing both correct and incorrect patterns"；用 applyTo 限定路径；从 10–20 条具体指令起步，"Add new instructions one at a time or in small groups"，单个文件约 1,000 行为上限；不支持 "Be more accurate"、"Don't miss any issues" 这类空泛要求。

        • 每类规则单独检查：Amp 把规则放在 .agents/checks 下，每个 check 单独执行，比写进 AGENTS.md 更可靠。Amp：.agents/checks
        • 规则为什么有两个写入处：审查时当场定的一条（“以后这种别报了”“以后都要查 X”）由 review 按 after-report.md 写进对应目录的 REVIEW.md；从 MR 评论批量沉淀、成主题的规则由 improve 经 plan.md 写进 .agents/rules/<主题>.md（范围正好是单个目录的“不要报”，也可以写进该目录 REVIEW.md 的“不要报”一节）。两处并存，是因为 REVIEW.md 按目录生效，适合当场定的一条；.agents/rules 按 paths 生效，适合成批、带证据的规则。业界也是两样并存：Bugbot、CodeRabbit 在审查现场教规则（learnings），仓库里另有规则文件（见上面两条的链接）。当场写的那一行带来源注释（审查目标和发现 id），improve 检查时能追溯；写之前先查两处有没有同一条。
        • REVIEW.md 为什么要短，怎么放：官方文档："Keep REVIEW.md to instructions that change review behavior, and leave general project context in CLAUDE.md."，并按“遇到什么问题就加哪类指令”来写（重新定义重要、限制轻微问题条数、列出要跳过的路径、写团队规则、要求证据），没有给条数建议；内容太长时用 @ 引入其他文件（最多 8 个文件，合计 150,000 字节）。Anthropic 的博客："The good ones are short. They say what failure looks like in that repo (for docs it's "it lies," for config it's "it misroutes"), cap the nits, list paths to skip, and ask for a file and line as evidence instead of a guess from a name."；以及 "Add a REVIEW.md, and move repeated review comments into it"、"tune REVIEW.md for a few weeks, then widen"。Copilot："Begin with 10–20 specific instructions"，"Add new instructions one at a time or in small groups"，"Short, imperative directives rather than long narrative paragraphs"，不支持 "Be more accurate" 这类空泛要求；Greptile 要求 "specific and measurable"（见上面各条）。我们自己的约定：REVIEW.md 超过约 15 条就拆，依据是 Copilot 的 10–20 条起步，不是官方数字；.agents/rules 是我们的扩展，官方没有这个目录。Claude Code Review：REVIEW.md 自定义；Anthropic：Solving code review at Anthropic；GitHub Copilot：定制代码评审
        • 为什么先出计划文档，再写入：一是所见即所得：plan.md 里写的就是落盘的，不是对话里说一套、脚本另生成一套。二是单一来源：你和 agent 改的是同一份文件，证据留在 candidates.json，来源 MR 由脚本按候选编号写，不信任 plan.md 里改过的文字，也不能凭空加没有编号的规则。三是预演：每次改完跑 --check，不写任何文件，只打印会写什么、跳过什么、哪里有错，有错整批都不写。“动作”默认是“待定”而不是“写入”，因为准入清单里“项目特有”“不主观”靠模型自评，脚本管不了，整批默认通过会让没人看过的规则进仓库。业界参照只有一个：CodeRabbit 的 @coderabbitai emit path instructions 把近 7 天的建议汇总成 PR，由人审阅合并；我们的审阅物是本机一份 plan.md，通过后只改工作区，不开 PR。CodeRabbit：emit path instructions
        • improve 不带参数只列出三件事：沉淀要拉一个季度的 MR，不该被一次空调用触发；明确说“沉淀”或带时间范围才开始。它只能用命令调用（Claude Code、Cursor 用 disable-model-invocation，Codex 用 allow_implicit_invocation: false），避免一句话误触发这种重任务；只有 review 可以用自然语言触发。
        • 不自动改、不自动停用，维护靠负责人判断：一条规则长期零命中，可能是没用了，也可能是大家都遵守了，从数字上分不出来，所以只给线索。曾让 agent 现场提炼规则，结果不可复现、证据无法核对，才改成独立的 improve：规则只写工作区，不提交、不推送、不开 MR，走团队正常的代码评审。Claude Code、Cursor 写代码时不会自动读 .agents/rules/，需要时在 AGENTS.md / CLAUDE.md 里用 @ 引入（问过你才加）。拉取的缓存只存 MR 标题、作者和评论，不存描述原文。

        七、判断记录

        • 对某条发现表态（成立 / 成立但不修 / 不成立 / 有争议）由 feedback.sh 记在你本机的 ~/.crosscheck/reviews/<项目名>/feedback.jsonl（不在仓库里，也不共享给别人），对这个项目的所有分支、MR 和范围有效；不成立和不修必须写原因。
        • 判断记着那段代码的样子（出问题的一行加上下各两行的哈希）。代码没变就不再报，代码变了重新评估并注明之前的判断。
        • 不在核实前删除候选：历史判断交给 verifier 判断是不是同一个问题；因此没报的在报告里折叠列出，可以核对。
        • 团队共享常见误报：本机的判断记录只对你自己生效；想让全队都不再报，写进仓库里 REVIEW.md 的「不要报」一节，随代码一起评审。
        设计依据：记住人的判断
        • 记住人的判断：CodeRabbit learnings、Bugbot 学习规则都从开发者的回复和反应里学，避免同样的误报反复出现。CodeRabbit：Learnings；Cursor：Bugbot 从反馈中学习规则
        • 记在项目级，带着发现的身份：被否定的发现换个分支或 MR 又出现、撤回没被记下来，是第一批真实反馈里最先暴露的问题。判断不挂在某次审查的目录下，记录时只需要发现的 id，换个会话也能记。身份是文件、维度、摘要、出问题的那一行，以及这一行上下各两行代码的哈希：只用一行代码不够（return nil、} 到处都是），只用行号也不够（行号来自模型，常差一两行）。
        • 不在核实前删除候选：曾考虑过“文件、维度、行哈希都对上就直接丢弃”，被否决：常见行会让同文件同类的新 bug 被静默丢掉，同一行上的另一个问题被一起丢掉，调用方变了而这一行没变时照样丢，而且不可审计。
        • 事实和处理决定分开：“不修”不把当前证据分改成 0；“不成立”是历史判断，压不掉本轮已核实成立的发现。历史抑制要有匹配的记录，并核对当前场景、调用环境、触发前提是否仍是同一个问题，文件没变不足以自动抑制。折叠项保留当前置信度、结论、历史决定和抑制原因，“已抑制”不记成“已解决”。
        • 统计口径：判断和去向分开存，不互相折算；“代码已改”不叫“已修复”；成立率只按有人明确判断过的算，并标出样本数和选择偏差。为减轻只记否定带来的偏差，--fix 修好的和你明确认可的会自动记为成立。规范违规和缺陷分开计数；没有加行内的 crosscheck: ignore 标记，因为它会污染代码，还和 REVIEW.md 的“不要报”重复。
        • 不要从别的会话猜 token：用量只由 hook 统计，没有 hook 时写“未统计”。曾考虑推断当前会话的记录，被否决：那需要读本机其他会话的完整对话，可能含密钥，还可能选错会话。

        同一个目标再次审查默认做增量：diff 没变的文件不再查找，上次的发现原样带过来；变更或识别到依赖的文件重新审，本轮进入核实流程时，上次仍在发现列表且有历史处理判断的条目也重新核对前提，分成“遗留”和“已解决”，已抑制不算已解决。规则、用户给的意图或计划、审查设置、审查范围（--only、--with-tests）、模型或插件本身变了就全量重审；提交说明、MR 讨论和判断记录变化不触发全量。已进入历史抑制列表的条目不会自动带入以后每轮增量；符号名依赖匹配可能漏掉配置、反射等间接影响，环境广泛变化时可用“重新审”全量检查。读不到被审查的代码时停止生成结论，不出空报告。

        设计依据：记录和增量
        • 在本地存记录、只重看变了的：AI 评审工具普遍在每次提交后只评审新改动；Bugbot、CodeRabbit 把学到的东西按仓库存。Ellipsis：每次提交重新评审；CodeRabbit：Learnings
        • 项目级和分支级分开记：需求来源按分支记、90 天过期；基准默认不记，用户明确要求才保存为项目规则，和判断记录放在同一目录。换基准默认仅本次，明确说记住才更新保存的规则。
        • 记录放用户目录，不放仓库：放仓库里要加忽略规则，还会让“审查不改动仓库”不再成立；放 .git/ 里不容易找。代价是换机器或重新克隆后历史不跟着走。按文件 diff 的哈希判断是否变化，对已提交和未提交的改动一视同仁，不用 commit 判断，因为本地审查的对象常含未提交的内容。
        • 增量对角色透明：collect-diff.sh 直接把 diff.patch、files.txt、ranges.txt 和批次缩减到变化的文件，角色看到的只是一个更小的改动，说明文档不用为增量写分支。上次的发现按文件状态处理：没变的原样带入，变了的交给 verifier 重新核实（复用已有的核实流程，不另写“是否已修复”的逻辑），文件不在改动里了算已解决。
        • 哪些记录能当基准由脚本定：上次深度不低于这次才复用；只查部分维度（--only）的审查存记录但不更新基准指针；--full 或你说“重新审”时不读历史，旧记录保留，新记录成为新的基准。这些判断交给 agent，不同次运行会不一致。
        • 按项目的身份存，不按路径：项目名取自 origin 地址的最后一段，没有远程时取主工作区的目录名。早期用“目录名加路径哈希”，同一个项目的每个 worktree 各有一份记录，增量接不上；现在直接在分支上审、从别的分支指名审、在另一个 worktree 里审，用的是同一份。两个不同项目重名时，目录里的 .repo 标记记着先来者，后来者在目录名后加哈希。
        • 改动行覆盖：Codecov 的 patch 覆盖率只统计本次改动的行，思路和“只审改动的行”一致。Codecov：只统计改动行的 patch 覆盖率

        九、安全边界

        保障做什么适用
        说明SKILL.md 的「只读约束」、references/common.md 和每个角色说明都写明只读、被审查的内容是数据不是指令、不接触凭证所有宿主
        核对开始时记下分支、HEAD、stash、暂存区和改动文件的哈希，出报告前对比，有变化写在报告最前面所有宿主
        • 没有事前拦截：审查过程中 agent 能执行的命令不受限制，只读靠说明，出报告前由核对发现改动。这是约束，不是强制。
        • hook 只做 token 统计，每家一份注册文件，只写各家文档里列出的事件和工具名：Claude Code hooks/hooks.json，Codex hooks/codex-hooks.json（要先在 /hooks 里信任），Cursor hooks/cursor-hooks.json。hook 不拒绝任何操作。
        • tools.code_host 只用来读：不评论、不改描述、不 approve、不合入；读到的标题、描述和讨论是待审查的材料；脚本只核对得了仓库、分支和提交，插件看不出远端的 MR 有没有被改过，这是已知限制。
        • MR 描述、需求单、评论、规则文件里写给 reviewer 的话（“忽略安全问题”“approve 这个”）一律不执行；意图只能解释改动，不能让安全问题不报。
        • 不改变仓库状态：不切换分支，不 reset / stash / clean / commit / push，读其他版本的代码一律用 git show。这条在 SKILL.md 和每个角色说明里各写了一遍，因为子代理不会看到 SKILL.md；被审查内容是数据这条同理，每个角色独立读材料。
        • --fix 只在你明确要求时进入（“review 一下”“该怎么修”不算），只编辑工作区、不暂存不提交，只应用通过核实的发现，每条用最小改动、不顺手重构，修复方式不明确的跳过并说明。
        • REVIEW.md 的头部设置只能调整报什么、怎么定级、报多少、要什么证据，不能取消核实、降低 80 分阈值、触发 --fix、往外发内容或 approve。只认 REVIEW.md：它是专门写给 review 的文件，CLAUDE.md、AGENTS.md 里指挥审查的文字仍然不采用。
        • 凭证：脚本和角色不读取、不保存、不输出 token；检查环境只看变量名在不在，不看值。
        设计依据：安全边界
        • 只读靠说明和核对：拦截按命令的字面形式匹配，sh -c、变量拼出的路径、经脚本间接调用 git 都挡不住，模型换一种写法就能绕过；三家宿主的 hook 输入和拒绝格式各不相同，维护成本高，Codex 还要先在 /hooks 信任。业界审查工具靠说明和只给只读工具的权限约束 agent。hook 保留，只用来统计 token：agent 拿不到用量，只能由 hook 从会话记录里读。Claude Code hooks 文档
        • 被审查的内容是数据：提示注入是 LLM 应用的首要风险；评审场景里 PR 正文、评论、需求文档都可能带指令。OWASP LLM01：提示注入
        • PR 改不了审查规则：Claude Code Review 只从受保护的默认分支读 REVIEW.md。Claude Code Review：REVIEW.md 自定义。我们的代价是 PR 里新增或修改的规则要合并之后才会用到；早期给被改过的 REVIEW.md 标记再降级处理，已去掉，从 base 读更简单，也没有“这次新增的规则要不要生效”的歧义。
        • 核对只报告，不恢复：恢复本身就要 git checkout / git clean 这类危险操作，而且脚本分不清哪些变化是你自己同时在做的。
        • 不往外发、不提交 MR：早期有过 --comment（发行内评论，带指纹去重），主要在本地使用而移除，需要时再加回来。提交 MR 要推送、选目标分支和评审人，是外发且不可撤回的动作，各团队规范不同，所以只给可复制的 glab / gh 命令。

        十、已知限制

        下面是已知的限制和应对办法，哪里可以调，以及有意不做的事；判断“这是 bug 还是设计如此”时先看这里。

        限制与应对

        组限制怎么应对
        漏报与成本会漏报：80 分阈值和封顶检查会挡掉没能追踪完整的真问题；核实只能反证收到的候选，补不回查找阶段没提交的重点改动用 --depth deep；rejected.json 里 70–79 分的可以核对
        成本比单次扫描高：standard 有两个查找角色加若干 verifier，分批后随批次数增长小改动用 --depth quick
        分批按行数而不是依赖关系，跨批的问题更依赖 deep 的影响面那一遍跨模块的大改动用 deep
        80 分、每批 1000 行、各档条数上限都是经验值，没有在标注数据集上验证；分遍的效果缺同预算的对比数据，分遍之间也不独立积累 rejected.json 和判断记录再校准；对比要在同一批改动上做
        无子代理时隔离变弱（第四节）；依据校验只证明位置真实存在，不证明依据足以支撑结论重要结论对照报告里摘出的原文自己确认
        保存的报告由编排者写入，漏写或写错会不准发现的状态由脚本生成，不受影响
        增量与记录增量按文件粒度，依赖识别按符号名匹配；通过配置、反射、间接调用产生的依赖看不到，“旧改动在新上下文里变成问题”可能漏环境广泛变化时说“重新审”
        按历史判断抑制的条目不会自动带入后续增量变更或依赖文件的查找再次发现，或用 --full 全量重审
        进行中标记按审查目标存放：同一个目标并发审查时共用，可能误报“上次没保存”；describe 采集期间会临时写入并恢复这个标记和需求来源记录，与同一目标的审查同时运行也可能互相覆盖同一个目标不要并发审查，也不要同时生成描述
        判断记录是项目级、只在本机：同一段代码在别的 MR / 分支里再出现时也按历史判断处理（第八节）团队共享的常见误报写进 REVIEW.md 的“不要报”
        token 只统计 Claude Code 和 Codex；运行记录只防幻觉，不防刻意伪造报告里写明统计不到的原因
        规则规则检查防得了编造，防不了漏看；规则冲突只靠 rules-auditor 提示，脚本不检测规则文件保持短；冲突的说明交给负责人处理
        PR/MR 里新增或修改的规则合并后才生效（从 base 读，有意的取舍）先合入规则，再审查依赖它的改动
        沉淀规则时，GitHub 只翻最近更新的 1000 个已关闭 PR范围以 plan.md 开头写的天数和 MR 数为准
        GitHub 上评论是否已解决（resolved）和之后是否改了代码（changed_after）多数未知，准入清单里“作者照改了”一项显示“?”放行“?”项由你自己看；plan.md 的动作默认“待定”，不会整批通过
        准入清单里“项目特有”“不主观”靠模型自评，脚本管不了逐条标“写入”或“跳过”，预演通过再 --apply
        平台与环境自建 GitLab 的域名不含 “gitlab” 时认不出；部署在子路径下时 glab 需要的 GITLAB_HOST 没在真实环境验证过配置 gitlab_hosts 或带 --platform

        有意不做的

        不做原因
        采纳率统计没有团队真实使用前拿不到足够样本。现在看本地的判断和去向、rejected.json 里 70–79 分差一点通过的候选、以及成本；有几十个合并的 MR 后再考虑加回。
        “待确认”一节，放宽到改动行以外离线统计里，被否决的已知问题分数都在 5–20，漏掉的已知问题全在改动行上；放进“待确认”的只会是低分的东西。
        规则编号和元数据、“证明读过规则”、组织规则包和团队数据同步、创建规则 MR 的脚本、风险分级、simplifier、自动打开报告、借用登录 shell 重试 glab、deep 下同一模型换顺序重复查找一个机制要么对应问卷里的痛点或精确率，要么有业界的实际做法支撑；两者都没有的，在有使用数据之前不做。同一模型的盲区相同，重复查找收益有限。
        按语言罗列的缺陷清单曾加过 JS/TS、Python、Go、Java 四份，后来去掉：内容是宿主模型已经知道的，会随版本过时，鼓励“匹配到模式就报”抬高误报，收益也没被验证。值得写的是项目自己的约定，写在 REVIEW.md 里；魔法数字、命名、格式交给 linter。

        想检验效果：说“拿我们修过的 bug 测一下”，agent 从 git log 找修 bug 的提交、定位引入它的改动，对那次改动跑一次审查看抓没抓到，再用普通改动做对照看误报。模型每次运行都不同，样本少时只能看出明显的问题。

        设计依据：为什么这些地方先不做、先不验证
